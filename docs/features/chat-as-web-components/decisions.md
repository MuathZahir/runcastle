# Decisions — chat-as-web-components

## 1. The server drives the agent through structured protocols, not a terminal
**Decision:** Claude Code chats run through Anthropic's Agent SDK (`@anthropic-ai/claude-agent-sdk`, already a server dependency for model discovery), pointed at the human's installed `claude` and launched with today's per-session flags (settings, MCP config, plugin dir, system prompt, permission mode, model). Codex chats run through `codex app-server`, the JSON protocol Codex's editor plugins use. Both sit behind the existing per-runtime adapter, so the rest of the server sees one interface.
**Why:** The SDK already carries the hard parts of an interactive session (tool approvals, the multiple-choice question widget, interrupt, permission-mode changes, resume by id), so we don't hand-roll that protocol against a CLI that changes between versions. Running the human's own `claude` keeps their login, hooks, plugins and version, as the terminal does today. If the SDK proves wrong, the cost stays inside the Claude adapter: it speaks the same JSON messages as Claude Code's raw stream mode.

## 2. One protocol for both runtimes: ACP through the official adapters; our own components
**Decision:** The server speaks the Agent Client Protocol (ACP) to every chat, through the two official adapters: `@agentclientprotocol/claude-agent-acp` (built on the Agent SDK, run against the human's installed `claude` via `CLAUDE_CODE_EXECUTABLE`, with our per-session flags passed through its `_meta.claudeCode.options`) and `@agentclientprotocol/codex-acp` (built on `codex app-server`, run against the human's installed `codex` via `CODEX_PATH`). The server uses the ACP TypeScript SDK's client side, owns the agent process, and streams to the browser over runcastle's own connection, so a chat survives a closed tab and runcastle's messages to an agent go in as ordinary prompts. The chat UI is our own small set of components on our design system (message, tool activity, approval card, question card, composer); `acp-components` is read for how it lays out tool calls and approvals, not adopted.
Refines: 1 (the Agent SDK and `codex app-server` still sit underneath, inside the adapters).
**Why:** One client instead of two hand-written protocol layers, and protocol churn from Anthropic and OpenAI is absorbed by adapters maintained elsewhere and used by Zed, JetBrains and VS Code clients. The cost is one extra process per chat and two dependencies we don't own. `acp-components` is a whole workbench with its own theme and store and little adoption; `assistant-ui` would cost as much to map ACP onto as writing the handful of pieces we need; `claudecodeui` is AGPL.

## 3. Every agent conversation moves; xterm stays only for program output
**Decision:** Every session kind that is an agent conversation moves to the web components: the feature chat, side sessions, the project chat, the preparation chat, and the drive's scenario and "Fix it" chats. xterm stays only for terminals that are a program's output rather than a conversation: the dev-server panes in a drive and in design mode, and the one-off flows on the Settings AFK checklist (`claude setup-token`, Codex sign-in, the image build).
**Why:** All agent conversations already render through one shared chat column, so moving only the feature chat would keep two paths alive in the same component with two behaviours to test, and would leave the project page, which design mode gave the same shape, still a terminal. Program output is what xterm is for.

## 4. What the chat keeps from the terminal: five things, no plan mode
**Decision:** The chat keeps: approvals (an ACP permission request is a card in the chat: Allow, Always allow, Deny); the multiple-choice question widget (a card with clickable options and a free-text "Other"); slash commands (`/` in the composer lists the session's commands and skills, from the adapter's command list); interrupt (a Stop button while the agent works, Esc as its key); and resume (reopening a chat loads the same conversation and replays its history into the column, including conversations begun in a terminal). There is no mode switch: no plan mode, and a session keeps the permission mode it was launched with. The CLI's terminal-only screens (its own `/resume` picker, `/config`, `/login`) are not rebuilt.
**Why:** Runcastle's own workflow (grilling, the spec, the plan preview and the human's yes before a round) does plan mode's job, so a switch would be a second, competing way to plan. Runcastle already owns resume, and settings and login stay in the CLI.

## 5. Select area crops land in the composer as image attachments
**Decision:** A Select area crop from the design pane no longer opens its own comment popover or types `[Screenshot: <path>] <text>` into the chat. It lands in the chat's composer as an image attachment (a thumbnail chip) and focuses the composer; the human writes the message there and sends it, and the agent receives a real image content block with the text. Several crops can ride one message, and pasting or dropping an image into the composer works the same way. A sent message shows its images as thumbnails in the conversation. The drive's note popover is unchanged: notes are not chat messages.
**Why:** The composer becomes the one place the human writes to the agent, and the agent gets the picture itself instead of a path it must open. The cost is one extra step for a wordless crop; a "send now" on the chip is a cheap later addition if that proves slow.

## 6. No separate headless runs of a chat: a wake starts the chat itself
**Decision:** A lead wake (Go, a round's end, a message with no chat open) and an orchestrator relay start, or resume, the feature's chat itself and send their message in as an ordinary prompt; the chat stays up afterwards like any other, so the human sees it work live and can answer an approval or type. The separate headless lead path, and the guard that kept it from colliding with an open chat, go away. A self-planning run stays unattended: its brief still says nobody is watching, and its approvals and questions are declined automatically so it cannot hang; it is still an ordinary session the human can open and watch live, and anything they type goes in as its next prompt.
**Why:** With the server owning the agent process anyway, "headless" no longer needs to be a second way of running the same conversation, and the human gains sight of work they cannot see today. The cost is that a woken lead keeps a process up after its turn, as a chat the human opened does.

## 7. Threads open instantly; the agent process is invisible
**Decision:** The chat behaves like ChatGPT threads, not terminals.
- **Showing is separate from running.** As a chat streams, runcastle saves every message, tool call and approval to its own log on disk. Opening a thread renders that log at once, with no agent process involved. Conversations from the terminal era have no log and show through the existing transcript reader as plain text turns.
- **No Resume or Start screen.** Every thread is its history plus the composer. Sending a message starts the agent in the background if it is not running (resuming that conversation); the message shows at once with a quiet "starting…" until the agent takes it. A new thread is an empty history plus the composer.
- **Processes are not the human's concern.** An agent process with no turn running for 30 minutes is stopped quietly; one waiting on the human's approval or answer is never stopped. The next message brings it back. "End session" and "Live" leave the UI; a thread shows only whether the agent is working, waiting on the human, or idle.
- **Every thread can be opened.** The header switcher is the thread list: the feature's main chat, its side sessions and its scenario chats, finished ones included, newest first, with "New thread" (a new side session). On the project page it lists the project's chats.
Supersedes: the "Resume the conversation" / "Start the conversation" chat-at-rest screen and the automatic resume on opening a feature (`opening-a-feature-shows-its-chat-as-you-left-it`).
**Why:** The human: "One thing I hated about the terminals was that they take time to open so we needed these 'Resume conversation' screens. I don't want these. The conversations should feel like chatgpt. They're multiple threads and I can open any." The cost is a second, small copy of each conversation that runcastle owns (so its format cannot change under us), and a few seconds' wait on the first message after an idle stop, shown on the message rather than as a screen.

## Revisited 2026-10-26 (after the first design round)

## 8. The chat's look: approved from the design preview
**Decision:** The chat column is built from the components approved in `apps/web/preview/chat.html` (`apps/web/src/components/chat/thread/`): a raised composer floating over the thread's faded foot, with the sidebar's travelling edge light while the agent works; the agent's words as full-width prose, the human's in a bubble on the right; a settled turn's work folded to "Worked for 3m 43s" with only its answer in view, followed by a changed-files card; live work shown step by step (thinking, subagents, narration, the call in flight shimmering); the agent's task list and background commands on a strip over the composer. What the agent waits on the human for docks in the composer's place: approvals with Claude Code's three answers (yes; yes and don't ask again; no, and say what to do instead), edit approvals showing the diff first; questions one at a time with numbered options, a typed "Other" as the last option, single choices moving on by themselves, and a "Check your answers" page when there is more than one question.
Supersedes: decision 4's "a card in the chat" for approvals and questions.
**Why:** The human, on the first round: "it doesn't look very professional and polished … Look at t3code's UI … I want something at that level", and asked for questions to work like Claude's: "The questions appear one at a time … The question UI replaces the text input at the bottom and should have an 'Other' text input." Approvals dock the same way so the human's eye is always in one place when the agent waits.

## 9. Model, effort and fast mode per message
**Decision:** The composer carries a picker for the model and effort (and fast mode where the runtime offers it) that the next message runs on; a change shows in the thread as a divider ("Now on Sonnet 5.5"), and each answer names the model that wrote it. A thread starts on the model runcastle resolves for its kind. The models offered are the thread's runtime's: switching between Claude and Codex inside one thread is not offered; a new thread does that.
**Why:** Both adapters take a model change mid-conversation, so it is a picker and a divider. A thread is one runtime's conversation, so a cross-runtime switch would be a new conversation in disguise.

## 10. Going back: edit, rewind, branch
**Decision:** Hovering a message offers copy, edit and branch. Editing a past message rewinds the conversation to just before it and sends the edited text in its place ("Rewind and send"); on Claude threads a checkbox, on by default, also undoes the agent's file changes since then through Claude Code's file checkpoints. Codex threads rewind the conversation only. Branch starts a new thread carrying the conversation up to that message. Retry is editing the last message unchanged. Editing is offered only while the thread is idle.
**Why:** Claude Code's rewind and Codex's fork are both carried by the adapters; only Claude has file checkpoints, so the file undo is offered only where it is real.

## 11. The capability inventory is the scope
**Decision:** `capabilities.md` lists everything a person does in Claude Code's or Codex's terminal and where each lands. Every row marked in there is in scope for this feature; the "Not rebuilt" list is out: login and logout, the CLI's own settings screens (`/config`, `/permissions`, `/hooks`, `/memory`), themes, vim mode, keybindings, `!` shell mode, the CLI's `/resume` picker, plan mode and the permission-mode switch.
**Why:** The human: "I want almost everything the user can do in claude code or codex to be available here … I want to make sure that I thought of everything." They approved the inventory as written.

## Revisited 2026-10-27 (after the first test drive)

## 12. A chat's opening and the human's first message are one prompt
**Decision:** When a thread starts because the human sent its first message (a never-started feature chat, a new project chat, the preparation chat, New thread), runcastle's opening briefing and that message go to the agent as one prompt. The thread still shows the runcastle line and the human's bubble, and the agent answers once. Threads that start by themselves (self-planning, scenario and Fix-it chats, lead wakes) still send their opening at once.
**Why:** The human, driving: "it seems to me that this is two different responses". Sending the opening first and steering the human's message into its turn made the agent greet twice.

## 13. The model and effort controls: one list, searchable, grouped; effort on its own
**Decision:** The model picker shows one list, the same before and after the agent starts: searchable, grouped by model family, newest first, older versions folded away, the current model checked. Effort is its own control beside the model, offering only the levels the model supports; fast mode is its own toggle where the runtime offers it. Both can be set on a thread that has not started yet and apply from its first message. Dividers name the real model, never "Default (recommended)".
Refines: 9.
**Why:** The human: "The model selector is hideous.. So many models, no grouping, no sorting, no search … The effort chooser also looks very bad. It should be a separate input anyway, not in the selector", "When I changed the model, the whole list of models changed", "I can't set the model before I start".

## 14. New chat always opens a new thread
**Decision:** New chat on the project page and New thread in the header do the same thing: open an empty thread, whatever else is running. Any number of a project's chats can run at once; there is no "one chat open" notice or "end it and start new". Every thread in a list is named by its generated title or its first message, never by its kind.
Refines: 7.
**Why:** The human: "I can't create a new chat when one is running???" while the header's New thread did create one, leaving two threads both called "Runcastle project session".

## 15. After the lead replies, the feature waits on the human, everywhere
**Decision:** When the feature's lead ends a turn and the human has not answered it yet, the feature reads "Waiting for you" in the header and "Waiting on you" with the amber dot in the sidebar, whether or not the lead asked anything explicitly. One rule drives both places, so they never disagree.
**Why:** The final review found the header saying "Talking with you" while the sidebar said "Waiting on you" for the same feature, because the sidebar read the thread's turn end and the header did not. The human chose the lead's recommendation: after any reply the next move is the human's, and the amber dot then shows a reply that came while they were elsewhere, like an unread chat. The cost is that a lead that only said "ok" still turns its feature amber until answered.
