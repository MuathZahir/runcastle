Tickets stop repeating checks, and tests earn their place

Ticket agents run only the checks for what they touched and write a test only where it protects real behaviour. The full gates run once per commit on the host, and nothing re-runs them on a branch that has not moved.

One full gate run per commit. A break elsewhere shows up as red round gates, and the lead runs a fix round whose ticket re-runs just the failing check 11.

A test is worth writing 6

  • logic with branches
  • a contract between modules
  • a bug just fixed, as its repro

Not worth writing

  • class names, copy text, static config
  • markup snapshots
  • tests that restate the implementation

Nothing worth testing: no new test, and the digest says so. The reviewer flags a useless test as a low observation, and the lead folds it into a fix ticket the round mints anyway 8.

How it gets built

One round. Tickets 1 and 2 touch different files and run side by side; the review checks both.

Under the hood

Ticket 1 · prompt and skill text

The burner prompt (its prefix above “Your ticket” stays identical across tickets), the verify-notes block built per project, the defect-fix note, the review prompt, the ticket-writing guide, and the prepare skill’s line on verify commands.

Ticket 2 · the reuse lookup

Before running the gates, the round end and the review pass both ask one shared lookup for a stored result on this feature that has:

status “ran”+ same commands, same order+ commit = tip, or only docs/features/<slug>/ changed since →reuse: copy record and logs, mark it reused

No hit, or the lookup itself fails: run the gates as today. Candidates are each round’s stored gates and each review ticket’s stored gate run; the newest wins.
