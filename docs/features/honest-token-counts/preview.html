How it gets built

No worker tickets for the build: it is one connected change to the counting code that fits one session, and workers here run one at a time anyway.

  1. The lead builds it in this chat, with the project's typecheck and tests green.
  2. One review round: a review ticket checks the code against the spec and the meter on screen.
  3. You test-drive the meter and read the recount; then Merge.

Under the hood
  • Core summing gains a per-message form: each counted message with its timestamp and its split (input, 5 min and 1 h cache writes, cache read, output). Sub-agent transcripts as today.
  • Usage service counts a whole conversation at once: the rows sharing its transcript plus the launch records (the existing "session launching" event, added where a launch path lacks one). Each row stores total, split and a by-purpose split.
  • When: turn end reads only the new part of the transcript (byte offset + last message id); session end recounts in full; feature read and round end stay as backstops. A missing or shorter transcript never lowers a figure.
  • Backfill: one pass on first boot, guarded so it runs once. Gone transcripts: newest row keeps the figure, the others go to zero, all marked not recounted.
  • Review workflow keeps its worker run's result and feeds the same harvest implementation tickets use.
  • Weighted tokens are derived, never stored: one core function plus a documented SQL query (per day, kind, purpose).
  • Launcher sets or clears a reused row's purpose on every launch.
  • Meter: tone rule and label in the shared context-meter component; thresholds are constants.
  • Sandcastle patch: file tools added to its tool-argument map.
