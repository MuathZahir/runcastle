- [ ] [Code review — Standards axis] The burn-time copy command hand-builds a Windows path with a literal separator. packages/server/src/workflows/ticket-burner.ts, in buildAttachmentCopyCommands: `copy /Y "${src}" "${dir}\\${basename(src)}" >nul`. CLAUDE.md § Conventions states "Windows paths: always node:path (join, resolve); never hand-concatenate; quote paths in shell commands". The quoting half of the rule is honoured; the concatenation half is not — the destination is assembled with a hardcoded `\\` rather than `join(dir, basename(src))`. Judgement call, not a hard break: the string is a cmd.exe argument and the test at packages/server/test/burn-attachments.test.ts ("copies with the shell each host actually has") asserts this exact spelling, so it works today. Expected: the destination built with node:path like every other path in the codebase.
- [ ] [Code review — Spec axis] The burn-time screenshot never reaches the agent under the default Windows/macOS burn mode. spec.md "Riding into the burn" says "Copy-at-burn works identically under docker and noSandbox". It does not. Verified chain: (1) config.ts defaults sandbox='docker' and burnWorkspace='auto'; (2) resolveBurnWorkspaceMode (ticket-burner.ts ~511) returns `platform === 'linux' ? 'mounted' : 'isolated'` for 'auto' — so on this Windows host the default is 'isolated'; (3) the attachment copy is a hooks.host.onWorktreeReady command with cwd = the host burn worktree, i.e. the MOUNTED workspace (/home/agent/workspace); (4) buildIsolatedSetupCommand (~578) then runs `git clone /home/agent/workspace /home/agent/repo`, and buildWorkspaceNotes (~616) tells the agent "Do ALL work there: cd /home/agent/repo first". A git clone carries tracked content only, and the PNG is untracked AND listed in .git/info/exclude by design — so it cannot arrive in the clone. The ticket context still says "An annotated screenshot of the problem is at .runcastle-attachments/<noteId>.png in your workspace — Read it before starting", and that relative path resolves to nothing from /home/agent/repo. Expected: the agent can Read the screenshot on a default docker burn. Actual: the Read fails on every Windows and macOS docker burn; only a Linux host (mounted) or an explicit burnWorkspace='mounted' / sandbox='noSandbox' works. This is not the graceful degradation the spec allows for — that is scoped to "A missing PNG at burn time"; here the PNG exists on the host and the context names a path the agent cannot reach. packages/server/test/burn-attachments.test.ts only exercises the mounted worktree, so the gap is invisible to the suite.
- [ ] [Code review — Spec axis] The attachment exclude writes a permanent, never-removed line into the human's own repo. spec.md "Riding into the burn" says only "The attachment directory is cleaned out of the workspace before commit/merge so it never lands in the repo." The implementation adds a second, stickier mechanism: excludePath (packages/server/src/services/git.ts ~707) appends `.runcastle-attachments/` to the project repo's .git/info/exclude before the first copy, and nothing ever removes it. Because git resolves info/exclude against the COMMON git dir, that one line applies to the parent checkout too — so from the first annotated-note burn onward, any directory named .runcastle-attachments/ in the human's own working tree is silently invisible to their `git status`, forever, in every worktree. Reproduce: promote an annotated note, burn it, then `cat .git/info/exclude` — the line is there after the run completes. Expected (from the spec wording): a cleanup confined to the burn workspace. Actual: a permanent per-clone git config change. The directory-clearing half (clearAttachments) also runs after run() returns rather than "before commit" — before merge, so the merge is safe, but the agent's own commits during the run are covered only by the exclude, not by the clean.
