Epic messages reach a busy agent at once

A message an epic sends a feature's agent goes into its running turn right away, as your own typing in that chat already does, instead of waiting for the turn to end.

The show

Today an epic's message to a busy lead waits until the lead's whole turn ends. After this, it goes straight into the turn 1, whether it carries your words or the epic's own 2.

After
lead's turn

Same moment, same turn: the lead reads it mid-work, as it does when you type in its chat.

Runcastle's own notices to a lead (worker handbacks, news, restarts, merge conflicts) keep waiting for the turn's end, as do your test-drive notes 3. A message that arrives while the lead is compacting waits for the compaction to finish 5.

In the feature's chat, the epic's message looks as it does now, with one new line under it 4. It still never counts as you typing there, so it does not clear the lead's "waiting on you".

Under the hood

The agent host's prompt queues every runcastle-sourced prompt behind a running turn and steers the rest. A new steer option lets a runcastle prompt take the steering path while keeping its source, so it still renders as the epic's message and never fires the human-typed path that clears waits.

Lead delivery gains a matching flag; only the epic's send_to_feature sets it. Existing guards keep their order: news-only holds, usage-limit holds, compaction queues, "turn just ended" falls back to the next turn, a runtime without steering queues (Claude and Codex both steer).

Web: the runcastle display branch passes the item's existing steered flag to the epic's message, which draws the same label as a steered human message.

Tests: agent host with the fake ACP agent; send_to_feature through lead delivery; the chat thread component.
