# Decisions — review-as-a-lap-trail

## 1. One lap, spec the whole thing
**Decision:** Sure-and-small: the backend half (the `unverified` outcome, the recorded mode, the prompt failure branch) and the UI half (the lap trail, the Agentic review button) are specced together as one lap.
**Why:** Both halves are well-bounded, the uncertain parts are design decisions settled in this session rather than things needing a prototype, and shipping only half leaves the post-mortem's failure half-closed — a loud outcome nobody can read in context, or a trail that cannot say "nothing verified". The codebase survey confirmed the trail mostly re-presents already-persisted per-pass data (tickets carry `lap`/`passKind`/`digest`; `routes/reviews.ts` already synthesises per-pass artifacts), so the UI half is smaller than it sounds.

## 2. Unverified detection: declared, artefact-cross-checked, downgrade-only
**Decision:** The review template mandates a machine-parseable declaration block in the digest — mode actually run, verified-or-unverified, one-line reason when unverified — which the harvester parses. Artefacts cross-check where they exist and can only downgrade: Drive declared verified without `walkthrough.webm` on disk lands as `unverified`. Gates has no positive artefact, so its declaration stands (`GATE_UNRUNNABLE.md` remains the negative channel). A missing or unparseable declaration block is itself `unverified`.
**Why:** The audit showed agents report honestly and the orchestration lied by reading "digest exists" as "reviewed"; a mandated declaration makes honesty machine-readable, and the downgrade-only cross-check catches the one observed failure (drive claimed, no drive happened) for free. Inference-only is impossible for Gates; declaration-only misses the webm check that costs nothing. The unparseable-block default inverts today's root cause: absence of evidence lands as absence of verification — loud, not blocking. The declaration block is also the source of the recorded mode that verification passes read (brief point 3).

## 3. Verdict and mode are ticket columns, not a status
**Decision:** `unverified` is not a ticket status. A review ticket still completes as `done`; two new persisted columns on the tickets row carry the outcome: `reviewMode: 'drive' | 'gates'` (what the pass actually ran, parsed from the declaration block — the recorded mode verification passes read, replacing the webm-existence check) and `reviewVerdict: 'verified' | 'unverified'` with a reason text. All the loud surfaces (trail entry, succeeded-unverified run card, templated digest headline, next lap's injected context) read the verdict. `couldNotReview`/`failed` is untouched — a pass that never ran is different from one that ran and verified nothing.
**Why:** Behaviourally an unverified pass is done for scheduling (auto-advance fires, findings stored, nothing blocks), so a third status buys no behaviour and costs a change to the state machine that "Four states and two hard rules" owns and this feature must not swallow.

## 4. Stage stays feature-scoped; the trail is the index and absorbs the earlier-recordings popover
**Decision:** The evidence stage keeps today's default: it plays the latest recording that exists from whatever lap, identified by lap in its identity line — the stage is the viewer, not a lap's property. The trail is a new full-width band, one entry per lap, newest first, all laps visible, no disclosure; it replaces the "Earlier recordings (N)" `<details>` popover. Clicking a trail entry's recording stages it in the existing player (the `picked` mechanism). The notes rail (`NotesRail`/`OpenWork`/`CarriedFindings`) is untouched — open work stays the rail's business; the trail carries the historical per-lap record.
**Why:** Decision 19's blank-stage rationale is honoured by never lap-scoping the stage: lap 4 with no recording still shows lap 3's on stage. The popover was the latest-only design's escape hatch and is redundant once the trail lists everything.

## 5. A trail entry is a lap; unverified renders as the template line in the entry plus an arrival banner for the current lap
**Decision:** Each entry: header (lap number, completion time, outcome chip = latest completed pass's verdict: `Verified · drive/gates`, `Unverified`, `Could not run`); what burned (ticket count linking to the run view, not duplicating it); one compact row per review pass in the lap (pass kind, mode, verdict, recording link that stages it — the old popover's listing lives on here); defect counts only (found / fixed / carried) plus test-note count — observations stay in the Full account (review-arrival-is-legible d8). An unverified entry's outcome line is the runcastle-filled template ("Lap 3 · drive mode · DRIVE FAILED · nothing verified") plus the declared reason, never agent prose. Separately, when the current lap's review is unverified the page arrives with "nothing verified this lap" as the top line — arrival-banner/StatusStrip territory, not inside the trail.
**Why:** A lap can hold several review passes (review, verification, agentic re-reviews), so the entry must be the lap with passes as rows. The trail is history and the arrival line is now; splitting them keeps the trail stable while the loud line does its job on arrival.

## 6. Agentic review: always visible, disabled-with-reason mid-burn, never queued
**Decision:** The button is present in every review-page state, on every lap, regardless of outcome — that is what "always available" means. While a run is live it is disabled with a reason ("a burn is running"), the same pattern the adjacent Test drive button uses for the occupied drive slot. No queueing; the moment the run ends it is clickable with no further conditions.
**Why:** The button is itself a burn and one-burn-at-a-time is a hard rule owned by "Four states and two hard rules". Queueing is new machinery that fires a burn at a surprising later moment; disabled-with-reason is the established adjacent idiom.

## 7. The button mints fresh; the denied-retry special case dies; the banner keeps its notice but adopts the mint
**Decision:** Agentic review mints a fresh `kind: 'review'`, `passKind: 'review'` ticket on the current lap and burns it; mode is chosen fresh by availability (no inheritance — inheritance is verification's business); its findings join the current lap under existing carry/link/close rules. The `retryingDeniedReview` special case in `retryTicket` is deleted — `retryTicket` returns to failed-tickets-only. The dirty-denial banner stays as information (denial + dirty files) but its action becomes the Agentic-review mint, and the `driveBlockingPaths` pre-check moves with it: when the latest run was denied-dirty, the mint refuses first, naming the files.
**Why:** A fresh mint supersedes resetting a `done` row and keeps history honest — the denied pass stays in the trail as what it was. The pre-check keeps its purpose: never burn an agent just to rediscover a dirty checkout.

## 8. Recording capability is part of drive availability, probed before spawn
**Decision:** Drive is offered only when all three hold, probed pre-spawn: `agent-browser` on PATH, `agent-browser` answers a cheap health invocation (e.g. `--version` exits 0 — working state, not just presence), and ffmpeg is present. Any missing piece makes drive unavailable; the availability block names the specific reason, the pass runs Gates, and the reason lands in the pass's recorded outcome.
**Why:** Resolves the latent conflict with decision 2: if a drive could run without ffmpeg, the missing-webm cross-check would downgrade an honestly-verified pass. Gating on recording capability buys the invariant that an offered drive can always record, so the cross-check never fires on an honest pass — and ffmpeg absence is reported as the reason Gates ran, not silently downgraded (brief point 3).
