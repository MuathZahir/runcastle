# Decisions — Model roster discovers new models

## 1. Discovery sources: Agent SDK for Claude, the Codex models cache for Codex
**Decision:** Claude models are discovered through the Claude Agent SDK's `supportedModels()` / `initializationResult().models` (the account-aware list behind Claude Code's `/model` picker), with the SDK pointed at the host's own `claude` executable (`pathToClaudeCodeExecutable`) and no prompt sent, so nothing is billed. Each entry is recorded by its pinned id, `resolvedModel ?? value`, never a bare alias. Codex models are discovered from `~/.codex/models_cache.json`, which the ChatGPT backend feeds to the Codex CLI, keeping only `visibility: "list"` entries. There is no runcastle-published remote list.
**Why:** Both sources run on the subscription logins runcastle already uses. Anthropic's `GET /v1/models` is documented as API-key-only, so building on OAuth there would rely on undocumented behaviour. Pointing the SDK at the host CLI makes the list match the binary runcastle actually launches. Pinned ids keep a ticket's model stable across laps, where an alias like `opus` would silently move. A remote list would be one more thing to maintain, and it could never be specific to the account.

## 2. Roster layering: curated, then discovered, then the operator's entries
**Decision:** The roster is `CURATED_MODELS`, then discovered models, then the operator's `models` entries, merged by id with the later layer winning. Operator entries (notes, custom ids, declared runtimes) always win, and discovery never writes into `config.models`. A discovered model's runtime comes from its source: the Agent SDK gives `claude-code` and the Codex cache gives `codex`. Discovered metadata (display name, description) replaces curated metadata for the same id. Curated stays as the fallback floor for when discovery has not run or has failed. Discovery results persist in their own cache under `~/.runcastle/`, separate from the operator's config.
**Why:** It keeps what the operator declared separate from what the providers reported. Use-case notes survive because they are keyed by id and nothing but the operator writes them. Runtime is never inferred from an id's spelling. A fresh or offline machine still gets a usable roster.

## 3. Cadence: at boot and on a manual Refresh; failures are quiet and per source
**Decision:** Discovery runs once in the background at server boot, without blocking startup, and again whenever the operator clicks Refresh on Settings → Models. There is no periodic timer and no staleness trigger. Each source fails on its own: a source that cannot run (no Claude login, no Codex cache) keeps its last good result, and the Models page shows one status line per source (count and age, or why it failed). Discovery never blocks a launch. A change to the discovered set emits an event so open choosers update.
**Why:** Models ship every few weeks, and starting the SDK spawns a CLI process, so a timer would cost more than it earns. The Refresh button covers the "a model just shipped" moment. Per-source quiet failure means a Claude-only or Codex-only operator never sees one runtime's missing login as an error.

## 4. Visibility: full dropdowns, collapsed roster table, "new" / "no longer offered" / retirement flags
**Decision:** The model dropdowns list the full merged roster, grouped by runtime as now. In the roster table, untouched discovered models collapse behind "show all" like untouched curated ones, except that a model which appeared in the latest discovery run and was absent from the previous one shows a **new** badge and stays visible until the next run that changes the set. When a model drops out of discovery: if nothing references it, it simply disappears; if it is annotated, used by a step, or the default, it stays and its row is flagged **no longer offered by Claude/Codex**. Retirement notices that the Codex cache carries (`upgrade`: retirement date and replacement model) show as a hint on that row.
**Why:** The dropdown is where a new model actually gets picked. The "new" badge is how a new model reaches the operator without anyone typing it in. A model that vanished but is still referenced needs a warning before a launch fails on it. The retirement data is already in the cache, so surfacing it is cheap.

## 5. annotatedModels stays annotated-only; every roster consumer reads the same merged roster
**Decision:** Discovery never adds notes, so `annotatedModels` still lists exactly the models the operator annotated. Every server consumer of the roster reads the same merged roster (curated, then discovered, then operator): the MCP `annotatedModels`, `emit_tickets` / `update_ticket` model validation (`services/tickets.ts`), `resolveModelEntry`'s runtime lookup at launch, and the web's settings view. The web gets the discovered layer from the server rather than computing a roster from `CURATED_MODELS` on its own.
**Why:** The past `annotatedModels: []` bug came from two surfaces disagreeing about the roster. One merged roster, served from one place, keeps the UI, the MCP and the launcher in agreement. Annotation remains the operator's explicit opt-in for per-ticket assignment.

## 6. Burns in parallel with sandbox-agent-clis-track-the-host-version; no CLI-version guard here
**Decision:** This feature does not wait on `sandbox-agent-clis-track-the-host-version`, and the two burn in parallel. Their files are disjoint: that feature owns the Dockerfiles, `sandbox-image.ts`, the doctor, `planImageBuild`, the burn preflight and the error classifier, and this one owns the roster, discovery, MCP/tickets roster plumbing and Settings → Models. The only shared piece is `resolveBinary`, which this feature calls read-only. This feature adds no CLI-version display or guard of its own.
**Why:** That feature's burn preflight (strict comparison of the image CLI with the host CLI) and its run-fatal "CLI too old for this model" classification already cover what happens when a discovered model is burned on an older sandbox CLI. Duplicating that here would create a coupling for no gain.

## 7. Discovery never changes the default or per-step models
**Decision:** Discovery only adds rows to the roster. It never writes `model`, `stepModels`, or `RUNTIME_DEFAULT_MODELS`. A new model reaches use only when the operator picks it. The onboarding seeds stay hard-coded as a first-run starting point.
**Why:** Automatically switching the default (for example to the Codex cache's priority-1 model) would silently change the cost and behaviour of every burn. The "new" badge is the notification, and promoting a model is the operator's call.

## 8. One lap, whole scope, no map
**Decision:** The full scope in decisions 1–7 is specced as a single lap. Two technical unknowns are left to the implementing ticket to verify, not held for a later lap: (a) opening an Agent SDK query and reading `initializationResult()` without sending a prompt bills nothing, and (b) whether the SDK's model list includes `[1m]` variants as separate entries, and what `resolvedModel` looks like for them.
**Why:** The operator is sure of the shape, and every piece hangs off one mechanism (two sources → one merged roster → Models page). If a surprise comes up, it adjusts a ticket rather than the design.
