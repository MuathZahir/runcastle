# Plan preview — decisions

## 1. Thin lap 1: the session writes the preview, the page shows it
**Decision:** Lap 1 is two things only: skill text that makes the planning session write the preview, and the feature page showing it at planning in a sandboxed frame that refreshes when the file changes. A staleness warning, handing the preview to burn agents, and showing the preview after planning are deferred to later laps unless a later decision here pulls one in. Marking which decisions the agent made on the human's behalf belongs to "Features plan themselves".
**Why:** The plumbing is certain. Whether a session-made preview explains a feature better than the grill did is the one real unknown, and it can only be judged by looking at real previews, so the first lap gets one in front of the human as cheaply as possible.

## 2. The preview is made at the end of the grill, before the spec
**Decision:** Once the decisions are locked, the planning session writes the preview, tells the human to look, and waits. The human confirms or says what is wrong; a correction is a decision edit and a redraw. Spec and tickets are written only after the human confirms. The preview is what the human confirms shared understanding on, replacing the chat-only confirmation the ideate skill asks for today. This feature's own session follows the same rule and writes its own preview before its spec.
**Why:** A reaction is cheapest to act on before the spec and tickets exist, and it is the order that worked by hand in `flow-redesign-settings` (decisions 4 and 14). Tickets slice the work without changing what the feature is, so a preview made first is still accurate beside Burn.

## 3. One file, `preview.html`, fully inline
**Decision:** The preview is exactly one file, `preview.html`, at the root of the feature's docs dir. Styles, scripts and images are inline and it makes no network requests. Several screens or flows are sections inside the one page. Existing `prototype.html` and `prototypes/*.html` files are left alone, and a session may still make throwaway explorations under `prototypes/`; the page shows only `preview.html`.
**Why:** A fixed name is the whole lookup, with no listing change, stored field or rule for choosing among files. A self-contained file renders from the existing doc read with no new serving route. "Preview" fits features with no screen, which "prototype" does not.

## 4. A visual page: a free show inside a light fixed spine
**Decision:** Every preview has five parts in this order. (1) What this is: one or two sentences. (2) The show: whatever explains how the feature will work, chosen freely by the session with no template: screens, clickable prototypes, skeletons, flows, before/after, scenarios. (3) What was decided: every decision in `decisions.md` by its number and title, each as a short visible consequence, with the reason available on demand; where a decision is visible in the show, that spot carries its number. (4) What is left out: out of scope and anything deferred. (5) Under the hood: the technical shape for a reader who wants it, collapsed by default and drawn where it can be. The whole page is visual first: a short sentence beside a picture, never paragraphs, with detail behind a click.
**Why:** The human asked for a page people want to look at, a show the agent is free to shape, and an implementation section for those who want it. The fixed parts around the show exist so a tired reader always finds the decisions in the same place and the session can check its own preview against `decisions.md`.

## 5. Runcastle theme for the page, the project's own styling for mocked screens
**Decision:** The preview page itself is always runcastle-themed: background, headings, the fixed parts, and every diagram and flow, in light or dark to match the app. A mocked screen inside the show uses the styling of the project it belongs to and sits in a framed panel. The skill pack ships a starter file carrying runcastle's tokens and the styles for the fixed parts; the session copies it and fills in the show.
**Why:** The preview should read as part of the feature page, and a prototype of another product's UI can only be judged in that product's look. A session working in another repo cannot see runcastle's theme, so the pack has to carry it; the starter keeps previews consistent without templating the show.

## 6. The preview leads the Overview body at planning
**Decision:** At planning, the preview is the first thing in the Overview body, directly under the next-step row that holds Burn and above the grill summary or ticket ledger. It appears as soon as `preview.html` exists, including before any tickets do. The inline frame scrolls itself, and one control opens the preview full-window. A feature with no preview looks exactly as it does today: no empty panel, no placeholder. There is no Preview tab and the preview is not hidden behind a button.
**Why:** The human reads down the page they land on: title, next step, preview, tickets. A tab would put the preview on a view without Burn, and a button puts it behind the click a tired reader skips. The cost is that a human in the Chat view switches to Overview to look; the session's message says so.

## 7. The frame runs scripts and allows nothing else
**Decision:** The preview renders in a sandboxed frame as a separate origin. Scripts run. The frame cannot read the app's page or storage, cannot open popups, post forms or navigate the app, and cannot make any network request: the app adds a content policy when it loads the file, so requests to any address, runcastle's own server included, are refused. A preview that links something hosted elsewhere does not get it.
**Why:** The preview is agent-written script shown inside an app whose local server has no login and can start burns and merges. The realistic risk is injected instructions reaching the preview's script through something the planning session read. The lockdown costs attributes and one added line, and it makes "fully inline" enforced, not promised.
**Known limit (found while writing the spec):** the content policy stops fetches, images, fonts and form posts, but nothing available stops a script from navigating its own frame, which is one GET. The frame still cannot read the app or any response, and the panel restores the preview when the frame loads anything else. Closing the gap fully is an open question in the spec.

## 8. A screen-building ticket points at one named screen block, never the file
**Decision:** Each screen in the show is an addressable block: the session names it and wraps it in a start and an end marker. A ticket that builds a screen names that block as its visual reference, and the burn agent reads only the lines between the markers. The ticket says the block shows the approved look and behaviour and is not the implementation: the agent builds with the project's real components and never copies the mock's markup. Tickets with no screen do not mention the preview, and the preview stays out of the docs digest. This is skill text only, in lap 1; it narrows decision 1, which had deferred all hand-off to burn agents.
**Why:** The docs checkpoint already commits `preview.html` to the feature branch, so it is in every burn sandbox with no server change. The human pointed out that the rest of the preview repeats docs the agent already has, plus theme styles, so reading the whole file wastes tokens; only the screen is new to the builder. Without any reference, the screen the human approved reaches the builder only as spec prose and drift shows up at review.

## 9. Whoever changes a decision redraws the preview; the page shows when it was last written
**Decision:** While a feature is at planning, a session that edits `decisions.md` updates `preview.html` in the same move, before anything else. The rule is in the ideate skill and the revisit skill. The page shows when the preview was last written, beside the full-window control. There is no staleness warning in lap 1, and a lap planned from review does not redraw the preview; both wait for a later lap.
**Why:** The human changes the plan by talking in the feature chat after looking, so the session making the change is the one that can keep the preview true. Detecting staleness from file times gives false alarms (a typo fix in `decisions.md` would flag a correct preview), so it is built only if a test drive shows sessions forgetting the rule.

## 10. Always made, sized to the feature, skippable only by the human
**Decision:** Every planned feature gets a preview. There is no minimum size: for a small feature the show can be a single picture and the other parts a line each. The session never skips the preview on its own judgement; the human can skip it by saying so in the chat, and then the session goes straight to the spec and the page looks as it does today. The skill text gives a reading target (about a minute for a small feature, a few minutes for a large one) as guidance, not an enforced limit. Quick changes have no planning session and get no preview. Codex sessions receive each skill's whole directory, so the starter file and skill text reach both runtimes.
**Why:** A session deciding a feature is too small to preview is making the call the human wanted to make by looking, and small features are where a wrong assumption is cheapest to catch.

## 11. The read-only Planning view shows the preview too
**Decision:** When the human steps back to a finished Planning step, the read-only view shows the preview in the same place and through the same frame as the live planning page. This narrows decision 1. Still deferred: the preview on the live Building, Review and Shipped pages, and redrawing it during a lap planned from review.
**Why:** The read-only Planning view is the record of what was planned, and the preview is part of that record. It also makes lap 1 test-drivable on this feature itself: its own preview is on the branch, so at review the human clicks the Planning step and sees it rendered by the code the burn just built. Skill changes on the branch do not reach live planning sessions until runcastle is published and reinstalled, so the skill half is judged on the next feature planned after that.

## 12. A "Preview ready" notice in the Chat view
**Decision:** While the Chat view is in front, a write to `preview.html` raises a chat notice: "Preview ready", with a "View preview" button that switches to the Overview. It wears the planning hue and is its own kind in the notice deck, so a redraw counts up on the one card instead of stacking. The human confirmed the plan and the form of the preview on 2026-10-10 and added this.
**Why:** The session asks the human to look while they are in the Chat view, where the preview is not visible; decision 6 named that as its cost. The chat notices already do this for the spec ("Spec written · View spec") off the same docs event, so the preview joins an existing mechanism.
