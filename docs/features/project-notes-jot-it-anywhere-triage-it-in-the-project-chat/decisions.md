# Decisions — Project notes: jot it anywhere, triage it in the project chat

## 1. One lap, spec whole
**Decision:** Spec the entire feature as a single lap — store, capture affordance, inbox + badge, and project-session intake together.
**Why:** The design tree is narrow: the store lifts an already-proven design from `test-drive-improvements`, the capture guardrails are settled prior art, and each surface is thin. No uncertain core justifies a walking-skeleton lap; session triage behavior is briefing/prompt content, cheap to adjust in a revisit.

## 2. Capture lives on every in-project screen; the project is implicit
**Decision:** The capture affordance is present on every screen inside a project (project home, feature workspace, project chat, preparation) and attributes the note to that project — there is no project picker. The portfolio home has no capture.
**Why:** A picker breaks the under-ten-seconds contract. On the portfolio home there is no current project to attach to, and one click into the project costs less than a dropdown on every capture.

## 3. Three doors, one popover
**Decision:** Capture opens from (a) a titlebar "Note" button beside the ⌘K pill, (b) the ⌘/Ctrl+J hotkey, and (c) a "New note" entry in the ⌘K palette. All three open the same small floating popover over the current screen: one focused text line plus screenshot paste; Enter saves and closes, Escape discards. The hotkey must fire even when focus is inside an embedded terminal.
**Why:** The button makes it discoverable without memorising anything; the hotkey is the ten-second path; the palette entry is near-free. Ctrl+J can be taken over by a page (Ctrl+N / Ctrl+Shift+N cannot), and "J for jot" is memorable. Most time is spent with focus in a terminal, so a hotkey the terminal swallows would fail exactly where it matters.

## 4. A separate `project_notes` store; screenshots as files
**Decision:** Project notes get their own table (`project_notes`: id, projectId, text, status, timestamps, plus the triage link decided later) rather than widening `test_notes`. A note's screenshot is one PNG on disk under the data dir (`~/.runcastle/project-notes/<noteId>.png`); the file's presence is the record, as with test-note annotations. One image per note. Every writer — the capture popover now, `project-level-test-drive` later — goes through the same service function.
**Why:** Test notes and project notes share a shape but not a lifecycle: a test note belongs to a feature's lap and can be carried between laps; a project note has no lap and outlives every feature. Making `featureId` optional would push "which kind is this?" into every existing test-note query and lap rule. The on-disk screenshot convention is already proven and needs no schema.

## 5. Lifecycle: open → triaged (with outcome), reopenable
**Decision:** Two states. **open** — captured, not yet dealt with; counts toward the badge; editable and deletable. **triaged** — dealt with; carries a required one-line **outcome** (e.g. "→ new feature *Overflowing crumbs*", "dropped: works as intended") and an optional **featureId** link when the destination is a feature; frozen (no edit, no delete). The project session sets triaged via its tool; the human can also **Dismiss** from the inbox (outcome "dismissed") and can **reopen** a triaged note, which clears outcome and link. There is no `promoted` state.
**Why:** Nothing clicks "→ ticket" on a project note — the session routes it among five destinations — so test notes' `promoted` (= became a ticket) does not fit. A required outcome line makes the inbox an honest record of where each note went; freezing keeps that record true. Reopen is the escape hatch for a mis-route; human dismiss avoids opening a chat just to drop a note.

## 6. Notes reach the session by pointer, read live through a tool
**Decision:** The Notes card carries a **"Triage N notes"** button that starts a *fresh* project chat whose launch briefing says to triage the open project notes (if a chat is already live, the same open / replace choice New chat offers applies). A plain New chat still opens by asking, but its system prompt carries one line: "This project has N open notes." The session reads the notes through a new project-session-only MCP tool, **`list_project_notes`** (id, text, created-at, absolute screenshot path the agent can `Read`), and marks them with **`triage_project_note({ noteIds, outcome, featureId? })`**, which takes several ids so a group closes in one call. There is no up-front selection: the session works the whole open list, and a skipped note simply stays open. The inbox and badge update live from the events these tools emit.
**Why:** ADR-0009 fixes the briefing at launch and has an explicit briefing force a fresh conversation — so the button is a launch door, not something typed into a running terminal. Inlining note texts into the argv would go stale the moment a note is jotted mid-chat and presses on the argv size cap; a live tool read never goes stale. Picking notes before the chat would be a decision made without the portfolio — the Quick form's mistake.

## 7. Triage grills before it routes
**Decision:** Triage is not sorting. Before routing, the session grills the human about the ideas behind the notes, ideation-style — one question at a time, always with a recommended answer — until the intent behind each note (or group of notes) is actually understood. Grilling may change the notes: some get dropped, some merged, some turn out to mean something different from what they said. Only then does each one route to one of the five destinations.
**Why:** A note jotted in ten seconds records a symptom, not an intent. Routing it cold produces briefs and quick-change tickets that restate the one-liner; grilling first gives the project session the context to route correctly and to write briefs that carry real reasoning — which is what the project skill already demands of a feature born there.

## 8. Triage shape: cluster → grill per theme → route with the reasoning carried
**Decision:** A triage session runs in three movements. (1) **Read and cluster** — the agent reads every open note and its screenshot, plays back the themes it sees, and the human corrects the grouping before any grilling. (2) **Grill theme by theme** — one question at a time with a recommendation, consulting the portfolio as intake does; a theme is done when its intent is clear enough to route. During grilling a note may be dropped (triaged, outcome "dropped: <why>"), merged into its theme, or reframed. (3) **Route and carry** — each theme goes to one of the five destinations, and the grilled reasoning lands in what that destination carries: a new feature's brief, a quick change's ticket strings, or, for revisit / another lap (which have no tool), a handoff line the human can paste into that feature's session. A theme the human wants to leave for later is rewritten, with their OK, through **`update_project_note({ noteId, text })`**, so the next triage starts from the sharpened version.
**Why:** The main idea usually lives in the theme, not in any single note, so clustering comes before grilling. Grilling that is not written into the destination is lost the moment the chat ends. The rewrite tool gives the agent only a power the human already has in the inbox, and keeps grilled understanding from evaporating when a theme is deferred.

## 9. Screenshots travel with the note, on the existing convention
**Decision:** For a quick change, `list_project_notes` returns, per note with an image, the ready-made `.runcastle-attachments/<noteId>.png` attachment sentence; the agent puts it in the ticket string it passes to `create_feature({ tickets })`, and the burner's attachment lookup is extended to resolve project-note ids (their own id prefix, so no collision with test-note ids) from the project-notes directory. For a new feature, the brief names the screenshot by its absolute path, which the host-side ideation session can `Read`. A triaged note keeps its PNG (it is the frozen record and a ticket may point at it); deleting an open note deletes its PNG. No cleanup of triaged notes in this lap.
**Why:** The attachment sentence is already the whole contract between promotion and the burner — reusing it costs one lookup change and no new ticket field. Ideation runs on the host, so a path is enough there. Frozen notes are the audit trail of what work was built from; pruning them is a later concern if the store ever grows.

## 10. Badge on the project row; the inbox is a card on the project workspace
**Decision:** The open-note count is a badge on the rail's pinned project row, hidden at zero. The inbox is a **Notes** card on the project workspace's resting page, between the New chat card and the conversation list: the "Triage N notes" button; open notes newest first (text, thumbnail that enlarges on click, inline edit, delete, Dismiss); a collapsed "Triaged (N)" section (outcome line, feature link, Reopen). The card is hidden when the project has never had a note. No separate route. After a save, the capture popover confirms "Saved · N open", the count linking to the inbox.
**Why:** The project row is the chat door and is on every in-project screen, so the pile stays visible without titlebar clutter. The inbox is read right before triaging, and the project workspace is where triage starts — a separate page would split one job across two places. The saved-count line shows the pile growing without adding a step to capture.

## 11. The project skill learns triage the way it learned sweeps
**Decision:** The full triage procedure (decision 8's three movements, drop / merge / reframe rules, the outcome-line format, the attachment sentence, handoff lines for revisit / another lap) lives in a new on-demand reference, `packages/skills/.../project/references/triage.md`. SKILL.md gains a short "Notes triage" section pointing at it, §0 is amended so a triage briefing — or the human accepting the open-notes offer — loads the reference instead of asking the default opening question, and "Your tools" lists the three new tools. `list_project_notes`, `triage_project_note` and `update_project_note` are registered for project sessions only.
**Why:** Sweeps already set the pattern for intake whose raw material is not the human's opening line; an on-demand reference keeps non-triage chats paying nothing for it. Restricting the tools to the project kind keeps the rule from the brief: the project session is the only surface that marks notes.

## 12. Out of scope for this lap
**Decision:** No one-click "note → quick change" promote from the inbox (it edits, deletes, dismisses, reopens — nothing that creates work). No rendered `notes.md` — the only reader is the project session, which reads rows. No agent at capture time, no OS-global capture, no drive machinery, no cleanup of triaged notes. `project-level-test-drive`'s brief is amended in its own revisit to write through this store's service function; this feature does not touch it.
**Why:** Work creation stays in the project chat (the Quick form's lesson). Test notes need a file because the revisit skill reads one off disk; project notes belong to no branch, so a file would be a drifting second copy with nowhere to live. The rest are the brief's fences.

## 13. One batched quick change per triage session
**Decision:** Triage routes every quick-change-sized theme from one session into **one** quick-change feature carrying all their tickets — one rail row, one Burn, one Merge per triage pass. The batch's own review is an ordinary feature test drive of its branch: problems with the batch are test notes (fixed by Iterate); unrelated observations are project notes.
**Why:** A quick change's cost is ceremony (row, Burn, Merge), not the feature itself — the feature is what gives an unattended burn its branch, review, reject unit and record. Batching removes most of the ceremony with no new machinery and closes the loop: drive main → notes → triage → one batch → Burn → drive the batch → Merge → drive main.

## 14. No featureless project burn; the "project fix lane" is parked
**Decision:** Quick changes stay feature-shaped. A project-level burn of tickets with no feature behind them is rejected. If batches later prove heavy, the direction is a **project fix lane** — one standing feature-shaped container per project whose laps are fed by triage and reviewed by the project-level drive of its branch, and the natural home for the charter's anticipated full-auto (no Burn click) toggle. It is parked as a draft feature.
**Why:** Featureless tickets lose the branch, review, reject unit and work record that make an unattended burn safe. A lane saves only one row per triage over batching, so it should be built on evidence from using batches. Everything in this feature (store, inbox, tools, screenshot handling, feature link) works unchanged under both, since both are feature-shaped; only the routing text in `references/triage.md` would change.
