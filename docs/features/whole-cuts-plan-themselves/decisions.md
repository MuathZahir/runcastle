# Whole cuts plan themselves — decisions

## 1. The self-made plans held up, so this goes further than a cut that plans itself
**Decision:** The human read the self-made plans and judged them good. That was the test lap 1 of "Features plan themselves" existed for, so this feature builds on it rather than spending a lap on planner quality.
**Why:** The human's verdict after looking at real plans. The brief made the next step depend on it.

## 2. The project session becomes the orchestrator of a cut
**Decision:** The project session takes the human's place between the two ends of a cut. It grills the human about what they want, as it does today, and creates the features. The features plan themselves. The project session waits on them and is told when each one finishes or fails. It reviews each plan (or has a subagent review it when the plan is too much for its own context), then either burns the tickets or sends the feature back to its own planning conversation with the changes it wants. When a burn finishes, it reads the results: the final docs and the review.
**Why:** The human asked for it. A cut that plans itself still leaves the human to open every feature, judge every plan and click every Burn; the experience they want is to talk once and come back to work in progress.
**Supersedes:** two lines of this feature's brief under "What this must NOT swallow": burning without the human, and the project session answering design questions. Both were written before the human decided this.

## 3. Orchestration is an opt-in mode, off by default
**Decision:** The orchestrating project session is behind a setting. With it off, the project session, Start and Plan it yourself behave exactly as they do today.
**Why:** The human asked for it. Runcastle is published, other people use the project session as a shape griller, and a session that starts spending tokens on burns by itself would surprise them.

## 4. The orchestrator holds every click, merge included, and the mode says it is experimental
**Decision:** In the mode, the orchestrator can do everything the human can do with a feature: create it, have it plan itself, send its plan back, burn, start a test drive, start the next lap, and merge. The setting names the mode experimental.
**Why:** The human asked for it: the point is to see how far an agent gets with the whole project. A merge can be reverted, and the mode is opt-in, so the experiment only costs the people who turn it on.
**Supersedes:** the brief's "merging … without the human" line, and decision 2's stopping point at reading the results.

## 5. The orchestrator works by judgement, not by a procedure
**Decision:** Runcastle does not script the orchestrator's moves. It gives the project session the tools to do every step and tells it when something it started finishes or fails; the skill describes how a senior engineer running a team of agents would judge each moment, not a sequence to follow. Whether a plan needs a subagent's review, whether merged siblings need an integration check, when a lap is worth a test drive, whether the human needs to see it now or after the next lap, how many features run at once: all of it is the orchestrator's call, made per feature and per moment. Calling the human in to test is one of those calls, not a fixed checkpoint after every lap. Planning a lap from a review and the human's notes, parked as item 5 in the brief, is part of this: the orchestrator decides when a feature needs another lap and has it planned.
**Why:** The human asked for it: the orchestrator should act like a professional software engineer orchestrating agents as well as possible. A fixed loop (plan, review, burn, drive, ask) spends the same effort on a one-line feature as on a risky one, and calls the human for checks that an agent could make.
**Supersedes:** the fixed "drive, wait for the human, file notes, next lap" loop proposed in the grill; the human's test drive is kept as something the orchestrator asks for when it judges the human's eyes are needed.

## 6. No hard limits beyond the human's own buttons; one move stops it
**Decision:** The orchestrator's tools refuse what the human's buttons refuse and nothing more. Merging red, leaving review findings open, how many runs go at once and how many laps a feature gets are its judgement, guided by the skill text (a professional does not merge red without saying why). The human can stop it with one move: turning the mode off, or telling it to stop in its terminal, means it starts nothing new. Runs already in flight finish, or are stopped as they are today.
**Why:** It is an experiment in the orchestrator's judgement, and hard rules would hide the judgement the human wants to watch. The stop is what makes having no rules safe to try.
**Alternative considered:** never merging with a red gate, capping concurrent runs at the project's burn concurrency, and refusing after a set number of laps on one feature.

## 7. The whole loop is one lap
**Decision:** This feature is built in one lap, through to merge: the mode, the notifications, a tool for every click and every read, and the orchestrator's skill text. Test drives, laps the orchestrator plans, merging, and starting drafts that were waiting on a merged feature are all in it.
**Why:** The human judged it: the new pieces are tools over services that already exist and the prompts that use them, so there is no part uncertain enough to deserve a lap of its own.
**Alternative considered:** a thin lap 1 ending at burn and reading the review, with drives, laps and merge in a later lap.

## 8. The orchestrator resolves merge conflicts itself; runcastle adds no tool for it
**Decision:** When a merge conflicts, the orchestrator resolves it the way an engineer would: itself, or through a subagent, in the feature's worktree, then merges again. Handing it to the feature's own conflict-resolving session is also open to it. Runcastle adds only what merging needs to keep its record (the merge itself, so the outcome doc, the shipped state and the worktree clean-up still happen).
**Why:** The human's call: the agent can do it. The project session is already the one session kind the edit guard does not bind, so nothing stops it writing the resolution.

## 9. The orchestrator acts on the features it created, and on any the human hands it
**Decision:** The orchestrator's features are the ones it created while the mode was on, plus any feature the human hands it by name. Every other feature stays the human's: it sees them, as the project session sees the whole portfolio today, and may tell the human when one interacts with its work, but it does not act on them. When the human opens a session on one of its features, the orchestrator is told the feature is busy and waits for that session to end rather than competing for it.
**Why:** Turning the mode on must not put the human's half-finished, hand-run features in an agent's hands, and the experiment's results should be the orchestrator's own work, not mixed with the human's.
**Alternative considered:** every active feature and draft in the project becomes the orchestrator's the moment the mode is on.

## 10. In the mode, the project session runs without permission prompts
**Decision:** With the mode on, the project session launches with permission prompts off: Claude Code's `bypassPermissions`, and approvals `never` on Codex. Runcastle's install guard still applies. With the mode off it keeps today's `default` mode and asks. The setting says in plain words that the orchestrator edits the repo and runs commands without asking.
**Why:** The orchestrator works while the human is away. A prompt with nobody there stalls the whole cut while the terminal still looks alive, which is the failure the headless planning run was built to avoid. Subagents inherit the session's mode, so pushing work into them would only move the stall.
**Alternative considered:** keep the prompts, and the human answers them on return.

## 11. The orchestrator hears about its features in its terminal, and catches up when reopened
**Decision:** While the project session is live, each time something on one of its features ends (a planning or other headless run finished or stopped short, a burn done or failed, a review in, a merge conflicted), runcastle types a short message into its terminal naming the feature, what happened and what to read next. While it is not live, nothing new starts: work in flight finishes as it would anyway, and nothing relaunches the orchestrator. When the human next opens the project session with the mode on, its briefing opens with what happened on its features since it was last live, and it carries on from there.
**Why:** The server owns the terminal, so closing the browser does not stop the orchestrator; only ending it or a server restart does, and both are the human's doing. Relaunching it by itself would be a second way an agent starts spending tokens without anyone asking.
**Alternative considered:** runcastle relaunches the orchestrator headless whenever something finishes and it is not live.

## 12. The orchestrator judges plans against what the human told it, and asks only when a wrong guess would cost a lap
**Decision:** The orchestrator judges a self-made plan against what the human said in its grill, and sends back any decision that contradicts it. A decision the human never spoke to it settles by its own judgement and names in its report to the human. It asks the human only when the decision changes what the human gets (not how it is built) and a wrong guess would cost a lap. It then asks one question at a time in its terminal and keeps the rest of the cut moving while it waits: only that feature's send-back or burn waits for the answer.
**Why:** The orchestrator stands in for the human on design, which the brief had kept away from the project session (decision 2), so it needs a line for when to stop standing in. A sentence from the human is cheaper than a burn and a lap spent on the wrong guess, and anything below that line would put the human back in the middle of planning.
**Alternative considered:** it never asks mid-cut; the human corrects wrong guesses afterwards, through test drives and notes.

## 13. An orchestrated feature is marked, and the human's buttons stay live on it
**Decision:** A feature the orchestrator owns carries a small "Orchestrated" marker on its card and its page. Every button the human has stays usable on it. When the human acts on one of its features, the orchestrator gets the same terminal message it gets for its own work. A headless run the orchestrator starts on a feature (sending a plan back, planning a lap) shows as working with Stop, as a self-planning run does today. Handing the orchestrator a feature is a sentence in its terminal, not a button.
**Why:** The human can step in on one feature without turning the mode off, and the orchestrator is never surprised by a change it did not make.
**Alternative considered:** the human's buttons are locked on orchestrated features while the mode is on.

## 14. A per-project setting, read at launch, on both CLIs
**Decision:** The mode is a per-project setting, "Orchestrator (experimental)", off by default, beside the project's other settings. Turning it on takes effect the next time the project session opens, and the setting says so, because the session's permission mode and briefing are fixed at launch. Turning it off is the stop of decision 6: a live orchestrator is told in its terminal to start nothing new, and its next launch is an ordinary project session. Claude Code and Codex can both orchestrate, on whichever runtime the project session's model belongs to.
**Why:** An experiment is switched on one project at a time, not everywhere at once. Everything the mode adds is MCP tools, terminal messages and skill text, which both CLIs already take, and the last feature found real Codex-only breakage only by driving it.
**Alternative considered:** a global setting, or Claude Code only for now.

## 15. The brief's other items are absorbed or parked
**Decision:** The orchestrator absorbs, with nothing extra built for them: the cut that plans itself (brief item 1); dependents (item 2: when a feature merges, it starts the drafts that waited on it); a loop driver (item 3: a stopped-short run is a message, and it decides whether to send the run back to work); self-planned laps (item 5, decision 5); a time limit (item 7: it stops a run it judges has gone too long); and the abandoned grill's way into self-planning (it can have any started feature with nothing planned plan itself). Parked as the draft "Self-planning polish" (`self-planning-polish`), waiting on this feature: Plan it yourself as the default (item 4), "plan the rest yourself" mid-grill (item 6), check-first entries that omit why they are uncertain, the Chat tab during a run, thin Codex plans, the human's open ruling on Codex running unsandboxed on Windows for ordinary sessions, and the page's entry into self-planning for an abandoned grill.
**Why:** The parked items serve a human who plans features one at a time without the orchestrator; none of them changes what the orchestrator does, and each would widen a lap that is already the whole loop.
**Alternative considered:** folding the small observations into this lap's tickets.

## 16. The record says who decided: assumed until the human says it
**Decision:** A decision the human did not make stays marked `**Assumed.**`, whether the planner made it or the orchestrator changed it on a send-back; the mark means the human has not seen it. A decision the orchestrator changed also carries `**Changed by the orchestrator:** <why>`. The human's answer to one of the orchestrator's questions is relayed to the feature as the human's, and the feature's session removes the marks, as the revisit skill already does when the human confirms a decision. The human's intent for a feature lives in its brief: the project session already writes its grill's reasoning there, and in this mode the orchestrator also adds to the brief what the human tells it about that feature later, so its judgement survives a compaction or a relaunch.
**Why:** The record has to show who decided (decision 7 of "Features plan themselves"), and there are now three deciders. The orchestrator's terminal is not kept, so it cannot be the record of what it changed, and it is the record the human needs when a merged feature turns out wrong.
**Alternative considered:** no new marks; the orchestrator's terminal reports are the only record of what it changed.

## 17. The orchestrator guards its own context and works at the level of the whole project
**Decision:** The orchestrator is told to preserve its context. It sends the reading to subagents on a cheaper model (Sonnet on Claude Code, the equivalent smaller GPT model on Codex): gathering context, reading a feature's docs, plan and tickets, reading a review or an outcome. It keeps only what they conclude. Like a senior engineer leading a team, it does not go into the details of a feature unless something needs it. Its own attention goes to the project as a whole: no conflicts or contradictions between features, the features integrating well, the best tooling for the job, and nothing more complicated than it needs to be.
**Why:** The human asked for it. One window holds a whole project over many features and laps, so detail read in full would crowd out the cross-feature judgement only the orchestrator can make. Each feature's own sessions already go deep on that feature.

## 18. Each cut starts with a working agreement
**Decision:** Before it creates anything for a cut, the orchestrator asks the human how they want the work run, offering three shapes: autonomous (carry everything through to merged and come back at the end), checkpoints the human names (for example, play the core before the extras), or a check-in after each feature. "You decide" means autonomous. It writes the agreement into the brief of every feature in that cut, so it survives a compaction or a relaunch. Autonomous means it never stops for a test drive: it relies on the checks every burn already runs (each lap's batch closes with a review ticket the feature's own planning creates, which the orchestrator reads rather than creates) and on its own integration subagents, and it calls the human only for decision 12's questions.
**Why:** In the lap 1 drive the human left the orchestrator expecting a finished snake game with every requirement, and came back to the core and a request to test it. Under decision 5 calling the human in was the orchestrator's judgement; how much the human wants to be involved changes from cut to cut, so it is agreed at the start of each one rather than guessed.
**Alternative considered:** a per-project setting for the involvement level, beside the Orchestrator switch.
**Supersedes:** decision 5's "calling the human in to test is one of those calls", which now holds only within the agreed shape.

## 19. In the sidebar, an orchestrated feature is a second ring on its phase glyph
**Decision:** The sidebar drops the Orchestrated text tag. A feature the orchestrator owns shows a thin accent-coloured outer ring around its phase glyph, and hovering the glyph says "Orchestrated". The feature page's header keeps the text tag.
**Why:** In the lap 1 drive the tag took the row's width: the title shrank to "Snake …", and on a waiting draft the title vanished altogether and the tag itself clipped to "Orch" beside "Waits on …". A ring takes no width. The page header has room, and it is where someone learns what the ring means.
**Alternative considered:** a small icon after the title, which still costs width on every row.
**Supersedes:** decision 13's marker "on its card", for the sidebar only.

## 20. Notifications reach the orchestrator through each CLI's own channel, never typed into its terminal
**Decision:** The notifier stops typing into the orchestrator's terminal. It gathers the pending lines for each live orchestrator and hands them to a delivery chosen by runtime. On Claude Code, a background hook (`asyncRewake`) that runcastle registers long-polls the server, and when lines are pending it prints all of them and exits 2, which wakes Claude with them as one system reminder. A new waiter starts at each turn end, and the server keeps one per session. On Codex, runcastle runs `codex queue --thread <conversation id> --message <lines>` against the session's own Codex home. Codex's queue service delivers the message: it starts a turn when the thread is idle, or delivers it after the current turn when the thread is busy, in about 10 seconds either way. Events that arrive together go as one message on both runtimes. If either channel cannot be shown working in the interactive session runcastle spawns, that runtime falls back to typing into the terminal, with a queue so each message is typed and submitted whole, one message per batch.
**Why:** In the lap 1 drive two notifications that ended within 350 ms arrived as one joined line ("…list_tickets({ slug: "snake-core" }).[runcastle] snake-core burn finished…"): `writeToLiveTerminal` (`launcher.ts:500-508`) types a line at once and submits it 350 ms later, and the notifier (`orchestrator-notify.ts:234`) calls it once per event with no queue. Typing also collides with anything the human is typing in the same terminal (spec, open questions). Both CLIs now offer a way to put a message into a live session without touching its input: Claude Code's `asyncRewake` hook is the documented way for a background hook to wake Claude, and `codex queue` is Codex's command for queuing a message to an existing session. Neither CLI's docs say outright that this works for the interactive session runcastle spawns (Claude Code's docs do not say what an idle session does, and Codex's watcher is in its source rather than its docs), so each is proven before it replaces the typing. The human's question in the same note — whether this works when they are on another tab or project — is answered either way: the notifier listens to the server's event bus and delivers to a session the server owns, whatever the browser shows.
**Alternative considered:** keeping terminal typing for both runtimes, fixed with a per-terminal queue; and Claude Code's channels, which are built to push messages into a session but are a research preview, stdio only, and show a full-screen confirmation on every launch.
**Supersedes:** decision 11's "runcastle types a short message into its terminal".
