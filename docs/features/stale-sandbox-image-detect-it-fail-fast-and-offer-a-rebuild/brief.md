# Stale sandbox image: detect it, fail fast, and offer a rebuild

## Ticket 1

Burn error classification: a container burn whose agent CLI is missing from the image must fail fast, not retry. Context: config `sandbox: docker`, image `sandcastle:runcastle-demo` built 2026-07-23; the burner Dockerfile (`packages/server/src/assets/sandcastle/Dockerfile`) gained `npm install -g @openai/codex` in a69cf5a on 2026-08-18. A Codex burn then dies with `codex exited with code 127` (the container shell's 'command not found'), and `RETRYABLE_ERROR_PATTERNS` in `packages/server/src/workflows/ticket-burner.ts` (`/exited with code \d+/`) classifies that as retryable, so every retry attempt is spent on a deterministic failure. Fix: in `classifyBurnError` (or wherever the pattern tables are consulted), treat exit code 127 and the wordings `command not found` / `not found` after an agent binary name as FATAL, checked before the retryable table. The surfaced message must name the runtime binary, the image tag, and the fix: e.g. `codex is not installed in image sandcastle:runcastle-demo — the image predates the burner Dockerfile. Rebuild it from Settings → AFK burns (Rebuild image).` Add unit tests for both runtimes and for the existing `exited with code 1` case staying retryable.

## Ticket 2

Container burn precheck: verify the image can run the burn's runtime before spending a sandbox. In `packages/server/src/workflows/ticket-burner.ts`, the run-level auth precheck (around `burnAuthReady` / the AUTH_MISSING_EVENT emit) already checks the host's Codex login but never that the image contains the CLI. For docker/podman sandboxes, before creating any container, run `<runtime> run --rm --entrypoint <bin> <image> --version` (bin = `codex` or `claude` per the resolved model's runtime) via the same exec/injection style the doctor uses so it is testable without docker. On a nonzero exit / 127, emit a run-level failure event with the same message as the fatal classifier ticket (binary, image tag, rebuild hint) and abort the run before any ticket burns. Keep the probe out of `noSandbox` runs, which use the host CLI. Cache the result per (image, runtime) for the life of the run so multi-ticket runs probe once. Tests cover: probe ok → run proceeds; probe 127 → aborts with message and zero sandboxes created; noSandbox → probe never invoked.

## Ticket 3

Doctor: report the sandcastle image as STALE when it predates the bundled burner Dockerfile. `sandcastleImageProbe` in `packages/server/src/doctor/doctor.ts` only checks `image inspect` succeeds, so a tag built before the Dockerfile changed reports `ok` while burns fail. Extend the probe: read the image's `Created` timestamp (`<runtime> image inspect --format '{{.Created}}' <image>`) and compare it to the mtime of the bundled template Dockerfile (`sandcastleTemplateDir()` in `packages/server/src/services/setup.ts`, or the `.sandcastle/` context if one exists under `sandboxBuildDir()`). If the Dockerfile is newer, return a new status `stale` (severity `error` for a runtime some configured model resolves to, consistent with decision 6), detail like `sandcastle:runcastle-demo built 2026-07-23, burner Dockerfile changed 2026-08-18 — rebuild`, and fix text pointing at the Rebuild image button. Keep `ok`/`missing` behaviour unchanged. Wire `stale` through the `ProbeStatus` type and any switch that folds statuses into the overall report and the setup tRPC router so the web card can read it. Inject the file-mtime read like `fileExists` is today so tests need no filesystem; add tests for ok / stale / missing.

## Ticket 4

AFK burns card: always offer a Rebuild image button when the image is present. Today the `Enable AFK burns` card in `apps/web` (the Sandcastle container image row) shows the build affordance only when the doctor reports the image `missing`; once the tag exists the row is green and there is no way to rebuild from the app, so a stale image has no in-app fix (a run through the same `build-image` terminal kind in `packages/server/src/trpc/routers/setup.ts` is all that is needed — it already pins `--image-name` and rebuilds the tag). Change the row: when status is `stale`, show an amber indicator, the doctor's detail/fix text, and a primary `Rebuild image` button; when `ok`, keep the green indicator but show a secondary `Rebuild image` button (a fresh Dockerfile ships with each runcastle upgrade). Both reuse the existing build-image terminal flow and re-probe on completion exactly as the `missing` state's Build image button does. Ensure `prepareSandboxBuildContext()` rebuilds from the CURRENT template: `scaffoldSandcastleConfig` is create-only, so if `~/.runcastle/sandbox-build/.sandcastle/` already exists it must be refreshed from the bundled template before a rebuild (overwrite the runcastle-owned scaffold files; this dir is runcastle-owned, not the user's). Add a component test for the three states and a unit test for the refresh.
