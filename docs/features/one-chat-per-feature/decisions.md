# Decisions — one-chat-per-feature

## 1. One session, thin-ish lap 1
**Decision:** Ideation stays in this single session (no map). Lap 1 lands the core: the kind collapse (ideation/revisit/qa → one chat kind), one transcript resumed by every door in all four states, the docs-only worktree that coexists with a burn, and the MCP audience table per state. Deferred to `## Later laps`: UI-placement polish beyond a minimal well-placed door, and any resume-cap story fancier than the simple one chosen here.
**Why:** The brief already enumerates the design branches; none needs research or a prototype, so no map. Placement is the part most likely to need a test-drive to judge (the operator explicitly flagged it), so lap 1 stays testable end-to-end without betting on getting placement right blind.

## 2. Chat worktree during a burn: temp branch, prompt landing via a per-feature queue
**Decision:** Outside a burn the chat lives in today's talk worktree checked out to `feature/<slug>`, committing docs directly — unchanged. During a branch-claiming run the chat runs in the same talk worktree but on a temp branch forked from the feature tip (`runcastle/chat/<slug>/<unique>`) instead of detached HEAD; each docs commit is landed promptly through the landing queue, which is promoted from per-run to per-feature so chat landings serialize with ticket landings. Not defer-until-run-end. The one-terminal guard splits: "one live HITL session per feature" stays; the "refuse terminals while a run claims the branch" clause (`launcher.ts:227-232`) is deleted.
**Why:** Docs commits touch only `docs/features/<slug>/`, which burners essentially never write, so landing conflicts are near-zero. Prompt landing makes a note or ticket edit durable on the feature branch even if the run crashes, and avoids "flush at run end" bookkeeping racing run finalization. The per-feature queue is the honest fix regardless — it guards a per-feature resource (the branch ref). The deleted refusal clause is the exact post-mortem pain this feature exists to remove.

## 3. The collapsed kind is `chat`; one toolset, per-state rules at call time
**Decision:** The collapsed kind is named `chat`; `ideation`, `revisit`, and `qa` leave the kind enum. `chat` gets one MCP toolset regardless of state — the union of today's ideation/revisit registration (feature reads, ticket writes, `complete_phase`, `resolve_finding`, map tools, `create_feature` draft parking, `record_event`). The qa read-only contract (`refuseIfReadOnly`) is deleted with the kind. Per-state policy lives at call time, not registration: (a) `update_ticket`/`cancel_ticket` refuse a ticket claimed by an active run — the chat edits the next burn's work, never the live one's; (b) `complete_phase` stays gated by the gates themselves. Everything else works in all four states; on Shipped, a ticket write is drafting the next lap.
**Why:** Registration is built at session spawn and the state can change under a live chat (a burn starts or finishes), so a per-state audience matrix fights the spawn-time model and buys nothing the call-time guards don't already give — matching the audience table's own doctrine that it only decides what a session is told about.

## 4. No resume caps for `chat` — resume is unconditional
**Decision:** The `chat` kind skips the `resumeCapExceeded` check entirely: no byte cap, no re-entry cap, resume always targets the one transcript. Claude Code's own auto-compact manages the context window. The cap machinery stays untouched for the kinds that keep it (waypoint, converge, prepare). Nothing new is built.
**Why:** The caps existed to dodge auto-compact silently dropping decision prose mid-conversation. This feature dissolves that justification: the kickoff re-injects the full current state on every resume, and decisions/spec/notes live on disk — compaction can only eat chatter, not the record. The operator's stance: users know how agents work; don't babysit them with forced fresh starts.

## 5. Migration: rewrite old session rows to `chat`
**Decision:** A one-time DB migration rewrites existing session rows: `kind IN ('ideation','revisit','qa')` → `'chat'`. No legacy aliases anywhere. `shippedQaSessions` becomes a `kind === 'chat'` filter with the same "only when worth a panel" guard (its final shape belongs to the placement work). Which door a historical row was opened from is not preserved on the row; the timeline events keep the story.
**Why:** With the three kinds gone from the enum, unmigrated rows would fail zod parsing on read, and aliasing would keep dead kinds in the schema forever. The migration makes resume work for free — the newest migrated row's `ccSessionId` becomes the seed of the feature's one chat, which is exactly the intended semantics.

## 6. Burn agents get no channel to the chat
**Decision:** Burn agents stay headless. The run's events and ticket updates are their only voice; the chat reads those. No talk channel in either direction.
**Why:** A talk channel would add a second, unrecorded path for a burner to influence the feature, undermining "the docs and events are the artifact." The post-mortem pain was the human having nobody to talk to, not the burners. A burner needing a human decision fails its ticket with a legible error — that mechanism exists.

## 7. State knowledge: short kickoff header + a fattened `get_feature_context`
**Decision:** The chat's kickoff is a short header — current state, lap, ticket counts by status, latest run status, and in Review the drive outcome named explicitly with a pointer to the evidence — ending with "call `get_feature_context` for the full picture." `get_feature_context` grows the missing state: a `latestRun` summary (status, tickets landed/failed, error headlines), the review outcome and findings, and test notes. No per-state kickoff variants beyond the header's wording, and no "changed since last wake" delta digest.
**Why:** Extends `review-arrival-is-legible` decision 7's precedent: name the carried work, point rather than dump. The kickoff rides the CLI's argv (prerequisite feature), so short is the robust choice. One tool returning the whole current state in every state beats new tools or state variants; the resumed transcript plus fresh header covers re-orientation.

## 8. Lap-1 door: one `chat` action, a constant secondary named "Chat" in all four states
**Decision:** One action kind `chat` replaces `startGrill`, `askQuestions`, and `revisit`; it always resumes the one transcript (first open starts it). `resolveConflict` and `stopDriveAndIterate` survive as roads launching the same `chat` kind with their kickoff overrides. Placement: a constant secondary action on the next-step bar in all four states, same position, one-word label "Chat", never reworded per state; promoted to primary only where talking is genuinely the next step (planning with nothing live). During a burn the bar keeps "Cancel run" primary and gains Chat as secondary. On Review, Chat sits beside the trail's actions without touching them. Richer placement (inline panel, body placement, shipped-body panel redesign) is `## Later laps`.
**Why:** A constant, predictably-placed one-word door is the "well placed, not cluttering" answer for lap 1, and it produces real test-drive evidence for the deferred placement design. Collapsing the destination while keeping the context-carrying doors preserves what those roads know.

## 9. Worktree handoff at burn boundaries
**Decision:** Burn clicked while the chat is live: the runner switches the talk worktree to a fresh `runcastle/chat/<slug>/<unique>` branch at the feature tip (`checkout -b`; working files unmoved, session unaffected) instead of detaching it. Run end (success, failure, or cancel): unlanded chat commits land through the queue as the run's last landing, then the talk worktree checks back out to `feature/<slug>` at the new tip. The chat session never restarts across the boundary — only its worktree's branch changes underneath it. An empty chat temp branch at run end is deleted; the boot sweep's existing merged/unmerged rule covers crashes.
**Why:** Keeps decision 2's model symmetric at both edges with no new concepts: the branch is released to the landing queue either way, and the chat merely keeps a named place to commit.
