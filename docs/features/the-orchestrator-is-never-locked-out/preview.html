The orchestrator is never locked out

A stale "session ended" signal can no longer stop an open chat from acting. A chat runcastle is running heals itself on its next turn or tool call.

The show

No screen changes. What changes is what the orchestrator chat can do after a restart or a stop.

Today

  1. Server restarts; the orchestrator wakes in a new process.
  2. An old leftover process is killed and sends "session ended".
  3. The record flips to ended. Its turns don't change it back.
  4. Every orchestrator tool refuses: "a new one must be opened to act". Autopilot stalls until the human types.

After

  1. Same restart, same leftover.
  2. Its "session ended" is only a timeline note 1.
  3. Even a record that says ended flips back to live on the chat's next turn or tool call, because runcastle runs that chat 2.
  4. The merge goes through. Leads and workers get the same rules 3.

Under the hood

The agent host (the server part that starts, watches and stops every chat's process) becomes the only owner of "ended" for Claude sessions, as it already is for Codex.

  • Session-end hook (Claude): writes a session.conversation_ended note with its reason; no longer marks the row ended. The lead's merge check still runs.
  • Host stop, stalled-turn kill and crash: mark ended only if no newer process for that session is running by then.
  • Turn check-in (prompt-submit and stop hooks) and the orchestrator tool check: an ended row whose session the host runs is marked live again, with a session.started event saying a turn revived it.
  • The refusal text changes; three tests pin it.
  • No schema change, no new env var.

Why it can still happen after the process-kill fix: the boot sweep of leftovers runs after chats are woken; a stop marks ended after slow awaits; /clear sends end and start as separate requests.
