The real design

Real sidebar components, waiting for your eye. It opens on the dev server in the design panel.

Sidebar with threads, and the header naming the thread

The sidebar pieces, the thread rows and lists, and the header are real components; features and threads are sample data. The open Orchestrator holds its chats inside its own accent card. Four samples: a feature with eight threads, a working feature inside the Working bay, a feature with only its main chat, and the Orchestrator with 80 chats. Click rows and threads to move around.

A Tweaks menu (bottom right) holds the looks left to you: thread rows as an icon column, divided by hairlines, or two lines; the open feature as one card or a tree line; and the "+" on hover or always on the open row. The plan builds icon column, one card and on hover unless you pick otherwise.

What was decided

Open one for the reason.

What is left out

Later

  • Archiving or hiding a thread, if dead threads crowd the lists
  • Threads in the command palette, for a closed sidebar

Not this feature

  • The rest of the chat header and the chat's look ("The chat looks the part")
  • The Orchestrator page's conversation list ("The Orchestrator's page")
  • Shared style and building blocks ("The whole app matches the sidebar")

Under the hood

The page publishes, the sidebar draws. Only the open page's threads ever show, and that page already holds them.

feature page chat column · Orchestrator page
  → shell-level channel { scope, threads, inFront, pick, newThread, actionsFor }
  → sidebar: open feature row / Orchestrator card → SidebarThreadList

  • No new queries: the sidebar draws the list the page already fetched.
  • thread.list rows gain createdAt; the web orders main first, then newest started. The server's order stays for the Orchestrator page.
  • Rename and Export move from the switcher to the thread row's menu, via the existing thread menu hook, for any thread. The scenario chat's close becomes a menu action.
  • ThreadSwitcher is deleted; the header gains the thread as a second breadcrumb.
  • Picking keeps the thread in the address (?thread=), so a reload lands on it.
  • Size: about a day's work in a handful of web files plus one field on the server, so the lead builds it in this chat. No tickets, no workers.
