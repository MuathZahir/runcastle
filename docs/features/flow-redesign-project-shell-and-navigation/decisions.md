# Decisions — flow redesign: project shell and navigation

## 1. Real URLs, as a projection of the existing state machine — no router library
**Decision:** The app gets real, history-backed URLs: `/` (portfolio home), `/p/<projectId>` (project, landing on its restored feature), `/p/<projectId>/f/<featureSlug>` (feature), `/p/<projectId>/chat` (project conversation), `/p/<projectId>/prepare` (preparation). `useProjectNav` + `useWorkspace` stay the owners of navigation state; a thin sync layer `pushState`s the path on every navigation action and, on `popstate` and initial load, parses the path and drives the same setters. Browser Back/Forward work. Transient overlays — the ⌘K palette, Settings, DocPeek, the Quick overlay, and the read-only phase pin — stay out of the URL and out of history. localStorage keeps one job: where a bare `/` launch lands (last project, last feature); a URL beats storage whenever both exist. No TanStack Router / React Router.
**Why:** Back currently exits the app to `about:blank` and nothing is linkable — history and addressability only come from the URL. But the navigation is already a clean, tested two-layer state machine whose body view derives from precedence-ordered *flags* (create > prepare > project > feature), not a route hierarchy; a router would invert ownership and force every reasoned rule (per-project preparation persistence, project-row-as-swap, unprepared-project takeover) to be re-expressed in a foreign idiom — rewrite risk with nothing a ~100-line sync layer does not also give. Overlays are excluded so Back never becomes "close the popup", a different and worse contract. One canonical location also removes the chat-vs-feature double-highlight (two independent booleans today).

## 2. One lap; cross-flow leaks deferred to their owning flows
**Decision:** Spec the whole chrome in one lap: routes (decision 1), titlebar, sidebar, ⌘K palette, inspector, status bar, update banner, the shell's `styles.css` migration, and the shell code-quality pass. Not mapped. Deferred out of this feature (to `## Later laps` / their owning flows): the merge-conflict duplicate explainer, next-step-bar wording ("Resume grill" etc.), and the map rail's "0 FRONTIER" stub — they live in other flows' bodies.
**Why:** Every branch is settled territory — no research or prototype gates any decision, so it is not map-sized; and the surfaces split into parallel per-surface tickets, so it is one burn. A half-migrated shell would leave `styles.css` in a worse mixed state than either end. The deferred items render inside phase bodies owned by flows 6/7; touching them here is the collision the one-flow-at-a-time plan exists to prevent.

## 3. Baseline is landed main; the New button and Settings are settled elsewhere
**Decision:** Spec and tickets treat current `main` — with `flow-redesign-project-chat-and-creation-doors` and `flow-redesign-settings` merged — as the baseline, not this worktree's fork point. The New-button behaviour is settled by chat-and-doors decision 12 (New with a live chat → inline notice on the New chat card with "Open it" / "End it and start new", wired through `ProjectShell`'s `newChatRequest` and `talk.replace`) and is out of scope here; the shell only keeps the door and its plumbing. Settings is a page-addressed dialog (`SettingsLocation`) — the shell's `openSettings(location?)` contract is kept, and any chrome that points at settings uses a location, not a bare open.
**Why:** Both flows shipped after this feature's branch was cut; the seams they left in shell files (`newChatRequest`, `SettingsLocation`, nullable `onSelect`) are contracts this redesign must preserve, and re-deciding the New behaviour here would collide with a landed decision.

## 4. Entering a project lands where the rail points
**Decision:** `/p/<id>` with no stored selection (and the fallback when a stored feature is gone) lands on the first row of the rail's triage order — top Needs-you, else top Agent-working, else top In-progress. If no feature is in those lanes (only shipped / drafts / archived), it lands on the project home with the two doors, not on a shipped feature's retrospective. A stored last-selected feature still wins; a URL naming a feature beats both.
**Why:** Today's landing is `list.data[0]` — newest-created, lane-blind — which auto-opened drafts and shipped features (findings F10.4; reproduced in the walk). The rail already answers "what should I look at": landing the workspace on the row the eye lands on makes the two agree, and auto-opening a retrospective was the confusing case the audit flagged.

## 5. Inspector: feature-only for real, explainer on demand, product-language activity
**Decision:** The Inspector stays a feature-scoped right rail. On non-feature views (project chat, prepare, create, empty) the grid drops the column entirely — no blank strip — and the titlebar toggle is hidden there. The standing "Gates are the human approval points…" sentence is deleted; it becomes on-demand help (ⓘ/tooltip on the "Current gate" caption), matching the settings flow's text policy. Activity rows never show an event slug as the summary — `activityLine` widens so every event reads as a sentence ("Feature created on branch feature/…"); the small humanized `type · time` line stays, dimmer; agent internals stay behind the expander.
**Why:** The walk found a dead ~300px column on chat/prepare (the code hides content, not the column), the explainer repeats on every feature forever (the human's screenshot), and rows like "feature.created (feature/kickoff-probe-throwaway)" still leak developer slugs into a human-facing feed (F10.5/F18 residue).

## 6. The gate override UI is removed; server escape hatch deferred
**Decision:** The gate card becomes read-only: gate name, requirement, ready/blocked line. The "Override with reason…" link, the reason form, and the "G1 was overridden — Undo" row are all deleted from the Inspector. The server procedures (`feature.overrideGate`, `feature.undoGateOverride`) are left untouched this flow; their removal is recorded as deferred cleanup for a later feature.
**Why:** The human has never used it — the card without the form is much quieter, and the override's three UI states (link, form, undo banner) were most of the gate card's bulk. The server half stays because a gate whose check wedges (e.g. converge dies with decisions.md missing) still needs an escape hatch reachable by an agent or a cleanup feature, and deleting pipeline machinery is beyond the chrome's frame.

## 7. One health indicator, two run counts — each labeled by scope
**Decision:** The status bar owns server health ("server ok/down" chip with the API origin in the tooltip), next to the distinct live/reconnecting stream dot. The titlebar's green health dot is deleted. Run counts shrink to two: the titlebar pill stays cross-project but says so in its text (e.g. "3 running elsewhere" when the runs are in other projects); the status bar's per-project "N runs" segment is deleted — the rail's "Agent working" lane already shows this project's running work by name.
**Why:** The walk found two health indicators driven by different queries (they can disagree) and four run numbers with three meanings and mismatched values (titlebar 5 / portfolio 2 / lane 4 / status bar 0). A count the lane already itemizes is noise; the one number that earns chrome is the work you cannot see from here.

## 8. Status bar: branch follows the view; everything else keeps its seat
**Decision:** The branch segment shows the selected feature's branch on feature views only; on chat, prepare, create and home it renders nothing (the chat strip already names `runcastle/project` and the landing branch). The sandbox chip, the driving segment with its stop button, the notify toggle, the live dot and server health all stay; the notify tooltip is reworded jargon-free in the copy pass.
**Why:** The walk caught the bar showing the previous feature's branch on non-feature views — a stale fact presented as current. The surviving segments each state something no other visible surface states.

## 9. Chrome copy: insider nouns as names, gate codes demoted, definitions in tooltips
**Decision:** Insider vocabulary may appear as established names (a button called Burn), but every chrome sentence must read without it ("Notify me when a burn finishes" → "Notify me when agents finish a run"). Gate codes demote to dim mono detail; the gate card leads with the plain name ("Spec written"). First-contact surfaces (Quick/New doors, prep row, drive segment) carry the definition as a tooltip sourced from `lib/vocabulary.ts`, so every surface says the same sentence.
**Why:** F16 — grill/burn/lap/G1 meet a newcomer at the moment of a click with no gloss anywhere; the settings and chat flows already locked the same help-on-demand text policy, and one shared vocabulary module keeps the sentences from drifting per surface.

## 10. Sidebar: roomier rows keeping the mini-map, wider and resizable rail
**Decision:** Rows keep the six-segment pipeline mini-map. Line 1: phase dot + title (up to two lines before truncating) + one status chip. Line 2: mini-map, plus ticket progress when it exists; the slug leaves the row (it lives in the URL and feature header) and the kebab gains "Copy link". Rows get taller with real breathing room on the foundation's 4px rhythm. The rail widens (default up from 252px, on the order of ~300px, tuned in the prototype) and becomes resizable: a drag handle on its edge, clamped to sensible min/max, width persisted globally in localStorage (like the inspector-collapsed flag — a screen preference, not a per-project fact). Lanes are unchanged: same triage order, Shipped capped at 5 with the expander, Archived behind the toggle. The head keeps FEATURES + Quick + New.
**Why:** The human wants the rail spacious above all; five "Flow redesign: …" rows are currently indistinguishable at 252px with one-line truncation. The mini-map stays at the human's call — it is glanceable pipeline state the dot alone does not give. Resizability is the honest fix for a density preference that varies by project name length; persisting globally matches how the other rail preferences already work.

## 11. Titlebar: a truthful three-level breadcrumb; wide search stays
**Decision:** The titlebar reads brand / project / current thing — the third level naming the selected feature (title), "Chat", or "Preparation", clicking up to the project home. All remaining controls stay: switcher, wide search field with the Ctrl+K chip, cross-project runs pill (decision 7 wording), Settings gear (opens at General via SettingsLocation), inspector toggle (hidden on non-feature views per decision 5). The health dot is gone (decision 7).
**Why:** With real URLs the breadcrumb becomes truthful and gives the chrome one place that states location — softening the slug's departure from rail rows — and the wide search field is the palette's discoverability, not decoration.

## 12. Palette: three labeled groups, all actions visible on empty query
**Decision:** The palette always shows three labeled groups — Features / Projects / Actions — with all five actions (Project chat, Preparation, Settings, All projects, Open a project…) listed on an empty query; typing narrows every group by its match terms as today. Feature rows keep the phase label and the violet "open" marker and adopt the rail's readable-title treatment. Keyboarding unchanged.
**Why:** Hiding Preparation and Settings until the right word is typed defeats the palette's discoverability role — the exact failure mode that made preparation unfindable before. Consistent group labels fix the walk's naming inconsistency.

## 13. Banner untouched-but-restyled, shared rhythm, prototype before spec
**Decision:** (1) The update banner keeps its behaviour (frame's first row, per-version dismissal) and is only restyled on the tokens during migration. (2) Every chrome surface adopts the flow-wide spacing rhythm already locked by the chat flow: 8px inside a control group, 16px between fields, 24px between sections, 32px header-to-body, on Tailwind's 4px scale. (3) An HTML prototype of the shell — titlebar breadcrumb, resizable rail with roomy rows, inspector, status bar, at the new widths and rhythm — is produced at `docs/features/flow-redesign-project-shell-and-navigation/prototype.html` and published as an artifact for the human to approve before spec.
**Why:** The banner's placement was fixed by findings F7 and needs no re-decision. One rhythm across flows keeps the app from accreting per-flow spacing dialects. The human judges a visual surface by looking; both prior flows locked their look via a prototype and this one is chrome — the most looked-at surface of all.

## 14. Prototype approved — the visual reference for spec and tickets
**Decision:** The HTML prototype (`docs/features/flow-redesign-project-shell-and-navigation/prototype.html`, published as an artifact) is approved as the shell's visual reference: 300px default resizable rail (240–420 clamp), roomier two-line rows with mini-map and no slug, three-level breadcrumb titlebar without the health dot, read-only gate card with the explainer behind ⓘ, view-dependent inspector column and status-bar branch, three-group palette with all actions visible.
**Why:** The human reviewed the interactive prototype and approved it without changes on 2026-09-03.
