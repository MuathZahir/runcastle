# Decisions — Tickets and review are tools, not phases

## 1. Specced and built whole
**Decision:** The whole feature is specced and built in one go, not sliced: Go removed, rounds started from the chat, review optional, status derived from what is happening, tickets shown in the panel.
**Why:** The human's intent is clear, and the parts depend on each other. Removing Go without deriving status would leave every feature stuck at "planning" while rounds run, so a thin first slice would leave the app half-broken in between.

## 2. The stored phase goes away
**Decision:** A feature no longer stores a lifecycle phase (planning → building → review → shipped). It is shipped or not; the existing status field already records shipped. Everything else is derived from facts when needed: a round running, the agent mid-turn, waiting on the human, ready declared. Every check that read the phase is rewritten to ask about the fact it actually cares about. This overturns the charter's phases decision (CONTEXT.md #7).
**Why:** A phase moved by actions would be a second version of the truth that drifts: "review" would keep meaning "the agent said ready once" after five more rounds. Deriving status also means features already past Go need no migration.

## 3. The human's approval lives in the prompt, not the server
**Decision:** The agent's instructions require the human's explicit approval in chat before it starts the first round, and before any round the agreed plan did not settle. The server enforces nothing about approval: no "approved" mark, no "a human has spoken" check on the round tool. Its existing refusals (a round already running, a drive in progress, after Stop until the human replies) stay. This replaces the charter's "two clicks" approval (CONTEXT.md #9) and its enforced gates (#8) for this step.
**Why:** The human judged the instruction enough. Server-side approval checks were weighed (refuse rounds until a human message has reached the feature; an approve tool) and rejected as machinery the human does not want.

## 4. The agent is always the lead, with one skill
**Decision:** There is no "before Go" and "after Go", and no moment the agent becomes the lead: every chat on a feature is the feature's lead from its first message, with one brief and one skill. That skill is written as judgement rather than steps: grill when the intent is unclear and record decisions; write the spec once the feature is concrete; write tickets when work is worth handing to workers, and do it directly when it isn't; show the preview and get the human's yes; run rounds; review when it's worth it; run the project's checks; tell the human what to test. The ideate, lead, spec, tickets and revisit skills fold into it, with their detail kept as reference files inside it, read when needed (writing tickets, running rounds, planning without a human, designing, the preview). An orchestrator relay, a merge conflict and a shipped feature's chat are just situations the same lead handles. The code-review skill stays separate: it belongs to the review agents a round runs, not to the feature's chat.
**Why:** The human does not want the agent to change role or for there to be separate skills. With no phase, nothing is left to choose between briefs on, and one text read on demand keeps the main guidance short enough to be followed.

## 5. The spec follows concreteness, not delegation
**Decision:** The spec is written when the feature is concrete, meaning what it does is settled, whether or not tickets and workers follow. It is not a step that exists only to feed tickets.
**Why:** The spec records what the feature is. A feature the agent builds itself needs that record as much as one handed to workers.

## 6. Review is optional; the agent tells the human in chat how the work was checked
**Decision:** Review is the agent's call. Quick changes no longer get a review ticket appended, the tickets skill no longer requires one per batch, and a batch without one no longer warns. The agent's instructions say it always runs the project's own checks (typecheck and tests) before declaring ready, and that its ready message in chat says what to test and how the work was checked, for example "typecheck and tests green; no review agent, since it's a one-file style change". `declare_ready` keeps only the drive's scenario, which the Test drive button starts; its `whatToTest` field and the "What to test" notice above the chat go, and the review trail's ready entry shows the scenario alone. The "nothing has reviewed the work since the last change" warning goes; the "last round had failures" warning stays.
**Why:** The chat is always on screen beside the panel, so a separate UI for what to test repeats what the agent says there. Once skipping review is legitimate, the old warning is noise.

## 7. Status is the sidebar's lanes, with "Needs you" rebuilt on facts
**Decision:** A feature's status is its sidebar lane: Needs you, Agent working, In progress, Backlog, Shipped. "Agent working" stays as it is (a round running, or the agent mid-turn). "Needs you" holds when the chat is waiting for the human's input, or the feature has a waiting reason: the agent asked (`wait_for_you`), the human pressed Stop, the provider halted, or the agent declared ready. Declaring ready sets the waiting reason ("ready to test"), so it clears like the others, on the human's next message or the next round. "Needs planning", "ready to Go" and "a ticket failed" are no longer reasons. The feature page's status line keeps its fact-based words ("Working · Round 2", "Waiting for you · <why>", "Ready for you · Test drive ▸ <scenario>", "Merged"); "Planning with you" becomes "Talking with you", for a feature with nothing running and nothing asked. The state line injected into the chat uses the same words instead of the phase.
**Why:** The lanes already come from facts except for "Needs you", which read the phase and ignored `wait_for_you`. A self-planned feature lands in Needs you because its agent asks for the yes and waits. Failures are the agent's to handle after the round wakes it, and it asks when it can't.

## 8. The panel holds Plan, Work, Review and Details
**Decision:** The panel's single phase-keyed "body" view, and the separate Preview view, are replaced by four fixed views, each offered once it has something to show: **Plan** (the plan preview, with the decisions and spec one click away inside it), **Work** (the feature's tickets, review tickets included, grouped by the round that ran them, with live status; a running ticket opens its live log, folding in today's Run view), **Review** (ready declarations, the review's findings and evidence, and what shipped once merged, folding in today's Outcome view) and **Details** (timeline, docs, sessions). **Design** and **Drive** appear only while the design server or a test drive runs. Every entry in the view picker shows its icon. The agent's `show_panel` tool opens any of these by name. `emit_tickets` itself switches the panel to Work, opening it if it is closed; that counts as the agent's own act, so runcastle still never opens the panel unprompted.
**Why:** The phase-keyed body hid tickets whenever the only ticket was a review ticket, which is what happened on the grain feature. The human found seven views confusing, so related views are folded together. Opening Work inside the tool makes the switch reliable.

## 9. The feature glyph shows ticket progress
**Decision:** The glyph beside a feature's title, in the page header and on sidebar rows, no longer shows the phase. Its pie is the share of the feature's tickets that landed (cancelled ones not counted); it is a dashed ring while the feature is a draft and a filled check once shipped (`ProgressIcon`, replacing `PhaseIcon`).
**Why:** The status dot beside the title already shows what is happening, so the glyph is free to say how far the work has got. Status and "none" were the alternatives shown.

## 10. Quick changes are retired: there are only features
**Decision:** The quick-change path goes: no feature is created with tickets already written, no review ticket is appended at birth, and nothing is marked plan-finished at creation. `create_feature` takes a title, a one-liner and a brief, and the feature's agent reads the brief and judges the work: it does a small change itself, or writes tickets and asks for the human's yes. There is no "quick change" type or path anywhere.
**Why:** Tickets are a tool of the feature's agent, which reads the code before it writes them. Pre-written tickets made a second place that cards work without looking, and only existed to skip grilling, which the agent can skip itself when the brief is concrete. The alternative weighed was keeping tickets-at-birth and dropping only the appended review ticket.

## 11. Laps are removed
**Decision:** A feature has no laps. The lap counter on the feature, the lap on tickets, and everything filed by lap (test notes, carried defects, review evidence, ticket tallies, the spec's "Later laps" section, the "thin lap 1" slicing question) go. After the human test-drives, they tell the agent what is wrong in chat, and the agent fixes it itself or writes more tickets; tickets simply accumulate on the feature. A review finding stays open until the agent resolves it. Scope deliberately deferred becomes a backlog feature, not a later lap. This overturns the charter's laps decision (CONTEXT.md #15).
**Why:** The human wants the simplest possible flow: build, drive, tell the agent, it fixes. With no phases there is no review-to-building moment for a lap to count, and grouping work by lap is machinery the human does not need.

## 12. Leftover machinery is removed
**Decision:** Four kinds of leftover machinery go. (1) Test-note filing: notes with screenshots jotted during a drive and "Send to agent" (one chat message) stay; marking notes done or open, promoting a note to a ticket, carrying and triaging notes, and the generated test-notes file go. (2) Human buttons that do the agent's job: Burn and re-burn, and "Run an agentic review"; the human asks in chat and the agent uses its tools. Stop and Merge stay the human's. (3) Planning-step bookkeeping: `complete_phase`, the "plan finished" mark (`ticketsReadyLap`), the phase stepper with its read-only past-phase views, Go's override, and its two locks (plan unfinished, uncommitted design work). The agent commits its own docs like any other change. (4) The orchestrator's `go_feature` tool; the rest of the orchestrator is left to *One orchestrator, no mode*.
**Why:** Each existed to push a feature through stages or to let the human do the agent's work by hand. Anything that proves useful later comes back as an agent tool, not a button. This overturns the charter's enforced gates (CONTEXT.md #8).

## 13. Every feature chat runs without permission prompts
**Decision:** One rule for every session on a feature, attended or headless, self-planning included: it runs without Claude Code permission prompts, as the lead does today. The self-plan run's docs-only edit lock goes; its instructions say to plan and not build.
**Why:** With one agent and no Go there is nothing left to switch permissions on. A lock kept only for self-plan runs would be an exception to explain; anything a misbehaving self-plan run wrote would land on the feature branch, never on main.
