Stopping a session kills its process

When runcastle stops an agent session, its processes really exit, and memory comes back. A server start also cleans up what earlier runs leaked (12 GB on the last autopilot run).

Under the hood

Cause, confirmed in today's code. The adapter is spawned without detached, so it shares the server's process group. The tree-kill helper sends one SIGTERM to -pid, gets ESRCH, swallows it. Detach drops the thread from the host's map before the kill and never waits, so the next prompt resumes beside the old one. Closing the connection never ends the adapter's stdin, which it would treat as shutdown. Windows uses taskkill /T /F, so the group bug is POSIX-only; the overlap is everywhere.

Fix. Spawn the adapter, the Codex side process, the short-command runner and the image build with detached off Windows. The tree stop: end stdin, SIGTERM the group, wait ~5 s, SIGKILL, confirm, report. The host keeps a per-thread "stopping" exit promise and awaits it before any spawn.

Start-up clean. After listen, before chats wake. Linux reads /proc/<pid>/environ; macOS ps -E -ww; the mark is RUNCASTLE_SESSION_ID plus RUNCASTLE_SERVER_URL equal to this server. Windows matches claude's --settings path under this data folder, and its parent adapter. Skips its own descendants; never blocks boot.

Tests. A real nested process tree is gone after the stop, including a child that ignores SIGTERM. The real spawn path with a fake adapter: stop leaves nothing; five resumes leave one holder of --resume=<id>. The start-up clean ends only marked processes for this URL.

Open: whether Windows adapters already die with the server (libuv job), and whether ps -E works under macOS SIP.
