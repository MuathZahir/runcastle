Features set up scenarios themselves

When a feature needs a slow-to-reach state and the project has no scenarios, its lead sets them up and proves them, so both reviews start right at that state instead of redoing signup.

What the lead does, in order

Only when the feature needs a state someone would build by hand 4 and the project is not set up yet.

1

Builds the feature's code, as today

Its Plan already said "the lead sets scenarios up" under who builds what. 3

2

Sets scenarios up

The same steps the human's ＋ New scenario chat follows: a drive-only login route if the app has sign-in, typecheck coverage, base fixtures, the runner command, then the scenarios.

login route_fixtures/runneraccounts/new-user-onboardedbilling/plan-card-ready-to-build

Green outline stays with the project 6. The feature's own scenario leaves with it, as today.

The fixtures are a ladder; each scenario calls the deepest step it needs and adds only its own bit. 9

signedUpUser()→onboardedUser()→userWithPlan()→ scenario: 3 lines + ENTRY_URL

A migration that breaks signup is fixed in signedUpUser(), and every scenario above it works again.

3

Proves each one on a real drive of its branch

Starts a drive the way a review does, runs the scenario, and a browser subagent checks the landing shows the state, signed in. 5

4

Starts the full review

The review replays the scenarios. A state it still had to reach by hand comes back as "No scenario reaches …".

5

Writes those missing scenarios, then the verify review

So the second walkthrough starts at the fixed state too. 7

If the project's drive cannot carry scenarios (it will not start, or it does not hand over the database), the lead says so once, points at project preparation, and the review goes on by hand. Nothing stops. 8

Under the hood
  • Lead drive tool (new). Shaped like the review's review_drive: start, status, stop, scenario. Reuses the review-drive path on the human's checkout, the one drive slot and drive.env; names the lead as holder; refused retriably while the slot is taken; gated to this feature's own lead.
  • Runner. set_scenario_runner is also given to the lead, unchanged.
  • "Set up" rule. scenarios.setUp = runner recorded and the base branch tracks any file under .runcastle/scenarios/, fixtures included, so a project whose scenarios all left is still set up.
  • Review prompt. The no-scenarios fallback also asks for the "No scenario reaches <state>" observation. "Never write a scenario" stays.
  • Skill pack. The feature skill's Scenarios section is rewritten; a new reference page carries the setup steps, taken from the ＋ New scenario chat's setup brief.
  • Ladder. Lives in the project's fixtures as functions calling their parents; runcastle reads nothing inside a scenario. Said in the setup page and in renderScenarioPrompt.
  • Proof. Runcastle has no sign-in, so the signed-in landing is proven on the human's own project after merge; live sessions get it only after a publish and reinstall.
