# Decisions — Project-level test drive

## 1. No video; capture is the DrivePanel's screenshot + note
**Decision:** A project drive records no video and has no annotation player. Capture during a project drive is the feature drive's existing DrivePanel experience — the live app in its iframe, drag-select screenshot (single-frame tab capture), a note box — except each note lands as a **project note** (text + one PNG) instead of a feature test note. Recording human drives stays parked.
**Why:** The shipped annotation player only annotates the review agent's walkthrough video; human drives are unrecorded by an explicit decision (`video-annotation-for-reviews` #2) that calls recording them its own sizeable feature. A project drive has no review agent, so there is nothing to play. Screenshot + text already carries "look at this", and the project-notes store already holds one PNG per note.

## 2. One lap, spec whole
**Decision:** Spec the entire feature as a single lap.
**Why:** The mechanics already exist in project-keyed form (preparation's dry run), the note store and capture shipped with `project-notes`, and the DrivePanel capture UI exists. What remains is glue in one area — no research, no prototype, a narrow design tree.

## 3. Drive the checkout as it is — never switch branches
**Decision:** A project drive runs on the project repo's current checkout (whatever HEAD is), exactly like preparation's dry run: no branch switch, no restore on stop, and therefore no dirty-tree guard — uncommitted edits are driven too. The drive surface names the branch being driven (and the repo path) prominently, so a checkout sitting somewhere other than main is visible before any note is taken. Notes land as project notes regardless of which branch it was.
**Why:** Chosen over "main only, switched in when needed" and a branch picker. It is the cheapest shape — the dry-run mechanics already do exactly this — and it is honest: you drive what is actually on disk. Features live in worktrees, so the main checkout normally already sits on main; when it doesn't, the visible branch label is the safeguard rather than a checkout dance.

## 4. The drive lives on the project workspace; the approved prototype is the UI
**Decision:** The approved design is `prototypes/project-drive.html` (published at https://claude.ai/artifact/W4AjzzEXCFRdWp827SZyVG). In words:
- **Resting page** gains a **Test drive card** between New chat and Notes, with a secondary (not solid) button — New chat stays the page's one solid button. The card states, before the click, what a drive will do: the branch the checkout is on (no switch), and the setup / dev / stop commands that will run, each unset one shown as "nothing set" with a Settings link. When the one drive slot is held by another drive, the button is disabled and names the holder; while this project's drive runs, the card reads "running" and its button returns to the drive.
- **Starting the drive takes over the workspace body**, as a live project chat does. Left: a header naming the branch and repo path, "Project page" (step back to the resting page, drive keeps running) and "Stop drive"; then the feature drive's stage — the app in its frame, Select area, Reload, Open app ↗ — and the dev-server strip with Show output. A titlebar pill shows a project drive is live and returns to it.
- **Right: the project's notes inbox, live** — notes from this drive first, then the notes that were already open (so a driver sees what is already reported), a composer at the bottom. Drag-select captures, the composer and Ctrl/⌘+J all write ordinary project notes.
- **Stop** returns to the resting page; the drive's notes are waiting on the Notes card. No summary, no prompt — the inbox is the exit.
- **A live project chat and a drive coexist.** While both are up, a Chat | Drive switch in the drive header chooses which fills the body; neither is refused or ended by the other.
**Why:** Everything about a project drive belongs to the project page, and a separate route would split one job across two places (the same call as `project-notes` #10). Showing the plan before the click answers `make-test-drive-clear`. The rail is the existing inbox rather than a second notes surface. Chat and drive hold different resources (a terminal vs. the drive slot), so refusing one for the other would break "inform, never block" with no git-safety reason.

## 5. A drive note carries the branch and commit it was seen on; the server stamps it
**Decision:** `project_notes` gains two nullable columns: **`driveBranch`** (the branch checked out when the drive started) and **`driveCommit`** (short HEAD SHA at drive start, suffixed `+dirty` when the tree had uncommitted changes). The server stamps both onto **every** project note created while that project's drive is live, whichever door it came through (drag-select, the rail composer, Ctrl/⌘+J) — no client passes them. The UI tags such notes `drive · <branch>` with the commit on hover; `list_project_notes` returns both fields so triage sees "noted while driving main @ 1882e87". The rail's "This drive" group is derived from the live drive's start time — there is no drive id. This extends `project-notes` #4's store (one service function, one table); it is not a parallel store.
**Why:** Drives are in-memory and unpersisted, so a drive id would dangle the moment a drive ends. Because decision 3 drives the checkout as-is, the branch alone is ambiguous — main on Tuesday is not main on Friday — and the commit lets triage tell whether an observation is already fixed. Server-side stamping makes the rule impossible to forget at any door. Two nullable columns are too small to justify a separate revisit of the shipped feature.

## 6. Merge stops a running project drive first, and says so in its confirm
**Decision:** When a project drive of the same project holds the slot, Merge stops it (running the stop command as an ordinary Stop would) before merging — the same treatment merge already gives a drive of the feature being merged. The merge confirmation dialog states it up front: a project drive is running on your checkout and merging stops it. Drives of *other* features keep today's hard refusal.
**Why:** Merge checks out and commits in the very checkout the project drive serves from; merging underneath a live dev server would leave setup, `drive.env` and migrations describing old code and make the drive's stamped commit (#5) false. A bare refusal would send the human to the project page and back for no gain — notes are already saved, only the dev server is lost. The confirm dialog is where four-states says to inform; and "merge, then drive main again" is the loop this feature exists for.

## 7. When the drive can't really run: hide, prepare, or show the failure
**Decision:**
- **Empty project** (born-empty — nothing but runcastle's docs): the Test drive card is hidden.
- **Neither a setup nor a dev command set**: the card still shows its plan, but its button is **"Prepare drive"** and opens the preparation workspace instead of starting a drive. With only one of the two set, the drive runs; setup-but-no-dev shows the stage's existing "bare" state, and the notes rail works as normal.
- **Setup command fails**: the feature drive's failure stage is reused — command, how it ended, output behind a disclosure, Stop — with the drive left up and the notes rail working. In place of the feature-scoped **Fix drive**, the project drive offers **"Open preparation"**.
**Why:** A project drive never switches branches, so with no commands it would do literally nothing — pointing at preparation is the useful move, not a block. Fix drive opens an agent scoped to a feature; preparation is the project-level surface where drive commands are repaired and proven.

## 8. A project drive runs under the fixed identity `project-drive`
**Decision:** Setup and stop scripts of a project drive receive `RUNCASTLE_SLUG=project-drive` (so `RUNCASTLE_ID=project_drive`) and `RUNCASTLE_BRANCH` = the branch actually checked out. The identity is the same for every project drive of the project; the card's plan shows "as `project-drive`".
**Why:** Chosen over reusing the dry run's `prep-dry-run` (preparation's proof runs and real driving would trample one shared database) and a fresh slug per drive (databases leak unless the stop script drops them). Driving main is ongoing use of the app as it stands, so state built up in one drive should be there in the next; isolation from feature drives is the property that matters. Whether the data actually persists stays the project's setup script's call — runcastle only injects identity.

## 9. A project drive shares the one slot unchanged; wherever it blocks, it is named and stoppable
**Decision:** The single machine-wide drive slot keeps its rules: a project drive holds it like any other drive, nothing preempts it, and a review agent never stops it. Every place a project drive blocks something names it — "a project drive of `<branch>` is running" — and offers **Stop it** (or a link to it): the review-drive denial banner, the feature page's disabled Test drive tooltip, and preparation's dry-run refusal. The titlebar pill (#4) keeps a live project drive visible on every in-project screen. No idle timeout, no auto-stop.
**Why:** A project drive is the human's own session; letting an agent take the slot would kill it mid-use, and drives have no activity signal to time out on honestly. The real risk is a forgotten drive quietly stalling reviews, which visibility plus a one-click stop at the point of blocking solves without new rules.

## 10. Out of scope
**Decision:** Not in this feature: recording human drives (video) or an annotation player for them; drive-machinery robustness (restart survival, `{{port}}`, setup client timeout — `test-drive-improvements` #8, still parked); any embedded browser beyond the existing app frame; any change to how feature drives behave beyond naming a blocking project drive (#9); a branch picker; auto-creating work from notes (triage stays the project session's job).
**Why:** The brief's fences, plus the options rejected in #1 and #3.
