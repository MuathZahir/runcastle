# Prompts read the evidence

## Ticket 1

The lap session reads the previous lap's review evidence and any 'not demonstrable' markers before it plans. In the 2026-09-14 post-mortem a lap session asked 'what are these tickets based on? did you test the app?' answered 'No, I moved too quickly to Burn' and burned one minute later; and the human was shown a lap-1 build whose own plan said 'no UI, nobody should demo this before ticket X'. Today the lap kickoff names carried notes and open defects (review-arrival-is-legible decision 7) but not the review artefacts themselves. Change the revisit/lap skill in packages/skills and the injected feature context so that before planning the session (1) reads the previous lap's review DIGEST.md and screenshots directory (~/.runcastle/reviews/<ticket>/) and the review outcome, (2) greps the spec and tickets for 'not demonstrable' / 'do not demo' / 'later laps' markers and says so to the human before offering a test drive, and (3) applies a 'stand on the failure' rule for every human-reported bug: reproduce it, or trace it to file and line, or declare it unreproduced and make reproduction the ticket's first acceptance criterion. Keep it prompt-side; no new gate. Tests: the rendered kickoff/context for a lap ≥ 2 includes the artefact paths, pinned beside the existing kickoff-registry tests.

## Ticket 2

The tickets skill budgets parallelism explicitly. On a real project burnConcurrency was 3 and every lap's tickets formed a dependency chain, so measured speed-ups were 1.09x, 1.16x and 1.00x: a chain of N tickets is N sequential sandboxes. Change packages/skills tickets skill (and the converge path that emits tickets) so the session, after slicing, states the dependency graph's critical path and the number of tickets that can run at once against the project's burnConcurrency, and reslices when the chain is longer than roughly total/concurrency; it must not chain tickets by habit, only where a ticket genuinely reads the other's output. Add the rule beside the existing 'every batch closes with one review ticket' rule so the two are read together. Test: the skill text asserts the rule (skills are content; pin the wording the way packages/skills tests already pin other rules).

## Ticket 3

Thin ticket contexts and degenerate imports warn at the Burn card, never block. A 14-ticket quick change was imported where every ticket had title == goal == context == first acceptance criterion, 3.7-4.3 KB blobs truncated mid-word, empty seams and text-only dependencies; the implement prompt's TDD discipline cannot execute that shape. The quick-change door (quickChange, features.ts:374; create_feature tickets shape, mcp/server.ts:2042) has no validation at all. Add warnings, not refusals (the operator chose two hard rules only): at ticket creation and again on the Burn card, flag a ticket whose context is under ~300 characters or whose goal equals its context, a quick change with more than ~5 tickets, a prose over ~1500 characters that looks like a pasted document, and a docs digest injected into burns over a size threshold (emitDocsDigestEvent at ticket-burner.ts:3505 already reports bytes; add the threshold and the card line). Each warning names the ticket and says what to fix. Tests: each shape yields its warning; a well-formed batch yields none; Burn stays enabled in every case.
