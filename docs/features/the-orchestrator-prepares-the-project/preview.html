How it gets built

Four tickets, one at a time (this project burns one ticket at once), then a review round that drives the onboarding scenario.

  • #1The Orchestrator gets preparation: open settings, "none", its start note, the dry run with landing, the skill movesserver, skills
  • #2Start the project wired, Preparation screens gone, buttons re-pointedweb
  • #3The preparation chat kind deleted, old chats removed by a migrationafter #1, #2
  • #4The onboarding drive: scenario variable, empty start, sample repo, drive tool takes a scenarioafter #1
  • #5Review: drive the onboarding scenario end to endafter all

Under the hood
  • OpenA key is open with no value and no finding; record_finding takes a "none". The session-ended rule and its date go.
  • NoteThe SessionStart digest for a project chat carries open keys, empty repo, ever-had-a-feature.
  • Landdry_run_drive (project kind only) and start_feature land runcastle/project on the base branch first, like a git pull; refused on conflict, overlapping edits or another branch.
  • SkillThe prepare skill becomes project/references/preparation.md; the project skill's opening gains the exception.
  • GoneThe prepare kind, talkToPrep, PreparationWorkspace, the /prepare route, PrepRow, the palette row, the guards' prepare cases. A migration deletes old prepare chats.
  • DriveDrive setup gets RUNCASTLE_SCENARIO; runcastle's own setup starts empty with a private git config for the onboarding scenario.
  • ModelThe roster step prepare stays for scenario and drive-fix chats, labelled "Drive chats".
