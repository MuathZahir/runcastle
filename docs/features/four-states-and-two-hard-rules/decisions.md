# Decisions — four-states-and-two-hard-rules

## 1. One lap, spec the whole thing
**Decision:** Spec the full state-model collapse as one lap; no thin walking-skeleton slice, no map.
**Why:** The uncertainty was burned down in the project session (four states, two hard refusals, Burn/Merge as the only clicks are settled). A half-collapsed state enum is a worse intermediate state than either endpoint, and all five open questions are entangled with the same enum change, so slicing buys risk, not safety.

## 2. Planning sub-steps are derived, not stored; complete_phase stays wire-compatible
**Decision:** The state enum collapses to Planning/Building/Review/Shipped with no `step` column inside Planning. `complete_phase` keeps its name and its `phase: "ideation" | "spec" | "tickets"` argument, but inside Planning it transitions nothing — it records a timeline progress event and returns `ok` plus what's next. UI hints about progress inside Planning derive from artifacts: decisions.md exists → ideation done, spec.md exists → spec done, tickets in the store → tickets emitted.
**Why:** Same spirit as the lap counter: derived state nobody manages. A stored sub-step re-creates a mini-pipeline inside Planning — exactly the decoration the post-mortem condemned — while the artifacts already carry the answer. Keeping `complete_phase`'s wire shape means the skills (`/runcastle:ideate`, `spec`, `tickets`, `converge`) and in-flight sessions need zero rework. The former phase-complete stamps survive as honest timeline events, not gate crossings.

## 3. Mutation surface: burn and merge are the only state-moving mutations
**Decision:** `rethink` dies outright — mutation, `rethinkAndLaunch`, the `lap.aborted` event and `LapAbortAlert.tsx`, no deprecation stub. `advance` (tRPC mutation) dies too; the internal service shrinks — the runner's Building → Review auto-advance uses `setPhase`, and `complete_phase` no longer transitions (decision 2). `burn` and `merge` survive: Burn crosses Planning → Building and stamps the lap; Merge crosses to Shipped from any state after creation, guarded only by the two git refusals, with no phase precondition. Next-step resolvers collapse six → four: `planning.ts` (derives grill → spec → tickets → Burn hints from artifacts), `building.ts`, `review.ts`, `shipped.ts`; `draft.ts` stays (draft is a status, not a phase).
**Why:** With sub-steps derived and two human clicks, there is no generic "step the pipeline" action left; the UI is the only caller of `advance`/`rethink` and it ships in the same lap, so a compatibility alias would have nobody to be compatible with. Dead mutations kept "just in case" are the residue this feature exists to remove.

## 4. Migration: one irreversible value-mapping, history untouched
**Decision:** A single SQL migration maps the old enum to the new: `ideation`/`spec`/`tickets` → `planning`, `implementation` → `building`, `review` and `shipped` unchanged. `Phase` in `packages/core/src/schemas.ts` becomes the four-value enum. No dual-enum period, no down-migration. Historical timeline events naming old phases are left exactly as written.
**Why:** The mapping loses nothing: the derived sub-step (decision 2) recovers "where inside Planning" from artifacts, so a row at `spec` is just a Planning feature with decisions.md present. Rewriting old events would be falsifying the record, not cleaning it. The collapse is deliberately one-way — the old sub-phase cannot be reconstructed and nothing moves backwards. A side effect is the cure for the post-mortem wedge: a Rethink'd feature stuck at ideation becomes a Planning feature with Burn and Merge both reachable.

## 5. Burn warns like Merge warns: server-computed warnings, enabled button
**Decision:** Burn gets the MergeFeatureDialog pattern — a confirm dialog stating what will burn (pending tickets, the lap it stamps, model), a warn-styled box, an enabled primary button; friction is reading, never disabling. Warnings are computed server-side and exposed via a tRPC query (the `mergeDelta` pattern): no `kind: "review"` ticket in the pending batch (ex-G3), earlier-lap open defects not linked/carried/closed, no spec.md on disk. `complete_phase("tickets")` stops refusing on the review-ticket precondition and instead returns `ok: true` with a `warnings` field carrying the same list, so the session hears it while it can still fix it. Burn with zero pending tickets is not offered — a no-op, not a gate; the next-step bar hints "emit tickets" instead. Hard refusals at Burn stay exactly two: a burn already running on this feature, and git safety (surfacing as launch failure).
**Why:** Extends the settled "inform, never block" rule (test-drive decision 7, flow decisions 29/31) from Merge to Burn with the same UI grammar, so the operator learns one pattern. Server-computed warnings keep the UI from re-deriving policy. The MCP warning preserves the one real value of the old G3 refusal — telling the ticket-writing session at the moment it is alive to act — without the seatbelt firing hours later at the human.

## 6. Override machinery dies, table included
**Decision:** Delete the gate-override machinery entirely: `gates.ts:220-310`, the `overrideGate`/`undoOverride` mutations, `previousPhase` in `pipeline.ts` (its only caller is the override undo), and the `gate_overrides` table — dropped in the same migration as the enum collapse, historical rows included. Tests pinning override behavior go with it.
**Why:** Overrides exist to push past a refusing gate. After this feature the only refusals are the two hard rules, and those are physics that must not be overridable — an override on "one burn at a time" or a dirty main checkout is a foot-gun, not an escape hatch. Everything else warns and lets you through. A read-only history table would be dead schema every future migration carries, for a story the events table already tells.

## 7. Merge during a live burn warns; auto-advance no-ops on Shipped
**Decision:** Clicking Merge while a burn is live (Building) is a warning, not a third refusal: "a burn is live — work landing after this merge stays unshipped on the branch." When that run finishes, the runner's Building → Review auto-advance becomes a no-op on a feature already Shipped; the run itself completes normally and its events still land on the timeline.
**Why:** Git-wise the merge is safe — it takes what has landed; agents keep committing to the feature branch after it. The operator may want exactly the landed commits. The auto-advance guard is just "nothing moves backwards" applied to the one writer that could violate it.
