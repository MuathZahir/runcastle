# Decisions — Preparation proves its findings

## 1. The dry-run runs on the real drive machinery, triggered server-side
**Decision:** The dry-run drive is executed by the server's actual drive path (env render, setup hook, dev pane spawn, URL sniff, stop hook), triggered from the prep session via a new MCP tool — not by the prep agent running the commands in its own shell. Verified status is stamped server-side from observed results, never self-reported by the agent.
**Why:** Fidelity and trust. The drive path has its own shell choice, Windows quoting workaround, `{{...}}` env rendering and PTY spawn — a command that works in the agent's shell can still fail there, and "proves" only means something if the proving path is the running path. Server-side stamping keeps the agent from marking its own homework.

## 2. Only the four drive-loop keys are verifiable, each by its own observable
**Decision:** The dry run can verify `driveEnv` (rendered with zero unknown placeholders), `driveSetupCommand` (exit 0), `devCommand` (pane spawned AND localhost URL sniffed), and `driveStopCommand` (exit 0). It verifies whatever subset is set — an empty key simply isn't part of the run. `dbResetCommand` (drift-banner only, not in the drive loop) and the sandbox keys (`setupCommand`, `verifyCommands`, `knownFailures`) are unverifiable by a host drive: they never get a verified badge, and that reads as "unverifiable", not "failed".
**Why:** Verification must mean "the running path observed it work". A host drive never touches the sandbox keys, and `dbResetCommand` has no drive slot to prove it in; stretching the stamp to cover them would make it a guess with a badge. For `devCommand`, "spawned" is too weak (a crash-on-boot still spawns) — the sniffed URL is what "Open app" depends on, so it's the signal.

## 3. The dry run is a two-half flow: server drives, agent inspects between halves
**Decision:** The dry run replays the whole test-drive lifecycle minus the branch switch, in two halves. Start half: render `driveEnv` under a synthetic drive identity, run `driveSetupCommand`, spawn `devCommand` in a real dev pane, sniff the URL. The agent then inspects while it's up — stack-aware checks the server can't do generically (temp DB exists and is fresh, migrations applied, app actually responds at the URL). Stop half: run `driveStopCommand`, then the agent inspects cleanup (temp DB gone, nothing orphaned). Anything off → agent fixes the finding and re-runs until a full pass is clean. Verified stamps come ONLY from the server's machinery observables on a clean full pass; the agent's deeper checks decide whether to fix-and-retry, never the stamp itself.
**Why:** "The DB is there, new, migrated, and gone afterwards" is database introspection, and the drive design deliberately models no vendor's database — but the prep agent is on the host and knows the stack, so it does the introspection while the server proves the machinery. The split keeps the stamp honest (a sloppy agent can't upgrade it) while a diligent agent catches "exit 0 but the DB never appeared".

## 4. One lap — spec the whole thing
**Decision:** Spec the full feature in one lap: schema, dry-run service + MCP tool, prep prompt changes, verified badges in the prep UI, and the unverified-key warning at drive start. No deferred laps.
**Why:** The mechanics reuse existing machinery (drive hooks, dev pane, env render) and the human described the end-to-end flow without hesitation — the uncertainty that would justify a thin lap 1 isn't there.

## 5. Synthetic identity: slug `prep-dry-run`, branch = the repo's real current branch
**Decision:** The dry run renders drive variables from a fixed reserved slug `prep-dry-run` (so `{{id}}` → `prep_dry_run`, temp DB e.g. `myapp_prep_dry_run`) and passes the repo's actual current branch as `{{branch}}`. No per-run uniqueness (no timestamps).
**Why:** The name can't collide with a real feature's drive DB, and an orphan left by a failed teardown is self-describing — a human seeing `myapp_prep_dry_run` knows what left it and that it's droppable. A retry wanting the same name is a feature: a leftover DB from a failed previous attempt makes `createdb` fail loudly, which is the "make sure it's new" check enforced by the machinery itself. `{{branch}}` stays truthful rather than invented.

## 6. Any write to a verified key clears the stamp; provenance and repo-staleness don't touch it
**Decision:** Verification is invalidated by exactly one thing: a write to the key (human settings edit, prep re-record, or clear) — no value-diffing; a write is a write. The only way to become verified is a clean dry-run pass. Verification is orthogonal to provenance: a `human`-sourced value can be verified (the stamp records "this exact value was seen working", not who chose it). Repo movement does NOT un-verify: verification carries its own sha and ages visibly like findings do, but the drive-UI warning fires only on never-verified-or-invalidated, not on staleness.
**Why:** A stamp that survives edits is a lie waiting to be trusted, and re-verification is one dry run away. Staleness already has its own signal (`staleCommits`); routing it into the warning would make the warning fire on every active repo, and a warning that always fires is one nobody reads.

## 7. The warning is inline and non-blocking, at the Start-test-drive step
**Decision:** When any drive-loop key has a value but no valid verification, the next-step bar's Start-test-drive step shows an inline warning naming the specific unverified keys and pointing at preparation ("never proven by a dry run — run preparation to verify"). One click still starts the drive; no modal, nothing interrupts. Keys with no value at all don't warn — a checkout-only drive stays clean.
**Why:** Drives are deliberately best-effort (a failing hook never fails a drive; a possibly-failing one shouldn't gate one), and they happen on every feature review — a modal would become a click-through ritual for anyone who skips the dry run. The inline line sits where the eye already is before the click, stays honest, and disappears forever once a dry run passes.

## 8. The dry run is the prep session's closing move — instructed by the prompt, never enforced
**Decision:** The prep prompt gains a closing section: once open keys are recorded, the agent proposes the dry run as the session's finale, under the existing "ask before you act" rule (it starts services and creates a database on the host). If the human declines, the session ends normally and the keys stay unverified. `isPrepared` is untouched — no gate on session end, no verification requirement in the prepared flag.
**Why:** Skipping carries its own visible consequence (the drive UI keeps surfacing unverified keys), so a hard gate buys nothing. `isPrepared` exists to stop the call-to-action nagging, and a human who consciously skipped the dry run has still been through preparation — the unverified badge, not the prepared flag, is where the remaining doubt lives.

## 9. The dry run occupies the same singleton drive slot as real test drives
**Decision:** The dry run lives in the existing one-at-a-time drive state. Dry run while a feature drive is active → MCP tool refuses with a reason; feature drive while a dry run is up → refused likewise (next-step bar says a preparation dry-run is in progress). The dry run surfaces in the UI as the active drive (project-scoped, no feature) with a working Stop control, so a human can run the teardown half by hand if the prep session dies mid-run, and server-boot reconciliation treats it like any orphaned drive.
**Why:** They genuinely collide (same repo, ports, dev pane, database server), and living in the drive slot inherits the whole lifecycle — stop control, orphan reconciliation — that a bespoke parallel state would have to rebuild. Accepted consequence: a dry run blocks feature drives while up; dry runs are short and human-attended.

## 10. Verified state surfaces in the prep workspace and project settings, off one source of truth
**Decision:** `ProjectFinding` grows optional verification fields (stamped-at time and sha). Two display surfaces beyond the drive warning: the preparation workspace findings list shows per-key "verified (age)" / "unverified" on the drive-loop keys, and the project-settings prepared-key fields show the same stamp inline. Non-verifiable keys (`dbResetCommand`, sandbox keys) show nothing — absence of proof, not failure.
**Why:** Settings is where a human edits a value, so "editing this clears its verification" must be legible at the moment it happens; the prep workspace is where findings already live. One set of fields on the finding keeps all three surfaces reading the same truth — no separate verification table to drift.
