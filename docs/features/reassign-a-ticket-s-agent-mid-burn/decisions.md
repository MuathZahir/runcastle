# Decisions — reassign a ticket's agent mid-burn

## 1. One lap, spec whole
**Decision:** Sure and small — spec the entire feature in one lap: model menu on run lanes, launch-time model resolution, quota-exhausted-as-fatal classification, and the retry gesture. In-run retry-with-new-model is the one piece pre-agreed as demotable to `## Later laps` if it fights ADR-0006's scheduler constraints.
**Why:** Scope is three narrow edits riding on plumbing the brief verified already exists (`ticketCredentials` re-resolves model+auth per ticket). Uncertainty is low; the areas are too interdependent to slice.

## 2. Reassignment is pending/failed only; burning lanes stay committed
**Decision:** The run-lane model menu appears only on pending and failed tickets. A burning lane cannot be reassigned — stop is the human's separate first move; the stopped ticket lands in failed and takes a reassignment there.
**Why:** Matches `assertMutable`'s existing contract (refuses `burning` rows) — nothing to extend. A one-click stop-and-reassign hides a destructive action behind a dropdown for the price of one saved click, and drags in worktree/attempt-count questions the plain stop path already answers. With quota-exhausted classified fatal, a stranded burning ticket dies fast and lands in failed where the menu waits.

## 3. Launch-time resolution: refresh the whole row in `runOne` via `ctx.listTickets`; launched lanes are committed
**Decision:** When a lane starts (`runOne` in `burnTickets`), re-read the live ticket row from the store via the existing `ctx.listTickets` seam and launch that row instead of the run-start snapshot copy; fall back to the snapshot when the ctx has no store hook (test fakes unchanged). Refresh the whole row — model, body, criteria — not just the `model` column; the scheduler's own bookkeeping (`status`, `blockedBy` graph) stays on its snapshot. A mid-run edit reaches only not-yet-launched tickets; a burning lane finishes (or is stopped) on the model it launched with — no signal to running lanes.
**Why:** The launched ticket object is the single source of truth downstream: it flows through `gateTicketAuth` → `ticketCredentials` → executor untouched, so one refresh point makes model, auth token, and the per-ticket precheck all see the new assignment — the brief's "precheck and executor cannot disagree" property preserved for free. Whole-row refresh because `ticket.edit` also allows body edits on pending tickets, and launching stale text when the fresh row is in hand serves nobody.

## 4. No in-run retry; "retry on <model>" is one gesture only when no run is live, composed in the UI
**Decision:** ADR-0006's refusal of `ticket.retry` while a run is live stands. In-run retry (via scheduler re-admission) is parked in the spec's `## Later laps`. Where retry is legal — no run live — a failed lane's retry affordance grows a model choice: the UI composes the existing `ticket.edit` (model) then `ticket.retry` calls as a single click. No new server surface.
**Why:** The refusal is real scheduler mechanics, not just a guard: a reset seq the scheduler already moved to `failed` is never reconsidered, and its dependents may have cascade-failed — in-run reset means unwinding cascade state mid-flight. (`admitNewTickets` is a plausible re-admission seed for a later lap, but it fires only when a review settles and doesn't unwind cascades.) Composition is safe because edit lands first and the retry burn resolves the fresh row anyway (decision 3). The incident is still fixed: fatal quota classification drains the run in seconds; queued tickets reassign same-run, failed ones take edit mid-run and one retry click at run end.

## 5. Error classification is out of scope; reassignment covers every non-burning status
**Decision:** The brief's "quota-exhausted classifies fatal" tweak is dropped from this feature — no classifier changes, no fatal-table entries, no streamed-text enrichment. The feature is purely manual reassignment: the model is editable on any ticket that is not actively `burning` — pending, failed (including stopped-by-user), and cancelled — from the run lanes and the ticket ledger alike.
**Why:** Operator call: don't complicate it. The timeline investigation showed the observed quota deaths carry an empty error tail (`codex exited with code 1:` with nothing after the colon), so making classification work would mean enriching the classifier's input with streamed agent text — real machinery, and the in-flight `failure-aware-scheduling` feature already landed a `run-fatal` verdict with a `/usage limit/i` pattern on its branch. Classification belongs there (or nowhere), not here. Investigation notes preserved in this file and the spec for whoever picks it up.

## 6. Server contract unchanged: pending/failed stay the editable statuses; UI-only surface change
**Decision:** `assertMutable`'s pending/failed set stands untouched — "stopped" is a failed status and is covered; `cancelled` and `done` stay locked. The feature's changes are: the run-lane `ModelMenu` on pending/failed lanes (same component, roster, and `ticket.edit` door as the tickets-phase ledger), decision 3's launch-time row refresh, and decision 4's one-gesture "retry on <model>" on failed lanes when no run is live.
**Why:** A cancelled ticket is waived and never burns again, so a model edit on it can never take effect — a dead control; the existing contract's history argument ("rewriting done/cancelled would lie about what was burned") holds. Everything the incident needs is UI plus the launch-time refresh.
