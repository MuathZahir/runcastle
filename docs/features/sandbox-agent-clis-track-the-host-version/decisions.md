# Decisions — Sandbox agent CLIs track the host version

## 1. One lap, whole scope, no map
**Decision:** Spec the full brief (versions recorded on images, doctor drift check, install-layer-only Rebuild, burn preflight, classifying the "CLI too old" 400, surfacing build setup failures) as a single lap. The feature is not mapped.
**Why:** Every deliverable hangs off one mechanism and lands in seams that already exist (`sandbox-image.ts`, the doctor's image row, the burner's fatal-error classifier). Nothing needs research or a prototype first, and the two open questions can be settled in this session.

## 2. The sandbox CLIs are pinned to the host's versions through build-args
**Decision:** The stock Dockerfile and Containerfile declare `ARG CODEX_VERSION` and `ARG CLAUDE_CODE_VERSION`, each directly above its install `RUN`. The installs pin to those values (`@openai/codex@${CODEX_VERSION}`, `install.sh | bash -s ${CLAUDE_CODE_VERSION}`). Rebuild resolves them from the host's `codex --version` / `claude --version`. The rule is that the sandbox runs whatever the host runs.
**Why:** A changed arg changes the cache key for that install layer and the layers after it, and nothing before it. That makes Rebuild cheap and correct without anyone needing to know about `--no-cache`. `--no-cache` on every build was rejected because it pays the full rebuild every time. Installing at sandbox start was rejected because every burn would pay for it, it needs network access, and it fails mid-run. Pinning to the host rather than to "latest" keeps interactive sessions and burns on the same CLI, so a host `claude update` has an obvious fix: Rebuild.

## 3. Images record CLI versions as labels; only custom images are probed
**Decision:** Every image runcastle builds is stamped `runcastle.claude-code-version` and `runcastle.codex-version`, alongside `runcastle.dockerfile-hash`, with the same values passed as build-args. The doctor reads them with the `image inspect` it already runs. Project images inherit the stock image's labels through `FROM`, so base drift shows on them too and the existing chain rebuild fixes it. Custom (unmanaged, hand-typed) images carry no labels. For those only, the doctor probes with `<runtime> run --rm --entrypoint sh <image> -c 'claude --version; codex --version'`, and it warns without arming the button.
**Why:** A label is free to read and records exactly what the build was asked to install. A probe starts a container on every doctor pass just to learn the same thing. Accepted gap: a project Dockerfile that reinstalls an agent CLI on top of the base would make the inherited label wrong. The stock image owns the agent CLIs, so that case is out of scope.

## 4. A CLI missing on the host means no pin and no drift check for that runtime
**Decision:** When the host has no `claude` or `codex`, Rebuild leaves that build-arg empty and the Dockerfile falls back to latest (`${CODEX_VERSION:-latest}`, or `install.sh` with no version). The image's version label for that runtime is stamped empty, and the doctor reports "not on host — not checked" rather than stale. Burns need nothing extra, because a runtime whose CLI and login are missing on the host is already refused by its `checkReady`.
**Why:** Stale means "doesn't match the host". With no host version there is nothing to drift from. Inventing a target such as latest from npm would bring back network lookups and a button that stays armed forever.

## 5. Burns fail fast on a CLI version mismatch and never auto-rebuild
**Decision:** The existing run-level image preflight in the burner (the single `sh` probe for the agent binary and toolchain) also reads the in-image version of every agent runtime the run's tickets use. It compares each one to the host version with strict equality. On a mismatch the run aborts before any ticket container starts. The message names the image, both versions and the fix ("Rebuild from Settings → Burns — only the CLI layer rebuilds"). Burns never trigger a build.
**Why:** The brief's goal is that burns never die mid-run on a CLI that is too old, and only a check before any ticket runs guarantees that. Keeping auto-rebuild out upholds the shipped rule that image builds are terminal actions a human watches. Since decision 2, a Rebuild takes only seconds, so one click is cheap. Accepted trade-off: Claude Code auto-updates itself on the host, so a silent host update blocks burns until someone clicks Rebuild, even when the old CLI would have served the model. Warning only on a mismatch was rejected because it leaves the failure mid-run.

## 6. The burn preflight checks the container runtime first, using the doctor's classification
**Decision:** Before the image probe, the burn preflight runs the same health check as the doctor's `containerRuntimeProbe` (`<runtime> info`): not installed, daemon not responding, or podman machine stopped. When the runtime is down, the run aborts before any ticket starts, with the doctor's detail and fix text (for example "Start Docker Desktop, then re-burn"). This emits its own event (for example `burn.container_runtime_down`), not the image event. The image probe's "could not start a shell" fallback stops claiming the image is stale when the real cause is unknown. Docker dying mid-run is out of scope.
**Why:** Today a dead daemon makes the probe fail, and the burner reports that as "claude is not installed in image … Rebuild", which sends the human to a Rebuild that fails too, or leaves them guessing. The doctor already classifies this correctly. Reusing that one classifier keeps the doctor and the burn from disagreeing about whether Docker is up. It was folded in rather than parked because it is the same preflight seam this feature already changes.

## 7. "CLI too old for this model" is run-fatal and names the host update
**Decision:** Claude Code's `does not support this model; version … or newer is required` is classified **run-fatal** and checked before the retryable patterns. Today it matches `/\bapi error\b/i` and is retried, in every ticket. The message names the in-use version, the required version, the model, and the fix in order: "run `claude update` on the host, then Rebuild from Settings → Burns". No Codex pattern is added until its real wording has been observed.
**Why:** The error is a fact about the image, like a missing agent binary (already run-fatal), so every other ticket on that runtime would rediscover it. Because of decision 5's preflight, the error can only reach a burn when the host CLI is too old as well, so "Rebuild" alone would rebuild the same old version. The host update is the real first step. Guessing a Codex string risks misclassifying unrelated errors, and the preflight already covers Codex image drift.

## 8. "Surface setup failures" covers only the failure modes this feature touches
**Decision:** Three failure modes get a named, fixable message instead of a raw stderr line:
1. The host version cannot be resolved before a build (`--version` fails to spawn or prints something unparseable). The card says so, using the doctor's PATH fix text, and the build goes ahead unpinned for that runtime as in decision 4. It does not refuse.
2. A pinned install fails inside the build (the npm version is not found, or `install.sh` rejects the version). The card's failure state names the step and the version instead of showing only a non-zero exit.
3. The preflight probe's own failures, already covered by decision 6.

A general redesign of how build errors render is out of scope.
**Why:** These are the failures this feature creates or depends on. Anything broader is its own feature.

## 9. The doctor shows CLI drift as the existing stale state; unlabelled images read as stale
**Decision:** The doctor's image rows (stock and project) treat a version-label mismatch with the host as the same "stale → Rebuild" state as a hash mismatch. The row names the runtime and both versions (for example "Claude Code 2.1.270 in image, 2.1.280 on host"), and the build plan treats the stock image as not fresh whenever either check fails. A managed image with no version labels, which is every image built before this feature, reads as stale, following the shipped precedent for unlabelled hashes. Custom images get the probe-based warning from decision 3, and their button stays disarmed.
**Why:** One stale concept and one fix (Rebuild) keeps the UI honest and requires no new states. Counting unlabelled images as stale is the safe direction: runcastle cannot vouch for what they contain. The Dockerfile change in decision 2 alters the hash anyway, so every image needs one Rebuild after this ships regardless.
