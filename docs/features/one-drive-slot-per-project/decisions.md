# Decisions — One drive slot per project

## 1. One lap, the whole feature
**Decision:** The feature is specced and built in full in lap 1; nothing is deferred to a later lap.
**Why:** The intent is certain and the change is mechanical — the slot becomes keyed by project, every reader takes a project, the drive API takes a project id. The acceptance test is the original repro (a drive in project A, a test drive started in project B, both run), and nothing in it is uncertain enough to earn a walking skeleton.

## 2. Every surface is blind to other projects' drives
**Decision:** Every drive surface sees only its own project's drive — the project page's Test drive card, the feature page's Test drive button and its disabled tooltip, the titlebar drive pill, the review body, preparation's dry-run state, and the review agent's `review_drive`. Nothing anywhere hints that another project has a drive running.
**Why:** Nothing in project A can act on B's drive — cross-project collision warnings were ruled out at intake — so a hint would be noise. The titlebar pill is already filtered to this project, so blindness is today's behaviour inside one project. A forgotten drive in B is still shown on B's own pages, the same as a forgotten dev server in another terminal.

## 3. The drive API is asked per project; there is no global view
**Decision:** `feature.driveInfo` takes a required `{ projectId }` and answers with that project's drive or null. Server-side, every reader of the slot takes a project: `activeDriveInfo`, `activeTestDriveFeatureId`, the readiness poll's "is it still the same drive" check, `holdSetupJob`, and the review drive's releaser (one per project, not one global). The MCP drive tools (`review_drive`, `dry_run_drive`, `retry_drive`) and the drive-fix launch keep their inputs — they already resolve a project from their session — and read that project's slot. Nothing answers "what is driving anywhere".
**Why:** The bug was a reader that forgot to filter by project. Making the project a required argument means no reader can see another project's drive by accident; a global list filtered client-side would leave that mistake one forgotten filter away.

## 4. ADR-0014 records the amendment; the shipped decisions stay as written
**Decision:** A new `docs/adr/0014-one-drive-slot-per-project.md`, shaped like ADR-0013, with an **Amends:** line naming `preparation-proves-its-findings` decision 9 and `project-level-test-drive` decision 9. Its context is the brief's argument (both justified the single slot by collisions inside one repo; across projects the checkout, dev pane, drive env file and repo are all distinct, and one project is one checkout because projects are unique by canonical repo path). Its decision: one slot per project; within a project everything those decisions said still holds; no cross-project collision detection, by design. The two shipped `decisions.md` files are not edited. The ADR is written by a ticket, alongside the change it explains.
**Why:** The shipped docs are the record of what was decided then; the ADR is where the change lives, as ADR-0013 did for decision 24. A talk session may only write this feature's docs, so the ADR rides a ticket.

## 5. Drive identity is unchanged; the prepare recipes stop sharing names across projects
**Decision:** `RUNCASTLE_ID` stays exactly as it is — `project_drive` for every project drive, `prep_dry_run` for every dry run, the feature slug for a feature drive — so two projects' concurrent drives can carry the same id. The prepare skill's `references/recipes.md` is amended so every recipe names shared resources with the app prefix: the Redis recipe derives its index (and key prefix) from `myapp_$RUNCASTLE_ID`, not the bare id, and the schema-per-drive recipe prefixes its schema name the same way. ADR-0014's consequences state the rule: `RUNCASTLE_ID` is unique within a project only, so anything shared across projects (a local Redis, a shared database) must be named with an app prefix. No detection of scripts that break the rule.
**Why:** With one machine-wide slot a shared id could never be live twice; per-project slots make it possible, and the Redis recipe as written would let B's stop flush A's live drive data — silent loss, not the visible port/bind failure intake accepted. Changing the identity instead would silently re-point every prepared project's persistent project-drive database (project-level-test-drive #8) at a fresh one. Already-prepared projects keep their scripts; the ADR names the hazard rather than detecting it, in line with intake's no-collision-detection fence.

## 6. Inside one project, nothing about drives changes
**Decision:** Within a project the slot behaves exactly as today: one drive at a time across all four kinds (human test drive, review drive, project drive, preparation dry run); the same refusals with the same wording; a blocking drive is always named and stoppable (project-level-test-drive #9); a review agent never preempts a human drive; the human's Stop can still reclaim the slot from a review agent that died holding it; the review agent's slot-held wait/retry waits only on its own project's slot. The merge guard from `merge-is-not-blocked-by-another-project-s-drive` keeps holding — a merge is denied only by a drive of its own project — and its tests stay green. A server restart still forgets every drive, as today; there is no boot reconciliation of drives to change. Out of scope, from the brief: per-drive ports (`{{port}}`, E2E-FINDINGS F7) and cross-project collision detection.
**Why:** The brief's must-not-swallow fences. The single slot was right inside one repo (same checkout, dev pane, drive env file, ports, database server); only its reach across projects was an accident.
