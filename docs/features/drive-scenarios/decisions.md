# Decisions — Drive scenarios

## 1. Lap 1 is the web path end to end; the rest are later laps
**Decision:** Lap 1 delivers the scenario contract (a project command that prints `ENTRY_URL=…`), discovery, the drive-only login route (set up by the first ＋ New scenario chat, decision 5), the scenario picker at Test drive, ＋ New scenario (the agent writes the scenario, runs it against the drive you are in, and lands you there), and one dogfood scenario on runcastle-demo. Later laps: API scenarios and **Try it**, review agents replaying scenarios, feature agents shipping scenarios on their own judgement, and the Blank app nudge.
**Why:** The concept is settled, so lap 1 is real, not a throwaway skeleton. The core risk is whether a command plus a login route lands the human signed in, in a real app, and whether the chat writes a working scenario. Everything deferred builds on that and is cheap once it works.

## 2. Scenarios are discovered from `.runcastle/scenarios/`; one runner command runs them
**Decision:** A scenario is a file under `.runcastle/scenarios/` (fixed path, not configurable), committed with the project's other runcastle machinery. Its group is its first subfolder (`checkout/` → Checkout), and its display name is its file name made readable (`expired-coupon.ts` → Expired coupon). A file directly under `scenarios/` has no group. Files and folders starting with `_` (e.g. `_fixtures/`) are shared code, not scenarios. The project's host settings carry one runner command with a `{file}` placeholder (`bun {file}`, `bin/rails runner {file}`, …), which runcastle runs inside the drive and reads `ENTRY_URL=…` from. A feature's own scenarios are the scenario files its branch added or changed against its base, found by git diff. There is no manifest.
**Why:** Runcastle only lists paths and diffs git, so it stays language-agnostic and inside "paths, git and text". With no manifest there is nothing to drift: adding a file is enough. `.runcastle/` is already where committed project machinery lives (the drive scripts, the sandbox Dockerfile), versioned with the code it serves. One consequence: the project's typecheck must cover `.runcastle/scenarios/`, which dot-folders often miss by default, or the promise that scenarios break loudly when the model changes does not hold.

## 3. A failed scenario keeps the drive up and shows exactly what went wrong
**Decision:** A scenario fails when it exits non-zero or prints no `ENTRY_URL`. The drive still comes up, landing on its plain URL as Blank app would. The drive shows the failure where the human is looking: which scenario failed, why (the exit code, or "printed no ENTRY_URL"), and the tail of its output, so the human can see what went wrong without opening anything. A **Fix it** button opens the same chat as ＋ New scenario, briefed with that file and its output; the agent repairs the scenario, reruns it against this drive and lands the human there. The failure is also recorded on the timeline. Runcastle runs the command once: no retries, no fallback.
**Why:** A scenario breaking when the model changes is the design working. Throwing away a healthy drive for a stale fixture costs a full restart for what is usually a one-line fix, while **Fix it** repairs it in place. The human asked explicitly that the error itself be shown, not just the fact of failure.

## 4. A scenario lands on the branch being driven, committed by the chat
**Decision:** The scenario chat runs in the drive's checkout (the project's main checkout, as the existing Fix drive session does) and commits its scenario onto whatever branch is under the wheel before landing the human. On a feature drive that is `feature/<slug>`, so the scenario becomes one of the feature's own scenarios and merges with it. On a project drive of `main` it is a commit on `main`. The chat always commits, so nothing comes back as carried changes at stop.
**Why:** A scenario written during a feature drive usually uses that feature's new models and compiles only there. One rule covers both drive kinds. Routing `main` scenarios through a branch or the project worktree would be ceremony for a file that only affects drives.

## 5. The first ＋ New scenario chat sets scenarios up; `prepare` stays out of it
**Decision:** When the driven branch has no `.runcastle/scenarios/` yet, the scenario chat starts in setup mode and the edit guard opens the whole checkout. Its brief: add the drive-only login route if the app has sign-in (`/__drive/login?token=…`, present only when the drive environment is set, never in production), make the project's typecheck cover `.runcastle/scenarios/`, add base fixtures under `_fixtures/`, record the runner command in host settings, then write the scenario the human asked for. Once `.runcastle/scenarios/` exists, every scenario chat may edit only `.runcastle/`, like Fix drive. Whether the chat is in setup mode is decided once, at launch, from whether the path exists, and recorded on the session. Deciding it per edit would close the guard as soon as the agent creates the directory, before it writes the login route. If the first scenario is written during a feature drive, the setup lands on that feature branch and reaches `main` when it merges. Teaching `prepare` about scenarios is a later lap.
**Why:** Setup is proven the moment the human lands signed in, whereas a route `prepare` writes blind is not. Projects already prepared (runcastle, runcastle-demo) would never rerun `prepare`.

## 6. The login route exists only to carry the session into the browser
**Decision:** The scenario seeds the user like any other entity, and mints a one-time token for it. The route's only job is to turn that token into a signed-in browser through the app's own sign-in code, then redirect onward. An app without sign-in, or a scenario meant to land signed out, prints a plain `ENTRY_URL` and needs no route.
**Why:** Being signed in lives partly in the browser (a cookie or a localStorage token for the app's address), which neither a server-side command nor runcastle can write: the app runs in a cross-origin panel. Rejected: runcastle setting the cookie itself (cookies ignore ports, but it breaks for localStorage tokens, `__Host-`/`Secure` cookies and signed sessions, and depends on browser rules), and seeding a known password to type in (the blank-app chore again).

## 7. Scenarios are picked at start and switched inside a running drive
**Decision:** **Test drive** becomes a split button. The main click starts with the default: the feature's first own scenario, or Blank app when it has none. The arrow opens the picker: the feature's own scenarios, then the other scenarios grouped by group, then Blank app. A project drive lists every scenario with no "own" section, and defaults to Blank app. Inside a running drive, the drive panel carries a **Scenario** menu with the same list plus **＋ New scenario**. Picking one runs it against the live drive, with no restart, and points the panel at its `ENTRY_URL`. The panel names the scenario you are in. A scenario runs once the app answers (the moment **Open app** goes live), its output shows live, and the human lands when it prints `ENTRY_URL`.
**Why:** Drive setup is the slow part, and entities are unique per run, so switching scenarios inside one drive is nearly free: three states of a feature are checked in one drive. ＋ New scenario has to live inside the drive anyway, because it runs against the drive you are in. A start-only picker would cost a full restart to change scenario.

## 8. ＋ New scenario is a `scenario` session docked beside the drive, landing through runcastle
**Decision:** ＋ New scenario (and **Fix it**) launches a new session kind, `scenario`, in the drive's checkout, on feature drives and project drives alike. Its briefing carries the drive's identity and `drive.env` values, the runner command, the existing scenarios and fixtures, the human's description (or the failed file and its output), and setup mode when it applies (decision 5). The agent lands the human through one MCP tool, `run_scenario({ file })`, which runs the scenario through the same runner the picker uses and points the drive panel at its `ENTRY_URL`. A failure comes back to the agent as the same error the human would see. The agent commits before the final landing (decision 4). The chat docks beside the drive panel rather than in the Chat tab, and is still listed with the other sessions. One scenario chat per drive: while it is live, ＋ New scenario reopens it.
**Why:** "Proven on first use" must mean proven by the real path, not by the agent's own shell. Docking beside the drive keeps the "watch it land" moment the brief asks for. Switching to the Chat tab would hide the panel the result lands in.

## 9. Runcastle ships one dogfood scenario; the signed-in landing is proven on a real project with sign-in
**Decision:** Lap 1 ships `.runcastle/scenarios/review/feature-at-review.ts` in runcastle's own repo. It creates a fresh feature in runcastle-demo (unique per run, e.g. `scn_7f3a`) that sits at review with its tickets done, and lands the inner runcastle on that feature's page. Neither runcastle nor runcastle-demo (`shiplog`) has sign-in, so dogfooding proves the runner, picker, chat and landing but not the signed-in landing. That is proven on one of the human's own projects with sign-in, via ＋ New scenario in setup mode after merge, and the spec carries it as an explicit acceptance check.
**Why:** Review is the step runcastle drives test most often and today it costs a real burn to reach: the "hard to reach" state the brief means. The scenario also begins replacing the hand-written "open the feature at the step your change touches" paragraph in runcastle's drive instructions. Giving `shiplog` a fake sign-in only to test the route would be make-work.
