Every runcastle session is opened with a kickoff line (the per-kind briefing, e.g. "invoke /runcastle:ideate...") delivered by literally typing into the PTY after the session goes live: writeKickoffSequence in packages/server/src/launcher/sessions.ts writes the prompt bytes, waits 350ms, writes Enter; delivery is only *believed* when the line comes back through the UserPromptSubmit hook within 12s, else the input line is cleared and re-typed, up to 3 attempts, then session.kickoff_undelivered. This is fragile by construction — it races the TUI's startup redraw, depends on the hook pipeline being healthy just to know it worked, and on Codex the retry loop is the suspected cause of a visible cursor glitch (see the codex-hooks-never-fire quick change). The human has watched it fail: "doesn't always work reliably."

Both CLIs offer a native mechanism, verified against docs 2026-09-13:
- Claude Code: a positional initial prompt in interactive mode — `claude "…"` starts the REPL with that prompt already submitted. Runcastle already passes flags at spawn (--settings, --append-system-prompt-file), so the kickoff can ride the same argv.
- Codex: the interactive TUI accepts an initial prompt at launch (shared CLI options reference "the initial prompt", codex-rs/utils/cli/src/shared_options.rs), and separately `codex queue --thread <session-id> --message "…"` queues a prompt into an already-running session from outside — pin both against the live CLI via ctx7 /openai/codex.

Why this is a feature and not a quick change — the design questions its grill must resolve:
- Fresh launches are the easy case (kickoff known before spawn → argv). But resumed sessions (claude --resume / codex resume <id>) and resendKickoff — the "Send briefing" button, tRPC feature.resendKickoff — act on a session that is already open; do they keep the PTY path, or use codex queue where available, and what is the Claude analogue?
- The kickoff override machinery (setKickoffOverride is stashed BEFORE spawn precisely because delivery happened after go-live) can simplify once delivery moves to spawn time — decide how much of scheduleKickoff / KickoffDelivery / the confirmation loop survives as fallback vs. dies.
- What do session.kickoff / session.kickoff_undelivered events mean when delivery is an argv? The UI reads these.
- Argv length/quoting limits on Windows for long overrides (lap briefings with carried work can be long) — a file-based or queue-based path may be needed above some size.

What this must NOT swallow: hook enablement (the codex-hooks-never-fire quick change owns that; hooks stay load-bearing for live/Stop/edit-guard regardless of how the first message is delivered), and the approval_policy fix (its own card, already cut).
