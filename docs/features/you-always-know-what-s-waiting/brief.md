## Purpose
Pre-publish audit (project session, 2026-11-02). The human's words: "the user shouldn't have to look around … when he comes back to a feature" and "I don't want to come back the next day thinking the feature is done but finding out that the feature has been stalled". Today a returning human cannot tell what a feature needs, sometimes cannot even see the question, has to hunt for the action, and gets no ping when they are needed. This feature owns the whole "what needs me, and the button for it" surface: chat visibility of asks, the state words in the sidebar and header, the feature header's actions, and the pings.

## What the audit found (addresses are starting points — verify)
1. **Agent questions are invisible (two project notes).** The feature skill tells the lead to ask in words, then call `wait_for_you({ why })`, then end the turn (packages/skills/packs/runcastle/skills/feature/SKILL.md ~61-65, references/rounds.md ~76). The chat folds every assistant text that precedes a turn's last tool call into the "Worked for Xs" fold, closed by default (packages/core/src/thread.ts ~597-600 rule, ~654-678 implementation, ~384-385 settle; apps/web/src/components/chat/thread/Work.tsx ~196-215, narration small grey text inside the fold). So the human sees only "The feature is waiting on your answer to that question" with no question. Screenshots: /home/muath/.runcastle/project-notes/pnote_Ts5I6HBHYUqW.png and /home/muath/.runcastle/project-notes/pnote_2VZQMZPOm-Uw.png. Direction: words the agent puts to the human must never fold away (at least the narration before `wait_for_you` / ending in a question — `ENDS_ASKING` exists at thread.ts ~481; possibly: fold only tool calls and thoughts), plus a matching skill change (question is the last text; never "that question" / "my reply above"). The `wait_for_you` reason should also be visible in the chat itself, not only as a dot/sidebar mark (ThreadState.tsx ~20-24).
2. **State words don't say what's needed.** Sidebar row words (apps/web/src/components/…/SidebarParts.tsx ~75-96, `featureStateWords()`) and the header status line (lib/feature-ui/status-line.ts, five kinds) only say "Waiting on you" or the agent's free-text reason. A design to approve, a plan yes, an answer, a test drive and "ready to merge" all look alike; a feature ready to merge reads "In progress". The human wants each of those to be distinguishable at a glance. Check docs/features/waiting-is-not-backlog and go-waits-for-a-finished-plan-and-the-status-line-tells-the-truth decisions before redesigning — they are strict about the status line telling the truth.
3. **The header has no action for the state you're in.** In "waiting" there is no button at all; "Go" only lives on the Tickets view.
4. **Merge & ship is always behind the "⋯" menu (project note).** status-line.ts ~232-285 only promotes Merge when the next-step resolver offers it, and nothing in lib/feature-ui/next-step/ ever offers kind 'merge'. That contradicts design-mode decision 12 ("Merge stays in the header") — a regression. The human wants it easily accessible.
5. **New thread is hidden (project note).** The only desktop door is the hover-only "+" on a sidebar row (SidebarParts.tsx ~114, ~225-291, ~805); not in the feature page, not in the Ctrl+K palette (CommandPalette.tsx ~155-232 has no feature actions), no shortcut. The human asked for an easily reachable button and a keyboard shortcut. This revises threads-in-the-sidebar decision 4 (hover-only) — the human has said yes to that. Feature-scoped palette actions (New thread, Merge, Start test drive) belong here too.
6. **Nothing pings at the moments that matter.** Desktop notifications fire only on `run.finished` while a tab is hidden (apps/web/src/lib/notifications.ts ~100, use-notifications.ts) — and a succeeded round is the one moment the human isn't needed. Waiting-for-you, ready-to-test and merge-conflict never ping. Phone push only fires when an agent calls `notify_human` (and on held features only the orchestrator may). Direction from the audit: drop the round-finished ping, ping on waiting / ready / merge conflict. Whether runcastle itself should push to the phone on these (instead of relying on an agent choosing to) is an open question for this feature's grill — weigh it against the shipped agents-can-notify-your-phone decisions. A tab-title count ("(2) runcastle") is a cheap extra.
7. **Permission prompts stall silently.** When an ACP permission request arrives (packages/server/src/threads/host.ts ~1306, `openAsk` ~1357) it waits forever, with no push and no distinct state. The human's own rules (e.g. an "ask before git push" rule in their ~/.claude/settings.json) still prompt even in bypass mode, and they are deliberate, so prompts will keep happening sometimes. The want: a pending permission shows as its own "needs permission" state and pings, like any other wait. (Changing which session kinds run in bypass mode is NOT here — it is in the sibling small-fixes feature.)
8. **A round killed by a server restart wakes nobody.** workflows/reconcile-runs.ts ~80 marks it failed and emits `run.reconciled` but sets no waiting reason and sends no news line (orchestrator-notify.ts ~34-56), so an unattended feature just stops. Direction: treat it like a round ending — the feature shows it was interrupted and whoever is responsible hears.
