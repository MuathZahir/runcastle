# Go waits for a finished plan, and the status line tells the truth

## Ticket 1

Plan it yourself must show that it is running. Observed 2026-10-19 on a freshly started feature: clicking Plan it yourself (the "⋯" menu on the planning status row) launched a headless self-planning chat session (events `session.launching` 'launching a self-planning run' then `session.started`) that worked for about 2.5 minutes, but the feature page showed nothing, and the human concluded the click did nothing and pressed Go. While a self-planning run is live, the status line must say so (e.g. "Planning by itself"), offer its Stop, and the row must not look idle. Find where `featureStatus` (`apps/web/src/lib/feature-ui/status-line.ts`) and `leadActions` decide the planning row, and feed them the live headless self-plan session. Cover it with a status-line unit test and a tier-2 component test of the row.

## Ticket 2

Go must only follow a finished plan. Today `primaryOf` in `apps/web/src/lib/feature-ui/status-line.ts` returns 'go' whenever `feature.phase === 'planning'`, and `leadActions` builds an ENABLED Go even when the resolver offered no burn action. The server's `go()` (`packages/server/src/services/features.ts`) only warns 'no spec.md on disk'. So on 2026-10-19 the human pressed Go on a feature with no spec, no decisions and no tickets, while its self-planning run was still writing the plan. Change: (1) while a self-planning run is live for the feature, Go is refused, disabled with the reason in the UI and a GateError in `go()`, because Go would cut planning short; (2) before the tickets step is complete for this lap (`ticketsReadyLap !== lap`, the same arming `PLAN_READY` reads), Go is a gated action: disabled with the reason, overridable with a one-line reason recorded in history, as charter decision 8 does for every gate. A finished plan with zero tickets stays valid (`the-feature-lead-runs-rounds` decision 5: the lead may build a small feature itself); the gate is on the plan being finished, not on the ticket count. Tests: status-line units, a `go()` service test for both refusals, and the override path.

## Ticket 3

Go given while self-planning must never hand a planless feature to the lead. Observed 2026-10-19 (feature since deleted; the transcript survives at `~/.claude/projects/C--Users-user--runcastle-worktrees-proj-u3T1Bff2-S2D-the-map-shows-every-page-and-its-states/1a978196-0b64-4954-aaae-eb7deeaf381b.jsonl`). The timeline: 14:14:41 the self-plan session started; 14:16:48 `feature.go`, then `lead.message_pending` ('waiting for the agent's run to end'); 14:17:19 the self-plan session ended with 'session ended by user' plus `session.self_plan_ended` 'planning stopped before the plan was complete'; 14:17:23 `lead.woken_headless` resumed the same conversation headless with the Go text; that session loaded the `runcastle:lead` skill at 14:17:30 and ended at 14:17:31, again 'session ended by user' (`pty/end-session.ts`), exit code 1. Find what called `endSession` both times: the human says they only clicked Plan it yourself and Go. Candidates include the web's `feature.endSession` callers (`Workspace.tsx` `endLiveSession`, the `stopSelfPlan` action, `use-project-talk`, `use-resolve-conflict`) and `orchestrator-tools.ts`. Then fix it so an unrequested end cannot happen. With ticket 2's refusal in place, Go can no longer arrive mid-plan, but if a headless lead wake fails or exits immediately, record why (`lead.wake_failed` with the exit code and the transcript's last lines) instead of leaving it silent.

## Ticket 4

The status line must not say Working when nothing is working. `statusOf` in `apps/web/src/lib/feature-ui/status-line.ts` ends with a fallback that returns 'Working · Round N' whenever no other case matched: 'the agent is between rounds, or Go was just given and round 1 is not out yet'. On 2026-10-19 the lead's session had died and no round existed, yet the feature read 'Working · Round 1' indefinitely. Working must require evidence: a running round, or the lead's session live and mid-turn (`agentWorking`), or a lead wake pending for less than a short grace period. Otherwise show 'Waiting for you · the agent stopped' (or the wake failure from ticket 3) with the Chat door to resume it. Update the precedence doc comment and the status-line unit tests, adding the case 'Go given, no round, no live lead'.
