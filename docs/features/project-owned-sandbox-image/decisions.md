# Decisions — project-owned-sandbox-image

## 1. One lap, whole feature, no map
**Decision:** Spec all four strands together in one lap: project Dockerfile detect/build/tag, Rebuild-image clobber fix, content-hash staleness, and toolchain preflight. No waypoint map, no deferred `## Later laps` scope.
**Why:** The strands share the same seams (image tag, hash label, doctor probe, build path) — slicing any one out would leave the others half-coherent, and the incident diagnosis already settled the shape of three of the four.

## 2. Detection is the contract; prep-authoring is one client of it
**Decision:** The core mechanism is authorship-agnostic: runcastle detects `.runcastle/sandbox/Dockerfile`, builds it as the project image, and sets the project's sandbox image itself — whether a human or the prep agent wrote the file. On top of that, this lap also teaches the prepare skill to author the Dockerfile when it probes a non-JS toolchain (pom.xml → JDK+Maven, build.gradle → Gradle, pyproject → Python, go.mod → Go, …), `FROM` the stock image.
**Why:** A hand-written Dockerfile must be first-class with no prep session at all — that keeps the contract simple. But detect-only would leave the incident's actual pain (hand-rolling the file) unfixed, and prep-authoring is cheap: prompt content on the prepare skill, whose write hook already permits exactly `.runcastle/`; it mirrors how prep authors drive machinery today.

## 3. sandboxImage gets a project column; project beats global
**Decision:** Add a `sandboxImage` project column on the `setupCommand` descriptor precedent (project column + existing global config twin + `RUNCASTLE_SANDBOX_IMAGE` env). Resolution order: project column → env var → global config → stock default. Runcastle writes the project column itself when it detects `.runcastle/sandbox/Dockerfile` and builds `sandcastle:runcastle-<projectId>`; a human-typed value keeps `userSupplied` provenance and is never overwritten by detection (the existing overwritability rule).
**Why:** A stored value keeps the five image consumers (build, doctor, precheck, burn, slot stamp) agreeing through one resolver instead of re-probing worktree state per call. Project-over-global is right because the file in the repo is the most specific intent — noted as a behavior change for anyone relying on a custom global image today.

## 4. Runcastle owns the build; hash rides a --label; doctor compares label vs file hash
**Decision:** Retire the `sandcastle build-image` shell-out. Runcastle invokes `<runtime> build` directly for both images, passing `--label runcastle.dockerfile-hash=<sha256 of the Dockerfile>` (and the existing `AGENT_UID`/`AGENT_GID` build-args). Stock image: same refreshed `~/.runcastle/sandbox-build/` context, tag `sandcastle:runcastle`, same watchable terminal flow. Project image: context `.runcastle/sandbox/` in the repo, tag `sandcastle:runcastle-<projectId>`, `FROM sandcastle:runcastle` — the build path ensures the stock image exists and is fresh first (two-step build when needed). Doctor staleness becomes label-hash vs current-file-hash for both images, replacing mtime-vs-Created outright.
**Why:** Sandcastle's build CLI takes only `--image-name` (no label/build-arg passthrough), its `run()` never builds, and baking a LABEL into the Dockerfile is self-referential. Owning the build costs nothing (the wrapper adds nothing we don't replicate) and avoids growing the permanent sandcastle patch (ADR-0011) for something runcastle can do itself.

## 5. Build button builds the resolved chain; hand-typed custom tags disarm it; staleness checks both hashes
**Decision:** The AFK card button builds what the project resolves to: no project Dockerfile → stock build; project Dockerfile present → two-step chain build (stock if stale/missing, then project image). If `sandboxImage` is `userSupplied` (a human-typed tag with no runcastle-managed Dockerfile behind it), the button disarms: the row says the image is custom and managed outside runcastle, fix text pointing at clearing the setting or adopting `.runcastle/sandbox/Dockerfile`. The staleness probe for a project image checks both its own Dockerfile hash and the stock base's hash label, and names which layer is stale; one Rebuild heals the chain.
**Why:** Building the resolved chain is the clobber fix restated positively — the button can never build stock content under a custom tag. Provenance we already store distinguishes runcastle-managed from hand-typed, so disarming needs no new state. Base-hash checking closes the silent hole where a runcastle upgrade changes the stock Dockerfile and every project image FROM it stays "fresh" by its own label.

## 6. Detect in the doctor; write the column on successful build; burns never auto-build
**Decision:** Detection of `.runcastle/sandbox/Dockerfile` lives in the doctor's image probe, which gains a "project image not built yet" state whose fix is the same Build button. The `sandboxImage` project column is written only on successful build — until then burns resolve to the previous image (stock or global). Burns never auto-build: the existing per-run probe aborts fatally with a message pointing at the button. A post-build Dockerfile edit surfaces only as the doctor's stale state (hash mismatch → Rebuild); no re-prepare nudge — a Dockerfile change is an image concern, not a preparation concern.
**Why:** The doctor already drives the AFK card, so a hand-written or prep-written file surfaces with no extra wiring. Writing the column at detect time would point five consumers at a tag that doesn't exist yet (sandcastle's run() hard-fails on missing images); stale-but-working beats broken. Image building stays a human-watched terminal action.

## 7. Toolchain preflight extends the per-run probe; 127 on setup goes fatal; extraction is a heuristic
**Decision:** Extend the existing per-run image probe in `burnRun` into a toolchain preflight: collect distinct command names from the setup command and each verify command, check them in one container run (`--entrypoint sh … -c 'command -v …'`) alongside the agent-binary check, memoized on (image, commands). Any missing aborts the run fatally: "`mvn` is not installed in image `X` — add it to `.runcastle/sandbox/Dockerfile` and rebuild." Command-name extraction is a modest heuristic (split on `&&`/`;`/`|`, first word per segment, skip `VAR=` prefixes and shell builtins), not a shell parser — a false miss just defers to the classifier. Backstop: `classifyTicketRunError`'s 127 handling extends to setup-hook failures — fatal with the named-command message when extractable, and never matching the retryable pattern. Out of scope: the pre-existing mixed-runtime preflight gap.
**Why:** The probe site, memoization, and fatal-abort plumbing already exist — this widens what is probed, not how. Retrying an exit-127 can never succeed; the incident's worst behavior was exactly that retry. A heuristic extractor is wrong-but-harmless where a parser would be complexity spent on exotic commands.

## 8. Deleting the Dockerfile auto-clears the project column
**Decision:** When the doctor's probe sees the `sandboxImage` project column set (machine provenance) but `.runcastle/sandbox/Dockerfile` gone, runcastle clears the column itself; resolution falls back to global/stock on the next burn. The orphaned local image tag is left for the user to prune. Corollary of decisions 2+6: prep writes the Dockerfile but never builds — its ending guidance points the human at the Build button.
**Why:** Runcastle wrote the value on build, so removing it when its justification disappears is symmetric; a doctor warning asking the human to clear it would nag about something with exactly one sensible resolution. A hand-typed (`userSupplied`) value is never touched, consistent with decision 3.

## Lap 2 (revisited 2026-09-10)

Lap 1 landed whole; the test drive surfaced nothing new. Lap 2 closes the two review findings that were still open after the lap-1 fix tickets: one behavioral defect from the verification pass and one cohesion observation. ## 9. A blank stored `sandboxImage` is unset everywhere — normalized inside the `unmanagedImage` seam
**Decision:** `unmanagedImage` (the shared guard lap-1 ticket #8 introduced) trims the stored project value and treats an empty result as unset, before any custom-tag reasoning. With `stored: '  '` and a project Dockerfile present, the doctor takes the project-image branch and `planImageBuild` returns the chain — matching burn resolution, where `resolveSandboxImage` already trims (lap-1 ticket #7). The normalization lives inside the shared seam, not at its call sites. Corrects done work from ticket #8 (finding `finding_bQdNMvQbt-rd`).
**Why:** Tickets #7 and #8 each normalized on their own side and disagreed: burns read a whitespace column as unset while the card/build path read it as a hand-typed custom image — the exact card-vs-burn divergence this feature exists to eliminate. One seam owning the normalization means the question "is this a user-managed image?" has one answer everywhere.

## 10. Image mechanics and project persistence split into separate modules
**Decision:** `sandbox-image.ts` keeps only the pure image mechanics — `hashDockerfile`, `inspectBuiltImage`, `planImageBuild`, `imageBuildTerminal` — and the persistence pair `adoptProjectImage`/`releaseProjectImage` (DB writes + `settings.updated` emission) moves out beside the other stateful services. The doctor imports only the mechanics module. Closes finding `finding_a9XxnwnZ5smC`.
**Why:** The review flagged the Divergent Change smell: one module changing for build-planning reasons and for persistence/SSE reasons, with the doctor inheriting the persistence dependency graph it never uses. Splitting is cheap now and keeps the doctor's import surface honest.
