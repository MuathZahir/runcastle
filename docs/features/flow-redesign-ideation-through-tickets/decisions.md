# Decisions — Flow redesign: ideation through tickets

## 1. The as-is flow map is confirmed; the goals are "never stuck" and a visible model choice
**Decision:** `flow-map.md` (walked 2026-09-03) is the confirmed baseline for this redesign. Its 13 numbered dead ends are the fix list the design must answer. Two goals frame every decision that follows: (1) the flow from a feature card to the Burn click must be streamlined enough to make sense to a user who has never read the docs, with **no state in which the user has no correct next action** — every state names one door; (2) the model that will run each ticket must be choosable **in the UI**, not only by asking the agent. The project-shell flow's landed decisions (read-only gate card with the override UI deleted, gate explainer behind ⓘ, gate codes demoted, the vocabulary-tooltip copy policy, the 8/16/24/32 spacing rhythm, 300px resizable rails, real URLs with the phase pin outside them) are inputs this flow builds on, not questions it reopens.
**Why:** The human confirmed the map without corrections and stated the two goals directly. The per-ticket model select already exists inside the ticket editor (`Edit ticket` → MODEL), but the human did not know it was there — so the second goal is a placement/discoverability requirement on the ledger, not a new capability. Re-deciding what the shell flow settled would collide with a feature that lands before this one.

## 2. One lap, whole flow, no map
**Decision:** Spec the entire flow in one lap: the next-step bar's ideation/spec/tickets resolvers, the grill body (unmapped and mapped, rail and waypoint cards, session panel states), the spec doc surface, the tickets ledger with the visible model choice, the read-only retrospective views of these phases, the lap-aware fixes in these phases, this surface's `styles.css` migration, tests and the code-shape pass. Not mapped. Server changes are limited to honesty fixes the UI needs (lap-scoped counts, wiring existing endpoints such as `ticket.cancel`); gate/phase semantics stay as ADR-0001/0010 and the charter set them. An HTML prototype is produced at the end of ideation for the human to approve before spec, as the prior flows did.
**Why:** Every branch is settled territory with nothing to research or prototype before decisions can lock, so it is neither map-sized nor uncertain enough for a thin lap. The rail and the bar share one layout and one vocabulary; a lap that redesigned the unmapped path first would design the same column twice.

## 3. The next-step bar is the single door for session actions
**Decision:** In ideation, spec and tickets, every session action — start, resume, resume converge, converge, override-and-converge, burn — lives only in the next-step bar. The body never repeats one: the ended-session card loses its `Resume session` button and becomes a quiet status line (when it ended, that decisions were captured); the in-body `Resume converge` bar is deleted and the converge-stranded spec state becomes a bar state (*The converge session ended before tickets were emitted* → **Resume converge**). Because the shell flow deletes the Inspector's override form, the bar's description is the one place that says, in plain words, why the feature cannot advance (the gate reason). Live-session states stay status-only (next-step-bar-affordance-audit decision 1). The body keeps what only it can show: the terminal, the map, the spec, the tickets.
**Why:** One terminal per feature means exactly one correct launch at any moment, and the bar is already where the eye goes for "what now". The duplicate doors (bar `Resume grill` beside the card's `Resume session`; three differently named doors on a converge-stranded spec — flow-map dead ends 1 and 2) are the confusion the human flagged. Rejected: keeping a resume button on the ended card because it sits next to the transcript — the eye travel to the bar is trivial and the duplication is not.

## 4. On an open map, the bar's solid action is `Work next` — a short button, the title in the description
**Decision:** Mapped ideation with open waypoints gets a solid action: **Work next**, targeting the lowest-`seq` frontier waypoint (the rule the done-strip already uses). The button label is fixed and short — never the waypoint title, which is often a sentence; the title goes in the bar's description together with the orientation line ("3 of 10 waypoints done · 2 ready to work — next: *{title}* · pick any of them in the map"). The button keeps the primitive's full padding and does not shrink or truncate to fit content. Sub-states: frontier empty with a research run in flight → status-only *Waiting on N research run(s)*; a live session → status-only, as now; all waypoints terminal → **Converge**. `Override & converge…` stays a ghost in the open state; the fog line folds into the description rather than a separate flagged row. The rail's done-strip loses its own `Work next` button (decision 3) and only reports *Resolved ✓ — {summary}*.
**Why:** Flow-map dead end 5: the one state that needs guidance most had no solid action and left the bar contradicting its own contract. Lowest-seq is charting order — the closest thing to authored intent — so "keep clicking the green button" becomes a valid way to work a whole map, while the rail stays the place to choose differently. The human asked specifically that the button not try to fit the title: it must look good with proper padding, so the label is fixed and the title lives in prose.

## 5. The map rail is a progress checklist, renders only during ideation, and opens up in retrospectives
**Decision:** The rail header reads `MAP · 3/10 done` with a thin progress strip. Groups keep today's order (ready → working → waiting → done), but each waypoint card leads with a plain-word state chip — *Ready*, *Working* (pulsing), *Waiting on "{blocker title}"* (names the blocker), *Done* — with the waypoint type (`research`, `grilling`, `prototype`, `task`) demoted to dim mono beside it. The collapsed strip shows `3/10` and a caret; the `0 FRONTIER` stub is deleted. The rail renders **only while the feature is at ideation**: at spec and later the map has retired (ADR-0001 §9) and `map.md` stays reachable from Knowledge. In a pinned read-only ideation view of a mapped feature, the done group renders **open**, each card showing its resolution summary. Frontier cards keep `Work` / `Resume` — the one deliberate exception to decision 3, because choosing a different waypoint than the bar's suggestion is a choice only the rail can offer — and those buttons are hidden while the view is pinned.
**Why:** The map's job is to answer "where am I and what is left"; today it answers with groups named after internal states and an empty rail beside the spec (flow-map dead ends 8, 10, 13). Progress, plain state words and the blocker's name give a newcomer the whole shape at a glance; opening the done group in retrospectives makes the map the record of how the idea was worked instead of two closed disclosures.

## 6. At tickets the terminal is a collapsible strip: open while emitting, collapsed once tickets exist
**Decision:** The tickets body is a vertical stack whose top row is the session strip. With zero tickets and a live session the panel is open at full body height — the terminal is the hero, as at ideation. Once tickets exist it starts collapsed to its one-line strip (`{kind} · live · N tickets emitted · Show terminal`), the ledger takes the body, and expanding gives the terminal the full height again with the ledger scrolling beneath; the open/collapsed choice is remembered per feature until the session ends. The ended-session state is the same strip, quiet (decision 3). No drag-to-resize divider. The `100dvh − 420px` height guess and its rule are deleted.
**Why:** With cards on screen the human's job is reviewing tickets and clicking Burn — the terminal is context, not the work — yet it must never be more than one click away because the agent may still be talking or need to be asked to change a ticket (flow-map dead end 12). A side-by-side split would squeeze the ledger's titles, dependency chips, model chips and status into half the width, which are exactly what is being read. Drag handles were already rejected as disproportionate for the rail.

## 7. The ticket's model is a menu on the row, with a bulk "for all pending"; Cancel ticket joins Edit
**Decision:** On every pending or failed row, the model chip becomes a small inline menu in the row head — `default (project model) ▾` or `{model} · {runtime} ▾` — listing the configured roster grouped by runtime and saving on change through the existing `ticket.edit({ model })` partial patch (toast on failure). Burning, done and cancelled rows show the chip static. Beside the ledger's `sandbox · {mode}` and default-model chips sits a **`Model for all pending ▾`** menu that applies one choice to every pending ticket in the current lap (one edit per ticket). The in-place editor keeps title, goal, context and acceptance only. The expanded row's actions are **Edit ticket** and **Cancel ticket** (inline confirm — *Cancel #4? Tickets that depend on it treat it as done.* — wired to the existing `ticket.cancel`; cancelled rows stay in the ledger, dim); both apply to pending/failed rows only and are hidden while the view is pinned.
**Why:** Decision 1's second goal: the human wants to choose the model per ticket in the UI and did not know the editor's MODEL select existed — it was two clicks deep inside a text form. The model is the one property decided per ticket at a glance, comparing rows, so it belongs on the row; the bulk menu covers the common case ("all of these on Opus") without ten dropdowns. `ticket.cancel` exists on the wire with no web caller (flow-map dead end 7). Rejected: per-row radio-style model chips — too loud for a ledger where most rows sit on the default.

## 8. No gate-skipping verbs in the bar: `Promote`, `Approve` and `Override & converge…` are removed
**Decision:** The bar in ideation, spec and tickets offers exactly four kinds of solid action — start/resume a session (grill, lap, converge), **Work next**, **Converge**, **Burn** — and nothing that crosses a gate by hand. The ghost `Promote to spec` and `Approve spec → tickets` secondaries (both `feature.advance`) are deleted, as is the mapped ideation's `Override & converge…` with its inline reason form. The `⚑ Fog remains …` line survives as description only. Server procedures (`feature.advance`, `feature.converge { overrideReason }`, `overrideGate`) are untouched; their removal is deferred cleanup alongside the shell flow's deferral of `overrideGate`/`undoGateOverride`.
**Why:** The agent crosses G1 and G2 itself, and every state in which a human might reach for a promote verb already has a session door — a fresh session on a feature whose docs exist simply calls `complete_phase`. The human has never clicked them, nor any gate override. On a map with open waypoints the honest exit is to tell any session to drop the rest: `resolve_waypoint` records why each was abandoned and the ordinary `Converge` appears, whereas an override skips that record for a one-line reason. Removing all three makes the bar's contract simple enough to state in one sentence and removes the last door into a phase whose artifact does not exist.

## 9. Lap-aware in three pieces: lap before map, mapped G1 lap-scoped, every count per lap
**Decision:** (1) The ideation resolver tests `lap ≥ 2` before `mapped`: on a later lap with no lap-N session the bar reads *Work lap N* → **Start lap N session** regardless of the map; once that session exists and has (re)charted waypoints, the map branches (decision 4) apply. (2) The server's mapped G1 check (`all-waypoints-terminal`) gains the rule the doc gates already apply from lap 2 — a lap-N ideation/revisit/converge session must exist — with a reason of the same shape (*the map is an earlier lap's — open the lap's session before converging*). (3) Every ticket count in the bar and the ledger header is the current lap's: `Burn N tickets` counts what `feature.burn` will burn; the *Emitting* / *Waiting for tickets* states look at this lap only; earlier laps' tickets still render under their collapsed `Lap N` headers.
**Why:** Flow-map dead ends 3 and 4: a mapped feature on lap 2 is told to `Converge` at once, and a lap-2 feature with no new tickets shows a solid `Burn 11 tickets` the server refuses. Both are audit finding F4 in a different coat. Piece 2 is consistency with the existing lap rule, not a new gate semantic; laps stay a counter plus tags (ADR-0010 §8).

## 10. A pinned phase is a frozen record: the docs inline, no live session, no actions
**Decision:** The read-only banner carries a one-line summary of the pinned phase derived from the events feed and docs — `Ideation · 2 days · 3 sessions · 12 decisions`, `Spec · written 2d ago`, `Tickets · 11 emitted, 11 done`. Pinned **ideation** renders `decisions.md` inline as its main content, the map open per decision 5 when mapped, and a quiet list of the sessions that ran (kind · started · duration). Pinned **spec** renders `spec.md` inline in full. Pinned **tickets** shows the ledger with lap headers and no session strip. No terminal, `End session`, `Work`, `Edit` or `Cancel` anywhere in a pinned view — the live session appears only in the current phase. Empty cases state what happened, not what to do (*No spec — this feature was created as a quick change and skipped ideation.*). A read-only transcript viewer for feature sessions goes to `## Later laps`.
**Why:** Flow-map dead ends 6, 11 and 13: a pinned view today is the live view with two buttons hidden, so a shipped feature's ideation shows whatever session happens to be running, empty states point at a bar that is not there, and the record — decisions, spec, tickets — is only reachable through the Knowledge list. The docs already exist on disk; putting them in the body is the honest reading of "click a done step", and the banner summary keeps the shell's current-gate card from reading as a contradiction.

## 11. Every live phase body is the artifact on the left, the terminal on the right
**Decision:** The two-pane shape the mapped ideation already has becomes the shape of all three live bodies. Left pane, by phase: mapped ideation → the map rail (decision 5); unmapped ideation → `decisions.md` rendered as it accrues, headed *Decisions so far · N*; spec → `spec.md` rendered in full and live-refreshing as the session writes it (empty: *The session is drafting the spec — it appears here as it's written.*). Right pane: the terminal, full height. The artifact pane reuses the rail's chrome (collapsible to a strip, choice persisted globally like the map rail) but is wider — on the order of 380px, tuned in the prototype — because it holds prose. The one-line spec doc card and its `View ›` are deleted; `DocPeek` stays for the Inspector's Knowledge list. Tickets keeps decision 6's vertical stack, since its artifact is the ledger itself.
**Why:** The human's standing wish is that an ideation session be followable without reading terminal scrollback; the map gave that to mapped features and nothing gave it to the ordinary grill or the spec, whose bar copy ("the spec takes shape beside the conversation") promised it. One recognisable layout across the phases is simpler to learn than three. Rejected: a "spec written ✓" chip beside the terminal — it says the file exists, not what it says.

## 12. Vocabulary: keep Burn, Converge, waypoint and lap as names; retire grill, frontier, fog, promote; `Revisit` becomes `Ask for changes`
**Decision:** Under the shell flow's copy policy, four insider nouns survive in this flow as established names, each with a tooltip sourced from `lib/vocabulary.ts`: **Burn**, **Converge** ("Turn the finished map into a spec and tickets in one session"), **waypoint** (glossed once, on the rail header's ⓘ) and **lap**. Retired: "grill" everywhere — buttons read `Start session` / `Resume session`, the kicker `GRILL LIVE` becomes `SESSION LIVE`, descriptions say "the ideation session" (the strip chip still shows the session kind); "frontier" → *ready* (decision 5); "fog" → *Still unspecified: …*; "promote"/"approve" are gone with decision 8. The tickets-phase ghost `Revisit` becomes **Ask for changes**, with a description ("Open a session to change the tickets before burning"). "briefing" stays — it is plain English. `GRILL_EXPLAINER` and any vocabulary entry with no remaining caller are deleted.
**Why:** "Grill" is the word a newcomer meets on every button in this flow and it names nothing the phase name *ideation* does not already name; the stepper and the button should agree. Converge and waypoint earn their place because nothing plainer names them as shortly. Audit finding F16 residue.

## 13. The session strip says what and whether; stepper tooltips teach the pipeline
**Decision:** The strip reads `{Kind} session · ● live · 14 min` (kind in plain words: Ideation, Converge, Lap 2, Waypoint), the short session id demoted to a tooltip, **End session** a ghost with no confirm (recoverable — the conversation stays on disk). Launching: `● starting…`, then the existing 30-second *agent hasn't checked in yet* hint and the briefing banner with **Send briefing**, unchanged. Ended: `{Kind} session · ended 2h ago` and nothing else — the door is the bar (decision 3). The stepper keeps the shell's chrome; what each step offers changes: a done step's tooltip is that phase's decision-10 summary (`Ideation · 3 sessions · 12 decisions — click to review`), the current step's tooltip says what the phase is for in the new vocabulary (`Shape the idea with the agent in a session`), an upcoming step's says what unlocks it (`Opens when the spec is written`). The `Lap N` chip and the header phase tag are unchanged.
**Why:** The strip's job is "which conversation is this and is it alive"; the raw kind word and the id do not help a human answer it. Tooltips on the stepper are the cheapest place to teach the pipeline without a standing paragraph anywhere — the same help-on-demand policy the settings and shell flows locked.

## 14. Code shape, tests and the `styles.css` cut
**Decision:** `GrillBody.tsx` splits into `components/bodies/grill/` (`GrillBody`, `ArtifactPane`, `MapRail`, `WaypointCard`); `TicketsBody.tsx` into `components/bodies/tickets/` (`TicketsBody`, `TicketLedger`, `TicketRow`, `TicketEditor`, and a `ModelMenu` shared by the row and the bulk control); `SessionPanel.tsx` into the strip and the panel. Derivations are pure modules in `lib/feature-ui/` with tier-1 tests: the rewritten ideation/spec/tickets resolvers, the pinned-phase summary (events + docs), lap-scoped counts, map progress. Tier-2 DOM tests cover the collapsible strip, the model menu and the editor. Smells removed: `ns.warning`/`ns.fog` merge into one field; the kind-blind `hasResumable` call is scoped; `MAP_SECTIONS` imports from core; the `as SettingsView` casts get a typed query. Every `styles.css` rule this surface owns (lines 839–1736 at charting: stepper, bar, read-only banner, lap banner, body split, rail, waypoint cards, terminal pane and strip, doc card, ledger, editor) is migrated to utilities and deleted with the ratchet constant lowered, together with the dead selectors (`.spec-doc*`, `.grill-empty`, `.wp-resume`, `.lg-commits`, `.gate-hint`, `.is-skipped`); the Inspector gate-card block stays with the shell flow. `Workspace.tsx` changes are confined to the phase-body dispatch and the action switch. Server changes are only decisions 7 and 9.
**Why:** The pattern three flows have already used, and the collision rule: flow 7 lands after this one and edits `RunBody`/`ReviewBody`, so this flow touches its own surface's files and nothing shared beyond the dispatch.

## 15. The Details panel is hidden by default in these phases; Knowledge folds into the artifact pane's docs menu
**Decision:** In ideation, spec and tickets the Inspector (Current gate · Knowledge · Activity) starts **collapsed**: this flow changes only the initial default for these three phases (one constant beside the shell's persisted `inspectorCollapsed` preference); once the human toggles it, their choice wins everywhere, and nothing auto-hides or auto-opens it afterwards. To make the panel unnecessary rather than merely hidden, the Knowledge list becomes a small docs menu in the artifact pane's header (`decisions.md ▾ · brief · map · spec`) that swaps what the pane renders; at tickets, where there is no pane, the same menu sits in the ledger header. The gate card is redundant in these phases because the bar's description states the gate's reason (decision 3); Activity stays in the panel, one titlebar toggle away. The Inspector itself is not removed — it is the shell flow's surface and build/review depend on it.
**Why:** With the artifact pane (decision 11) beside the terminal and both 300px rails open, a 1440px viewport leaves the terminal about 400px wide; a Claude Code terminal wants roughly 700px. The human asked whether the panel is needed at all in these phases and identified Knowledge as its only semi-important content here. Rejected: deleting the Inspector (not ours; flow 7 needs it) and shrinking the pane (380px is the floor for reading prose).

## 16. Prototype approved — the visual reference for spec and tickets
**Decision:** `docs/features/flow-redesign-ideation-through-tickets/prototype.html` (published as an artifact, twelve states: ideation live / ended / never started / mapped open / mapped done / lap 2; spec live / converge ended early; tickets emitting / ready to burn; pinned ideation of a shipped map / pinned tickets of a shipped lap-2 feature) is the approved visual reference. Where the prototype and these decisions disagree, the decisions win; the prototype's terminal is fake text and its docs menus are static. Pane widths at approval: artifact pane 380px, map rail 300px, Details panel hidden by default.
**Why:** The human reviewed the interactive prototype and approved it on 2026-09-04 after one change (decision 15).
