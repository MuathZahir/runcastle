# Review reads project verify commands and explains a failed browser check

## Ticket 1

Review tickets claim "this project has no verify commands configured" on every project, even ones with verifyCommands set. Cause: packages/server/src/workflows/review-ticket.ts (~line 644) renders `GATE_NOTES: buildGateNotes(deps.config)` from the raw GLOBAL RuncastleConfig, while implementation tickets layer the project's own settings over global via `resolvePreparedSettings(deps.config, ctx.project)` (packages/core/src/config.ts ~line 456; used at ticket-burner.ts ~line 4407 for VERIFY_NOTES). Verify commands and known failures are normally stored on the project row, so the review never sees them and Gates mode degrades to a diff read. Fix: build the review's gate notes from `resolvePreparedSettings(deps.config, project)` (verifyCommands + knownFailures), exactly as the burner does. Test: a project with its own verifyCommands/knownFailures and an empty global config renders those commands in GATE_NOTES; a project with none falls back to global; neither set still renders the 'no verify commands' line.

## Ticket 2

The review's browser health check fails with no recorded cause. `executableIsHealthy` (packages/server/src/workflows/review-ticket.ts ~line 115) runs `spawnSync(path, ['--version'], { timeout: 3_000, stdio: 'ignore' })` and returns only a boolean, so the withheld-drive reason reads just "`agent-browser` is on PATH but failed its health check". Observed: on the owner's Windows machine the long-running server (started 2026-09-25) withholds the drive on every review since ~2026-09-25 21:00 (right after a full-disk episode), while the identical probe run from any fresh Bun process (console, hidden, detached) returns status 0 in ~30ms. The cause cannot be diagnosed because status/signal/error/elapsed are discarded. Fix: (1) make the health check return a structured result (ok, status, signal, error message, elapsed ms, resolved path) and fold a short form of the failure into the recorded driveWithheldReason and the DRIVE_AVAILABILITY prose, e.g. "failed its health check (C:\\...\\agent-browser.CMD --version: ETIMEDOUT after 3001ms)"; also console.error it server-side. (2) Retry the probe once before withholding the drive, so a single slow spawn under load does not cost a whole review its Drive mode. Keep the probe cheap (no shell, same 3s timeout per attempt). Tests: unit-test the reason text for non-zero exit, spawn error, and timeout; a first-attempt failure followed by success yields an available drive.
