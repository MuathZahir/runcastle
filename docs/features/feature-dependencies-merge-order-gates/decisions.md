# Decisions — Feature dependencies (merge-order gates)

## 1. Only drafts carry dependencies; the gate is the Start click
**Decision:** A dependency is an edge from a **draft** (the dependent) to another feature (the dependency — draft, active, or any not-yet-merged feature). The only thing it gates is **Start**: `startDraft` refuses while any dependency is unmerged. Once a draft starts, its dependencies are inert — kept as history, gating nothing. Burn, ideation and session launches on a started feature are never gated by dependencies.
**Why:** The operator's framing is about drafts ("must merge before the user can work on the dependent one"), and a draft can't be worked on until it starts, so Start is the whole gate. Gating a started feature would mean refusing Burn or launches mid-flight — rebuilding the retired gate machinery and its overrides. After Start, ordering is a present-tense collision, not a future promise.

## 2. "Merged" means the dependency's phase is shipped — derived, never stored
**Decision:** A dependency is **satisfied** iff the dependency feature's `phase === 'shipped'`, computed at read time by one predicate. No satisfied flag, timestamp or event is stored. `phase`, not `status`: a shipped-then-archived feature (`status='archived'`, `phase='shipped'`) still counts as merged.
**Why:** One derived predicate means no state to keep in sync. Today any Merge click ships; when forks land, decision 25 of `feature-grouping-forking-and-referencing` narrows "shipped" to "merged into main", and this predicate inherits that for free — which is the correct meaning, since the dependent is cut from main at Start and work merged only into a parent's branch is not there yet.

## 3. Archived dependencies keep blocking; deleted ones cascade away; no override anywhere
**Decision:** An **archived, unmerged** dependency still blocks Start. The refusal names it as archived and points at removing the edge; unarchiving restores the normal flow untouched. A **deleted** dependency cascades its edges away in both directions, and the delete records an event on each affected dependent's timeline ("dependency `<slug>` deleted"). There is **no gate override** — the only lever is editing the dependency set.
**Why:** Archiving A says nothing certain about whether B's premise still holds (B may need to absorb A's work, or be moot) — only the human knows, so the edge must not drop silently. Deletion means the feature no longer exists, so there is nothing to wait on; the event keeps the silent unblock visible. Editing the set as the sole lever avoids resurrecting the retired gate-override machinery.

## 4. The human edits the set in the draft's workspace — one replace-the-set call
**Decision:** The draft workspace gains a **"Waits on"** row under the Parked header: one chip per dependency (title + state, e.g. `building`, `archived`) with ✕ to remove, plus **+ Add** opening a picker of the project's unmerged features. A satisfied dependency renders "✓ merged" with no ✕. On a started feature the row is read-only history ("Waited on: …"). The wire is one tRPC procedure, `feature.setDependencies({ featureId, dependsOn })`, which replaces the whole set and is validated server-side (dependent is a draft; same project; no self; no cycle; no already-merged dependency). It emits a `feature.dependencies.changed` event. runcastle has no feature-edit path today, so this is the first.
**Why:** The set only means something on a draft, so that is where it is edited. Replace-the-set gives the UI trivial add/remove and the server a single validation path shared with agents.

## 5. Agents: `dependsOn` at create time for any drafting session; set-edits only for the project session
**Decision:** MCP `create_feature` gains `dependsOn?: string[]` (feature slugs) on both its full and draft-only shapes, accepted **only with `draft: true`**. A new MCP tool `set_feature_dependencies({ slug, dependsOn })` replaces a draft's set through the same service as the UI, and is exposed **only to the project session**. The project skill's cut step states ordering via `dependsOn` instead of brief prose; the ideate skill's parking step mentions `dependsOn: [<this slug>]` for scope that builds on the current feature.
**Why:** Cut time is where ordering is known, and slugs are what agents hold — creating A then B-with-`dependsOn:[A]` chains naturally. Re-ordering the portfolio is project-level curation; a feature session must not rewrite other features' gates, so its only power is at creation.

## 6. Visibility: a chip in the rail, a disabled Start with reasons, a read-only "Blocks" line
**Decision:** **Rail:** no new lane and no triage change — waiting drafts stay in Drafts; the row chip reads `Waits on <slug>` (or `Waits on N`, tooltip listing them) instead of `Draft`, and ready drafts sort above waiting ones within the lane. A dependency merging does not push its dependent into "Needs you". **Draft workspace:** the next-step bar's Start is disabled while any dependency is unmerged, with the reason inline ("Waits on `a` (building), `b` (archived — remove it to start)"); `startDraft`'s server refusal stays authoritative. **Dependency's workspace:** a read-only header line "Blocks: `<slug>`, …" listing its unmerged dependents, editable only from the dependent side.
**Why:** Drafts are parked on purpose — the chip flipping back is enough signal, and lanes staying ignorant keeps this clear of rail grouping/clustering (out of scope). The "Blocks" line is where you need to see the edge: before archiving or deleting the dependency.

## 7. A dedicated `feature_dependencies` join table, kind-less forever; ADR-0013 amends decision 24
**Decision:** Store edges in `feature_dependencies(dependentId, dependencyId, createdAt)` — composite primary key, both FKs to `features.id` with `ON DELETE CASCADE`, **no `kind` column**. Cycle detection is a small new graph helper in `packages/core` over feature ids (the ticket `findCycle` stays private and untouched). ADR `0013-feature-merge-order-dependencies.md` explicitly amends decision 24 of `feature-grouping-forking-and-referencing`: decision 24 rejected *topical* edges (opinions that decay) and a generic table mixing write modes; this is one edge type with one job and a clear end (satisfied at the dependency's shipped phase, inert afterwards, like ticket `blockedBy`). The table name and the missing `kind` are deliberate: a second edge type needs a new ADR, not an enum value.
**Why:** A join table makes the reverse "Blocks" lookup and decision 3's delete cascade free, where a JSON column on the dependent would need hand-rolled scans. Refusing a `kind` column is what keeps this from growing into the `feature_links` graph the brief forbids.

## 8. Agents read the edges: portfolio and feature context both carry them
**Decision:** MCP `get_project_context` gives each feature row `dependsOn: [{ slug, satisfied }]`, and drafts a `waiting` flag. MCP `get_feature_context`'s header gains `dependsOn` (with satisfied state) and `blocks` (slugs of unmerged dependents). Edges and derived state only — no prose or advice.
**Why:** Without read access the project session re-cuts already-ordered work and can't tell what is startable, and a feature session can't know it is holding something up before suggesting an archive or a scope widening.
