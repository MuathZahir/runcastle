# Decisions — codex-runtime-support

## 1. Whole feature in one lap
**Decision:** Full parity ships in one lap — both surfaces (interactive talk sessions and AFK ticket burns) on Codex, behind the AgentRuntime seam. No thin lap 1 / deferred half.
**Why:** The feature is settled, not uncertain — users clearly want GPT models available. The codebase map shows clean seam points on both surfaces (sandcastle already ships a `codex()` provider for AFK; the launcher/artifacts/hooks form one adapter boundary for interactive), so the size is ticket-slicing work, not open design risk.

## 2. Runtime is derived from the model — no separate runtime knob
**Decision:** There is no standalone "runtime" selector. The existing model configuration (global default → per-step overrides → per-project → per-run override, resolved by `resolveModel`) is extended with Codex/GPT models; the runtime a session or burn launches with is a property of whichever model wins that chain.
**Why:** One knob instead of two. The model roster is already the thing users touch in settings; making runtime an attribute of the model keeps every existing config path, UI surface, and resolution rule intact and makes Codex adoption a dropdown choice, not a new concept.

## 3. Model→runtime mapping: curated entries carry it, custom ids declare it
**Decision:** Each curated model entry carries a `runtime` field (`claude-code` | `codex`) and the settings dropdown groups by runtime. Free-text custom model ids get an explicit runtime picker next to the field — the user declares the runtime; nothing is inferred from the id string.
**Why:** Pattern inference fails silently on unguessable future ids, proxies, or local models, and the failure mode is launching the wrong CLI. An explicit picker (shown only for custom ids) makes the mapping a stated fact instead of a guess, at the cost of one small control.

## 4. Per-ticket model assignment via annotated roster
**Decision:** Model entries in settings take an optional free-text use-case note (e.g. "opus 5 — UI/UX", "gpt-5.6-sol — mechanical refactors"). Only models **with** notes are passed to the tickets session's context; when emitting tickets it may stamp an optional `model` per ticket, chosen from that annotated set, leaving it blank when no annotated reason to deviate exists. Blank falls through to the existing `resolveModel` chain. The ticket card shows the assigned model (runtime implied) and the human can change it per ticket in the UI before Burn; the burner treats `ticket.model` as the run override.
**Why:** Ticket-time is when the work's nature is known, so that is where model fit is decided — guided by the user's own vocabulary, not a fixed taxonomy. Making notes the opt-in keeps the agent's candidate set exactly what the user curated, keeps context small, and degrades gracefully to today's behavior when nothing is annotated.

## 5. Codex auth mirrors the Claude pattern, per surface
**Decision:** Interactive Codex sessions inherit the user's own `codex login` (ChatGPT OAuth, `~/.codex/auth.json`); runcastle manages nothing. AFK Codex burns require `CODEX_API_KEY` (an OpenAI API key) in `~/.runcastle/.env`, injected into the burn env exactly like `CLAUDE_CODE_OAUTH_TOKEN`, with the same fail-early auth precheck. Verified against codex-rs source: `CODEX_API_KEY` is the highest-precedence auth path, designed for headless use. If the launcher relocates `CODEX_HOME` for a session, it must copy/link the real `auth.json` in, since auth lives at `$CODEX_HOME/auth.json`.
**Why:** Mirrors the mental model users already have from the Claude side (login for talk, token-in-.env for AFK). API-key env is the documented headless mechanism; copying OAuth files into sandboxes is fragile and over-scoped. Consequence, documented not fought: interactive Codex bills the ChatGPT plan, AFK burns bill the API key.

## 6. Onboarding is runtime-agnostic: auth what you have, at least one
**Decision:** First-run onboarding presents both providers (Claude Code, Codex) as peer cards — detect which CLIs are installed, let the user auth every provider they have or want, and gate first-run on **at least one runtime being ready**. No forced choice, no Claude-required baseline; a Codex-only user gets the full product (talk sessions and burns on Codex). Doctor probes both runtimes but only flags a runtime as a problem when it is missing *and* some configured model resolves to it. The AFK-enable surface becomes per-runtime (Claude setup-token flow; Codex API-key → `CODEX_API_KEY` in `~/.runcastle/.env`).
**Why:** Most users arriving at runcastle already have Claude or Codex — often only one. Requiring Claude would push Codex-native users away at the door. "At least one authed" is the true invariant the pipeline needs; everything else is per-runtime readiness surfaced contextually.

## 7. Per-runtime default pairs; onboarding seeds defaults from what is authed
**Decision:** Each runtime carries a curated default pair — flagship + cheap/smoke (Claude: `claude-opus-5` / `claude-haiku-4-5`; Codex: `gpt-5.6-sol` / `gpt-5.6-luna`). On onboarding completion the wizard writes the global default and smoke model from an authed runtime: Claude's pair when Claude is authed (both-authed keeps today's behavior), Codex's pair when Codex-only. Thereafter they are ordinary settings values. Additionally, any launch whose resolved model belongs to a runtime that is not ready fails early with a pointer to the doctor fix — the existing AFK auth-precheck behavior, extended to talk sessions.
**Why:** Hardcoded Claude defaults are dead values for a Codex-only user. Seeding once at onboarding keeps defaults ordinary, inspectable settings rather than magic that keeps re-deciding; fail-early beats a cryptic CLI error mid-launch.

## 8. AgentRuntime seam: symmetric interface, asymmetric mechanism
**Decision:** The seam is one per-runtime adapter contract (resolve binary, write session artifacts, build argv/env, declare kickoff line format, provide burn agent + guard install + error classifiers). Each adapter uses its runtime's *native* injection path: Claude Code keeps today's flag-based launch (`--settings`, `--mcp-config`, `--append-system-prompt-file`, `--plugin-dir`) inheriting the user's real `~/.claude`; Codex uses a synthetic per-session `CODEX_HOME`. We explicitly do **not** use `CLAUDE_CONFIG_DIR` per session — verified against Claude Code docs: on Windows credentials live inside the config dir (re-login every spawn), a fresh dir fires first-run onboarding in the terminal, and it orphans the user's real state.
**Why:** Forcing mechanism symmetry would degrade the working Claude path for aesthetics. Symmetry belongs at the interface, where the launcher and hooks server consume it; the server-side hook routes and MCP server stay runtime-neutral and unchanged.

## 9. Codex interactive sessions: synthetic per-session CODEX_HOME
**Decision:** The Codex adapter generates `~/.runcastle/sessions/<id>/codex-home/` containing: `config.toml` (model, `workspace-write` sandbox + auto-approval policy as the `acceptEdits` analogue, project trust, runcastle MCP server as streamable HTTP with the `X-Runcastle-Session` header), `hooks.json` (the same five lifecycle events → the same `bun run hook-client.ts` hook client, `commandWindows` on win32, launched with `--dangerously-bypass-hook-trust` since we author the hooks), `AGENTS.md` (the per-kind rendered system prompt, runtime-neutral wording), and `auth.json` copied from the user's real `~/.codex/auth.json` at launch. Codex's hook protocol is Claude-shaped (same stdin JSON, same `hookSpecificOutput.permissionDecision` verdicts), so the edit guard and `/api/hooks` routes are unchanged. Skills: the runcastle pack renders into Codex skill format (`.agents/skills` layout) at launch — one content source, two rendered formats; kickoff types the `$`-prefixed Codex invocation, delivery confirmed via the `UserPromptSubmit` hook as today. Burns: sandcastle's `codex()` provider through the existing `buildBurnAgent` chokepoint; the burn image bakes both CLIs; the burn guard gets a Codex twin installed into the container's `~/.codex/`; completion detection stays git-first; error classifiers gain OpenAI/Codex patterns.
**Why:** Codex has no per-launch config flags, but `CODEX_HOME` relocation is clean there: auth is one copyable file and every first-run/trust gate is bypassable via config we author. This reuses the entire existing hook/MCP/guard server surface — parity by protocol compatibility, not reimplementation.

## 10. Codex transcripts: best-effort parse, graceful degrade
**Decision:** The transcript service gains a best-effort parser for Codex's session rollout JSONL (`$CODEX_HOME/sessions/...`), rendered through the same conversation view. If the (undocumented) format shifts or a line doesn't parse, the UI shows "transcript not available for this session" — parsing failures never affect the session itself.
**Why:** The rollout format is internal to Codex; treating it as best-effort keeps the feature honest about that dependency while still delivering the transcript view in the common case.

## 11. UI copy becomes runtime-aware
**Decision:** All hardcoded "Claude" copy in apps/web (wizard headline, session/next-step copy, assistant transcript bubbles, AFK setup card) becomes runtime-aware: named per the session's/burn's runtime where a runtime is in hand, "the agent" where generic.
**Why:** A Codex-only user reading "Shape the idea with Claude" is a broken product, not a cosmetic nit — copy parity is part of the seam.

## 12. Reasoning-effort knob deferred
**Decision:** No per-model reasoning-effort setting in this lap; park it in the spec's `## Later laps`. Claude users can still express effort via model-id suffix (`[1m]`) as free text; Codex's `model_reasoning_effort` is not exposed yet.
**Why:** It's a nicety orthogonal to runtime parity; deferring keeps the lap focused. The model-entry structure (id + runtime + note) leaves an obvious place to hang it later.
