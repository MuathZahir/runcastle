# Decisions — preparation-supports-multi-service-projects

## 1. The feature is seamless drives, not just multi-service variables
**Decision:** The goal is reframed from "add multi-service affordances ({{port}}, redis, compose)" to "a test drive works on the first click for any project shape — the human opens the link and tests the feature, nothing else." Multi-service support, branch-delta handling (new packages, new migrations), and prompting changes are all in service of that. The injection-vs-cloning split stays: runcastle owns rendering variables into the environment; the project's own setup machinery owns making the world match.
**Why:** Real-world failure: a drive on a branch that added npm packages died on a missing install — nothing in the loop accounts for what the feature changed. Robustness of the whole loop is the actual want; the parked affordance list was a symptom inventory. The prep agent's intelligence is an explicit design resource: prefer teaching a smart agent to author robust project-specific machinery over growing per-stack drivers in the server.

## 2. Drive machinery is a repo-committed script in `.runcastle/`
**Decision:** The prep agent authors the drive setup/stop machinery as scripts committed to the project repo under a `.runcastle/` directory (e.g. `.runcastle/drive-setup.sh`); the `driveSetupCommand`/`driveStopCommand` settings shrink to the invocation line. Script steps are unconditionally idempotent (install, migrate, seed, compose up) rather than delta-detecting.
**Why:** Versioning the script with the code it prepares is the load-bearing property: a feature branch that adds a package, migration, or service amends the script in the same branch, and the drive on that branch runs the amended version — the branch carries its own setup, no server-side diff inspection ever. Idempotent-always steps solve the stale-deps failure by convention (`npm install` is a no-op when clean, exactly right when packages changed). Repo-committed scripts are PR-visible, human-editable, and carry no hidden state in runcastle's data dir.

## 3. The burner maintains the script; no pre-drive agent pass
**Decision:** The burner prompt gains a standing instruction: a ticket that introduces infrastructure the dev environment needs (new service, required env var, seed requirement, process to run) must update `.runcastle/` drive scripts in the same branch. There is no pre-drive "inspect the branch delta" agent pass — the drive loop stays pure machinery.
**Why:** Idempotent script steps already absorb the common deltas (packages, migrations) with no edit at all; only structural changes need script edits, and the agent making the structural change is the one who knows. A just-in-time agent pass at drive start would add latency exactly where the human wants to click a link, and would patch unreviewed what should be fixed in the branch.

## 4. Script verification is layered: prep dry-run, hermetic checks, self-healing drive start
**Decision:** The burner sandbox stays hermetic (locked by the brief), so it can never run the script. Verification layers: (1) the prep dry-run drive (existing, from preparation-proves-its-findings) proves the script as first authored; (2) the burner runs hermetic sanity checks only — script syntax, referenced files exist, compose file parses, env vars used appear in `driveEnv`; (3) a setup failure at drive start becomes first-class and recoverable: the failure output is surfaced prominently and a **one-click "Fix drive" action** spawns a host-side fix session — an agent with the failure log, the script, and the branch delta, mandated to repair the environment and retry. One-click, not auto-spawn. A background pre-flight (booting the stack on the feature branch before the human clicks) is parked as a later-lap candidate.
**Why:** Verification must live where a host exists; drive start is the first such moment after implementation. Typo-grade badness dies in the sandbox; environmental misses die at first drive start with an agent already on them instead of a stranded human reading a hookFailure blob. One-click over auto-spawn matches the ask-before-act ethos — an agent should not start running on the host uninvited — and costs one click at the exact moment the human is looking at a failure.

## 5. Readiness splits along the injection-vs-cloning line
**Decision:** Service readiness belongs to the script: the prep prompt teaches the agent to author waits (`docker compose up --wait`, `pg_isready` loops) into `drive-setup`, so exit 0 *means* services are up — no new health key, no server-side polling of arbitrary services. App readiness belongs to the server: after sniffing the dev pane's localhost URL, the server polls it until it responds (any HTTP status counts as serving), shows "starting…" until then, and surfaces a timeout as a warning, not a failure. "Open app" only becomes clickable when it will actually load.
**Why:** Waiting on services is stack-specific and the tools already exist — an intelligent prep agent scripts it better than a generic server poller could. Waiting on the dev server is the one thing the script cannot do (it runs before the dev pane exists), so the server does exactly that and nothing more. The prepared-key surface stays unchanged.

## 6. Scripts compute, the server injects: `RUNCASTLE_*` in, `.runcastle/drive.env` out — templating retired
**Decision:** The `driveEnv` textarea, the `{{...}}` templating, and every planned drive variable (`{{port}}`, `{{dbindex}}`) are retired. The contract becomes: the server passes identity as plain env vars (`RUNCASTLE_SLUG`, `RUNCASTLE_BRANCH`, `RUNCASTLE_ID`) into every hook; the setup script computes everything else — ports, database names, redis indexes, compose project names, URLs — and writes `.runcastle/drive.env` (gitignored, plain KEY=VALUE); the server overlays that file verbatim onto the dev pane's and stop hook's environment and shows the overlay on the timeline. Port strategy survives as a *recipe*: the prep prompt hands the agent a canonical snippet for deterministic slug-derived ports with a bind-probe fallback, so laps keep stable URLs. The dry-run verification observable for the retired `driveEnv` key becomes "setup wrote a parseable `drive.env`" — a deliberate amendment to `preparation-proves-its-findings`' contract. Identity stays server-passed (not git-derived in scripts) because the prep dry-run runs under a synthetic identity on whatever branch is checked out.
**Why:** With agent-authored scripts, templating is redundant machinery — anything can be computed in the script. Exactly two things a script cannot do for itself: know which drive it serves (identity), and set environment for a sibling process the server spawns (the dev pane). So the server does exactly those two and nothing more. The file interface preserves the injection-vs-cloning split in its sharpest form — script computes, server injects verbatim — works with any `devCommand`, needs no wrapper scripts, and gives the timeline, dry-run, and drive-fix agent one inspectable artifact saying exactly what a drive ran with.

## 7. The prep prompt teaches a shape-discovery protocol and a recipe pack, mandating almost nothing
**Decision:** The prep prompt's drive section is rewritten around minimal assumptions: the agent first *discovers* the project's shape — package manager, OS/shell, monorepo layout, docker presence, services, hosted vs local DB, how env loading works — and then authors scripts fitted to it. Runcastle mandates only the contract: scripts live in `.runcastle/`, setup writes `drive.env`, `RUNCASTLE_*` vars are the identity, steps are idempotent, exit 0 means ready. Everything else ships as recipes the agent adapts, not rules: per-branch postgres, compose (`COMPOSE_PROJECT_NAME` from `RUNCASTLE_ID`, env-var port mappings, `up --wait`), redis (logical index or key prefix derived in-script, db 0 left for the human), hosted DBs (Neon branch-per-feature, schema-per-branch where CREATEDB is refused), deterministic ports, service health-waits. The prompt also directs a prep-time env-loading audit: find `dotenv override: true`-class patterns that would defeat the injected environment, and fix or record a finding — the agent is the detector; the machinery never guesses.
**Why:** The user's explicit bar: works across a variety of project types without brittleness, leaning on the prep agent's intelligence rather than server-side stack knowledge. A contract-plus-recipes prompt keeps the server stack-agnostic — a project shape nobody anticipated still works if the agent can script it, which is the definition of not brittle.

## 8. `driveEnv` is removed cleanly, no legacy path
**Decision:** `driveEnv` disappears from the `Project` schema, `PREPARED_KEYS`, `DRIVE_LOOP_KEYS`, the settings UI, and the dry-run's verification observables. No deprecated column, no read-only migration shim. Existing projects lose the value; their drive-loop verification stamps clear, and the next-step bar's existing unverified-keys nudge points at a fresh prep session, which re-establishes the world as scripts.
**Why:** Pre-1.0, dogfooding, one known deployment — carrying a dead key forever to spare one re-prep is a bad trade. The re-prep is itself the migration: the prep agent authors the scripts the new contract wants.

## 9. Drive-fix is its own session kind
**Decision:** The one-click "Fix drive" spawns a new `SessionKind` (`drive-fix`), not a `prepare` session. It launches with the failure output, the drive's `drive.env` (if written), the branch delta, and the feature's docs as context; its mandate is narrow — repair the environment and retry this drive — under the same host-side ask-before-act rules as prep. It reuses the prep session's launcher machinery. The exact MCP tool surface for retrying the drive is spec detail.
**Why:** Prepare's mandate (establish and verify all findings) is the wrong frame for a session that exists to unblock one failing drive now; a distinct kind gets a fitted prompt and fitted tool gating while sharing the launcher plumbing.

## 10. One lap — spec the whole thing
**Decision:** All five work areas ship in one lap: the script contract (identity vars in, `drive.env` out, templating retired), app-readiness gating of "Open app", the prep-prompt rewrite, the burner-prompt maintenance instruction with hermetic checks, and the drive-fix session. Only the background pre-flight stays in `## Later laps`.
**Why:** The human's call: direction is settled, so build it whole and improve from real use. The lap-2-for-drive-fix idea traded completeness for failure data; the human prefers the complete loop now — a failing drive with no fix path would itself be the brittleness this feature exists to end.
