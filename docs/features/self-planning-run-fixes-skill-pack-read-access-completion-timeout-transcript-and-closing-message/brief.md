# Self-planning run fixes: skill pack read access, completion timeout, transcript and closing message

## Ticket 1

A headless self-planning run is refused when it reads its own skill pack's reference files, so it draws the preview by hand without the rules or the starter page. Seen on the first real run after 'Features plan themselves' merged (Claude Code, feature in another project, runcastle run from the global install): the run reported "The preview rules file can't be read here" and "I couldn't read the skill's preview rules or starter template (permission was refused)", then wrote preview.html by hand. The files are the ideate skill's references/preview.md and references/preview-starter.html, which carry the Check first group and the assumed marks. Suspected cause, read from the code and NOT reproduced: the launcher grants a session no read access outside its worktree. renderSettings (packages/server/src/launcher/artifacts.ts) allows only runcastle's MCP tools and git commands, and buildClaudeArgs (packages/server/src/launcher/runtimes/claude.ts) passes --plugin-dir but no extra readable directory; the skill pack lives outside the feature worktree, and in print mode (-p) there is nobody to approve the read. Confirm the cause first with a real headless run, then make every session able to read its own skill pack directory without a prompt: interactive sessions too, since a permission prompt for runcastle's own files is wrong there as well. Check the Codex adapter for the same gap. Expected: a self-planning run reads references/preview.md and the starter page and its preview is built from the starter (the Check first group comes from the starter's C list, not hand-written markup). Do not widen read access beyond the skill pack directory.

## Ticket 2

complete_phase can time out on the caller's side, and a headless self-planning run only survived it by retrying. Seen on the same run: "Retrying the ideation milestone once, since it timed out rather than being refused" and "The first attempt to mark ideation complete timed out. One retry succeeded." The cause is unknown; diagnose it before changing anything. What is known: the tool handler in packages/server/src/mcp/server.ts records the milestone synchronously (toolCompletePhase) and then awaits commitDocsCheckpoint (git add and commit of docs/features, then landChatCommits) before it answers, so a slow git commit or landing delays the response past the client's tool timeout even though the milestone is already recorded. That call was the first one to commit the new preview.html. Why it matters: completing the tickets step is what arms Burn (markTicketsReady). The ideate skill's self-planning section says a refused tool is not a wait and must not be retried, and says nothing about a timeout, so a run that does not retry a timed-out tickets completion leaves the feature reading as stopped short with a finished plan. Expected: a slow docs checkpoint cannot make complete_phase fail for the caller (answer once the milestone is recorded and let the checkpoint finish and report itself through its existing git.commit_pending warning event, or an equivalent that keeps the checkpoint durable), and the skill text tells a self-planning run what to do when a runcastle tool times out, as distinct from being refused. If the same awaited checkpoint sits behind emit_tickets and update_ticket, say so in the digest; fix them only if it is the same small change.

## Ticket 3

The launcher's self-planning briefing shows in the feature's chat transcript as something the human said. After a self-planning run, opening the chat shows a first turn from 'You': "Proceed with your task: no human is present and nobody will reply to you. Invoke the /runcastle:ideate skill and follow its \"Planning without a human\" section…". Nobody typed that. Cause: withoutKickoff in packages/server/src/services/conversations.ts filters a transcript's user turns with promptMatchesKickoff, which compares the first 40 characters against the per-kind default kickoff ("Proceed with your task: invoke the /runcastle:…"). The self-planning kickoff (selfPlanKickoffFor in packages/server/src/launcher/runtimes/skills.ts) differs from character 24, so it is kept. Tickets 1 and 2 of features-plan-themselves both recorded this as left undone. Expected: the self-planning kickoff is recognised for both runtimes' spellings and removed from the transcript, and it never becomes the conversation's derived title. While there, give the session.self_plan_ended event a label in apps/web (lib/activity.ts and Activity.tsx), which the same two digests recorded as missing.

## Ticket 4

A self-planning run's closing message reports things that have nothing to do with the plan. Seen on the same run, at the end of the closing message: "These connectors need authorising in claude.ai's connector settings before they can be used: Gmail, Google Calendar, Google Drive and Grafana Cloud. The helix MCP server failed to connect. This plan didn't need any of them." The session inherits the human's own MCP servers and reported their state. Expected: the ideate skill's self-planning closing message (the 'Straight through' rule in section 1a and the closing-message section it points to, in packages/skills/packs/runcastle/skills/ideate/SKILL.md) says the message covers the plan only: that it was made without the human, how many decisions it holds, which to check first, and anything that stopped the run doing its job (a refused or failed tool that the plan needed). The state of tools and connectors the plan did not need is left out. Keep the existing pinned phrases that self-plan-skill.test.ts asserts, and extend that test for the new wording.
