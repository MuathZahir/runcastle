Workers: prototype an agent you can enter inside a sandbox

A spike. One worker runs as a normal runcastle chat inside a burn sandbox: you open it, type to it, see its dev server, and it hands back to its lead. It ends with numbers so you can pick sandbox or host at checkpoint 1. The orchestrator agreed it with changes: no host networking, a scratch data folder, a timed handoff, and no product UI.

What is left out

Under the hood
Nonew table

None: a worker is a side thread plus one JSON file under the data folder's workers/: label, goal, done-when, status, branch, container, port, handbacks, timings.

Newtransport

At the thread host's existing transport seam, which may now also say how the session opens: docker|podman exec -i <container> node /opt/runcastle/acp.mjs, cwd /home/agent/repo, the worker MCP server, bypass mode. Resume is the same session/load chats use.

Newworker service

A plain docker run -p 127.0.0.1:P:P of the burn image (sandcastle cannot publish a port), the host repo's git dir mounted so commits come back as refs, the adapter bundled to one file and mounted read-only; stop/start on idle and wake.

MCPlead

start_worker (provisional name), only with the setting on.

MCPworker

A stdio MCP server inside the sandbox: hand_back({ summary }) writes a file the server reads at turn end, then one deliverToLead; start_dev_server({ command? }) runs detached on the published port.
