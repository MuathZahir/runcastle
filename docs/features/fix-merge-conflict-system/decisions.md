# Decisions — Fix merge conflict system

## 1. Resolver session keeps HITL revisit shape, edit guard gets a MERGE_HEAD-scoped exemption
**Decision:** "Resolve with agent" keeps launching a human-watched revisit session in the talk worktree (CONTEXT decision #9 stands). The edit guard exempts that session's file writes only while a merge is actually in progress in the worktree (`MERGE_HEAD` exists) — the launcher marks the session as a conflict-resolution session and the guard checks the merge state, so the exemption is "resolve the in-progress merge", not blanket write access. The moment the merge commit lands, the guard snaps back.
**Why:** The kickoff (`mergeConflictKickoff`) briefs the agent to resolve and commit, while `evaluateEditGuard` denies every non-project session's writes outside the feature docs — the two contradict and the agent gets wedged (or bypasses via shell). A sandboxed AFK resolver was considered and rejected: it abandons the deliberate HITL-with-spec-context design for a much bigger change. Merge resolution is materially different from "writing code" — the content comes from the two sides of the merge, and MERGE_HEAD scoping makes the exemption self-limiting.

## 2. Resolved conflicts clear two ways: ancestor check at session end, plus an always-enabled retry
**Decision:** (a) When a resolve session ends, the server checks in the talk worktree whether the base branch is now an ancestor of the feature branch tip (`git merge-base --is-ancestor`); if the merge commit landed, it emits a `merge.resolved` event, and `unresolvedMergeConflict` treats it like `burn.started` — the conflict clears and the normal Merge & ship primary returns. (b) Independently, the Merge & ship action is never disabled by a standing conflict: it becomes an enabled secondary "Retry Merge & ship". A successful retry ships (card superseded); a failed one re-emits a fresh `merge.conflict` with updated timestamp and files, so the card self-corrects.
**Why:** Today the only conflict-clearing event is `burn.started`, so a resolved conflict leaves Merge & ship disabled forever — the kickoff tells the human to retry a click the bar refuses. The ancestor check is event-sourced and survives reloads; the enabled retry covers everything the check can't see (manual resolution in the human's checkout, a crashed session). Findings F8 ("don't recommend a merge that will fail again") stays honored: Resolve remains the primary; the retry is a secondary, present but not promoted. Disabling it entirely was the overcorrection that created the deadlock.

## 3. Burn is reachable while a conflict stands
**Decision:** When pending tickets exist during a standing merge conflict, the review next-step bar shows Burn as an enabled secondary action (Resolve stays primary). The conflict branch of `nextStep` no longer shadows the `pending > 0` Burn promotion entirely.
**Why:** Burning runs tickets on the feature branch and never touches the base merge — a conflict with the base is no mechanical reason to forbid it, and `burn.started` already clears the conflict card (a re-run makes the recorded file list stale). Hiding Burn behind the conflict manufactured a deadlock: the conflict hid the only button whose event could clear the conflict. Forcing a resolve-before-burn ordering has no mechanical basis.

## 4. The Bash write hole stays as is — no Bash matcher
**Decision:** The edit guard keeps matching only `Edit|Write|NotebookEdit`. No Bash-command matcher is added; shell-based file writes in talk sessions remain covered by the prompt rule alone.
**Why:** Human's call. A conservative fail-open Bash matcher was offered and declined — with decision 1 in place the resolver has no reason to bypass, and the added parsing complexity/false-positive surface isn't worth it for the honest-agent case that remains.

## 5. The ticket-landing resolve flow gets the same exemption; no read-only-phase UI work
**Decision:** Both conflict-resolve launch sites — the review card's "Resolve with agent" (`mergeConflictKickoff`) and the run lane's "Resolve in terminal" (`ticketConflictKickoff`) — carry the same resolve-purpose flag, so the MERGE_HEAD-scoped guard exemption of decision 1 covers both. No hints or affordances are added to read-only phase views.
**Why:** The ticket-landing flow launches the same `revisit` kind with the same brief-to-resolve contradiction — fixing one site but not the other leaves half the bug alive. The detour to the read-only build phase was a symptom of Burn being hidden in review (decision 3 removes the cause), not a missing affordance.
