# Decisions — stopping a headless agent actually stops it

## 1. One lap, whole spec, no map
**Decision:** Spec the feature whole in a single lap. No waypoint map, no thin lap 1.
**Why:** The misbehavior is precisely diagnosed (abort never kills the child; no handle exposed to kill with) and the destination is unambiguous. Three tight areas — a minimal sandcastle-patch extension to expose kill handles, a kill-at-abort layer in the burner, and a "stopping…"/confirmed-dead state in server+UI. Heavy event-service gating by ticket status is consciously deferred: with a real, confirmed kill, zombies should not exist to write events; gating is defense-in-depth for later.

## 2. Kill lives in runcastle; sandcastle patch only exposes handles
**Decision:** Extend the existing sandcastle patch (`patches/@ai-hero%2Fsandcastle@0.12.0.patch`, ADR-0011 precedent) only enough to make the kill target knowable — the docker provider's container name and the host provider's spawned child PID. All kill logic lives runcastle-side, at abort time: `docker rm -f <container>` for docker burns, `killProcessTree(pid)` (the proven taskkill `/T /F` helper from `packages/server/src/pty/kill-tree.ts`) for host-mode agents.
**Why:** Sandcastle's README documents "signal kills the in-flight agent subprocess," but the shipped 0.12.0 code (the latest published version) cannot deliver it: every exec is a raw `child_process.spawn` inside a plain Promise with no canceler, host-mode `close()` is a no-op, and container teardown is scope-release at run end, not abort time. Fixing abort inside sandcastle's Effect internals would mean maintaining a fork of its concurrency core across version bumps, and the fix this stack needs (Windows tree-kill, container kill) is opinionated in ways upstream may not take. A handle-exposing patch is ~10 mechanical lines that rebases trivially, and the kill semantics land next to their only battle-tested sibling in this repo. Filing the upstream bug (docs promise kill, code can't) is a side errand, not part of this feature.

## 3. Handle plumbing: name-in for docker, pid-callback-out for host
**Decision:** The patch adds an optional caller-supplied `containerName` to sandcastle's docker options; the burner passes a deterministic name (`runcastle-<runId>-t<seq>`) and at abort runs `docker rm -f <name>`. For host mode (`noSandbox()` — review/research agents), the patch adds an optional `onChildSpawn(pid)` callback since a fresh child is spawned per exec; runcastle tracks the most recent live PID per run and at abort fires `killProcessTree(pid)` from `packages/server/src/pty/kill-tree.ts`.
**Why:** Docker's container is created once per sandbox, so a caller-chosen deterministic name is possible and valuable — `docker rm -f` needs no discovery, and a future boot-time sweep of strays by prefix comes free. Host mode has no stable process, so only a spawn callback can work there. `docker rm -f` over `docker stop`: immediate SIGKILL + removal, no 10s grace. The slot burn-cache is a named volume, untouched by container removal, and the next slot burn's setup already scrubs `.git/*.lock` and hard-resets — a SIGKILL mid-write lands in a state existing recovery handles. Tree-kill on host reaps the `claude.cmd` shim's node grandchild, per the dev-pane precedent.

## 4. Stop waits for confirmed death; no new ticket status
**Decision:** The `ticket.stop` / `run.cancel` mutations kill the process, wait for confirmed death (docker: container gone; host: tree-kill settled), and only then resolve — the UI button shows "Stopping…" off the mutation's pending state, no new DB status. Terminal state is written by the existing failure path, which now only fires after real death (the kill is what makes sandcastle's run() reject). If death is not confirmed within 10s, mark the ticket stopped anyway but say so honestly: a toast plus a timeline event ("stop timed out — the process may still be running").
**Why:** Death takes a second or two, so a synchronous bounded wait is the simplest honest UI — no schema change, no new status to render everywhere, and no way for "stopped" to precede death since death itself triggers the terminal write. The timeout escape keeps the UI from wedging on an unkillable process while replacing today's silent lie with an explicit warning.

## 5. Waive kills a live agent first
**Decision:** `cancelTicket` (waive) on a ticket whose agent is actively running routes through the same kill-and-wait as Stop, then does its DB flip. Waiving an idle ticket stays a pure DB flip.
**Why:** The observed bug included a waived verification agent that visibly carried on. Blocking waive on burning tickets and requiring Stop first would add a click for no benefit; the kill path is the same code either way.

## 6. Coverage: all four agent launch sites, and Cancel run kills every live lane
**Decision:** The kill wiring covers all four `run()` call sites — ticket burner (docker), merge-conflict resolver (docker), review/verification agent (host), research agent (host). `cancelRun` kills every live lane, not just one.
**Why:** All four share the same broken abort; research rides along free on the same host-mode path as review. Interactive PTY sessions and dev panes are already handled elsewhere and are out of scope.
