# Decisions — Agents can notify your phone

## 1. Notifications travel by browser push, for any runcastle user
**Decision:** A notification goes out by standard browser push (the Web Push protocol) to the runcastle app on the phone. It needs no account, no paid service and no separate app, so it works for anyone running runcastle, on Android and on iPhone. Each runcastle install makes its own signing keys (the VAPID keys a push service asks for) and keeps them in its data dir. The message text is an ordinary sentence, because the protocol encrypts it between runcastle and the phone: Apple or Google see only when a message went, its size and which device it is for. Notifications need the phone link to be on, because a phone can only install the app and subscribe over HTTPS.
**Why:** The human wants this to work for other runcastle users, not only themselves. Pushover needs an account and a purchase per platform, and ntfy needs a separate app and either a shared public server or one the user hosts. iPhone users have one extra step, adding runcastle to the Home Screen (iOS 16.4 or later). Only Android is tested on a real phone here, so iPhone support rests on the standard until someone tries it.

## 2. No timer: the agent's instructions decide when a recent chat means stay quiet
**Decision:** The server does not block a notification because the human typed recently. The agent's instructions say to notify when the human asked to be told, or when it needs them and they seem to have left, for example after a long unattended round. They say not to notify during a back-and-forth, when the human will see the reply anyway.
**Why:** A timer cannot tell "ask and walk away" from "still here", and "show me screenshots when it's done" is the job this feature exists for. It also keeps to the human's choice that nothing is automatic. The agent already knows when the human last typed. A wrong call costs one stray or missed ping, and a rule can be added later if that proves common.

## 3. The server limits who may notify, with no exception for a human's request
**Decision:** An orchestrator thread may always notify. A feature's main chat agent may notify only while no orchestrator thread holds that feature; otherwise the server refuses, and the agent says in the chat that it cannot ping and why. Side threads and workers, review workers included, do not get the tool. This holds even when the human asks a held feature's agent directly: they ask the orchestrator instead.
**Why:** It enforces the brief's rule through the holder field "Threads hold features" already keeps, so a skill wording slip cannot break it. One rule is easier to trust, and the server cannot tell a human's request from the agent's own judgement. The cost is one extra message in a rare case.

## 4. Tapping opens the thread that sent it, and an unreachable computer gets a page of its own
**Decision:** Tapping a notification opens the chat that sent it: a feature's chat for a feature's agent, the exact orchestrator thread for an orchestrator, not the latest one. When the phone cannot reach runcastle, the service worker this feature adds shows a "can't reach your computer" page instead of the browser's error.
**Why:** That chat is where the sender can explain and show what it wants seen. A feature's agent did not send an orchestrator's message and may have nothing to show. `runcastle-on-your-phone` decision 9 left the page to this feature, because it needs the service worker.

## 5. A "Notifications" row at the foot of the phone's list turns them on
**Decision:** The phone's feature list ends with one "Notifications" row and an On/Off switch, one per phone, covering every project on that runcastle. Turning it on asks the browser's permission, then sends a test notification. On an iPhone not yet added to the Home Screen, or with permission blocked, the row says what to do. Desktop Settings' "On your phone" section gets one line pointing to it. When an agent calls the tool and no phone is set up, the tool says so and the agent tells the human where to turn it on.
**Why:** The permission has to be asked on the phone, and Settings is not on the phone view. A row keeps the list clean where a banner would not. The test notification proves it works, and the tool's answer reaches a new user who never saw the row, without any automatic alert.
