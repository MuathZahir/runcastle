## 1. Tickets carry a kind: implementation or review

# Ticket 1 — Tickets carry a kind: implementation or review

## What was done

Added `TicketKind` (`implementation` | `review`) to `@runcastle/core` and threaded it end
to end. `TicketInput` gains `kind: TicketKind.default('implementation')`; the stored
`Ticket` inherits it as a required field. The `tickets` table gains a matching
`text('kind').notNull().default('implementation')` column, with migration
`0023_outgoing_jocasta.sql` generated by the repo's own `bun run db:generate` (one
`ALTER TABLE ... ADD` — existing rows read back as implementation tickets).
`storeTickets` passes kind through and `rowToTicket` reads it back. The web ticket card
renders a new `TicketKindChip` — a `review` badge in the review-phase colour, nothing at
all for implementation tickets. Tests cover the schema default, an unknown kind being
rejected, a mixed-kind batch stored and read back with `blockedBy` resolved, and the
`emit_tickets` seam with the batch parsed the way the registered tool parses it.

Two things deviated from what the ticket described. First, `emit_tickets` needed no zod
change of its own: its `inputSchema` is literally `z.array(TicketInput)`, so extending
the core schema extended the tool. Only its description string changed, to tell sessions
the field exists and to block a review ticket on the implementation tickets. Second, the
tRPC routers turned out not to re-declare the ticket shape at all — nothing to extend
there.

## Surprises

The exported *type* `TicketInput` had to move from `z.infer` to `z.input`. With a zod
default, `z.infer` (the output type) makes `kind` required, which would have broken every
hand-built batch — `promotionTicket` in the test-notes service and four test helpers —
for a field the ticket explicitly wanted optional. `z.input` keeps it optional at
construction while parse and `storeTickets` still apply the default, and the stored
`Ticket` (which uses `z.infer`) still carries `kind` as required. Worth knowing before
adding the next defaulted field to a wire schema.

The stated baseline was also stale in both directions. The three pre-existing
`@runcastle/web` typecheck errors are gone — the root `typecheck` script now filters web
and design-system too, and passes clean. But one test fails that the baseline did not
list: `packages/server/test/dev-pane.test.ts` > "kills the child process tree so the
port-holder is not orphaned". It spawns a real process group and asserts the OS reaped
it; it fails identically in isolation and touches nothing in this diff (confirmed against
`git diff --name-only`). It is a container process-reaping fault, not a regression. Every
other test passes — 1666 green.

## Left undone

Deliberately untouched, per the ticket: gate G4 (`all-tickets-terminal`) stays the
kind-agnostic DB predicate it was, and `TicketContentPatch` still does not let a revisit
session rewrite a ticket's kind — nothing asked for that, and it is not obviously
desirable.

The badge went on the tickets-ledger card only. `RunBody` renders its own per-ticket
"lanes" (`.lane-seq`, `TicketStatusChip`) during a burn, and those show no kind. Once
review tickets actually execute differently — no branch, no sandbox, no merge-queue entry
— the run lane is probably the surface that most needs to say so, since that is where a
human watches a review ticket behave unlike its neighbours. Left for the slice that makes
the behaviour real rather than guessing at the presentation now.

## 2. Agent-callable review wires: review drive and test notes

# Ticket 2 — Agent-callable review wires

## What was done

Two new MCP tools, `review_drive` (start|status|stop) and `add_test_note`, both gated on a
**run identity** rather than a session: a caller carries `X-Runcastle-Run: <runId>`, which
resolves to a run row that must still be `running`, and the feature comes from that run
rather than from anything the agent claims. Ordinary talk sessions carry no such header and
are refused with a `GateError` naming their kind, the way `dry_run_drive` refuses non-prep
sessions. The header's canonical spelling is exported as `RUN_HEADER` so the runner's
`mcp.json` (next ticket) does not re-derive the string.

`git.reviewDrive` runs the real feature test drive: I threaded a `DrivePurpose`
(`human | review`) through `testDrive`'s **start** path and onto the drive state, so a
review start is byte-for-byte the human's start minus the active-run denial. Dirty tree and
a held slot still deny, immediately. `status` returns `activeDriveInfo()` including the
sniffed `devUrl` (which arrives asynchronously, so the tool description tells the agent to
poll). A start that throws past the checkout switch stops itself before rethrowing.

Notes gained an `author` (`human` default, `agent`), in the core `TestNote` schema and as a
defaulted `test_notes` column (migration 0024). `addNote` takes it as a trailing argument,
so every existing caller is untouched; `note.added` carries it in the event data.

## Surprises

- **Deny ordering makes the carve-out awkward to observe.** Once a review drive holds the
  slot, a human start is refused for the *slot*, not the run — so the test proves the
  carve-out by denying the human first, while the slot is still free.
- **Stop deliberately is not purpose-gated.** I gave `reviewDrive` its own stop guard (it
  will not touch a drive that is not its own), but left the human's Stop able to end a
  review drive. If a review agent dies holding the slot, the UI's Stop is the only way the
  human gets their checkout back; refusing there would strand them.
- `packages/server/test/dev-pane.test.ts > "kills the child process tree so the port-holder
  is not orphaned"` fails in this sandbox, on a targeted single-file run, with code this
  ticket does not touch (PTY process-group reaping). It is not in the prompt's baseline
  list, but it is not mine. Everything else is green: 1677 passed, typecheck clean
  (including `@runcastle/web`, which passed here despite the baseline note).

## Left undone

- `activeDriveInfo()` does not expose the drive's purpose, so the UI still says "test drive
  active" while the review agent is driving. Ticket 5 (the loud review surface) is the
  natural place to surface "review agent is driving" and agent attribution on notes.
- The rendered `docs/features/<slug>/test-notes.md` shows no attribution — its `## Lap N` +
  checkbox format is a contract read by the lap kickoff and the revisit skill, and the
  ticket asked for attribution in the schema and storage only.
- Nothing calls these wires yet: the runner must create the review agent, pass the run
  header, and — importantly — call `review_drive stop` in a `finally`, since a crashed
  agent leaves the slot held and the checkout switched.

## 3. Burner executes review tickets host-side with the review prompt

# Ticket 3 — Burner executes review tickets host-side

## What was done

The burn now has two execution kinds. `isReviewTicket` is the only fork: the scheduler in `burnTickets` holds a review ticket until no implementation ticket is pending or in flight (defensively, so a review emitted without `blockedBy` still runs last), and `resolveBurnDeps` routes it to a new `workflows/review-ticket.ts` instead of `realExecuteTicketRun`. That path takes no branch (sandcastle `head` strategy), no container (`noSandbox` whatever `config.sandbox` says) and no merge-queue entry — just `claude --print` in the project's real checkout with the runcastle MCP wired in. A review prompt lives at `packages/skills/burner/review-ticket.md`; the tickets skill now tells sessions to author one review ticket per feature.

Two deviations worth knowing. First, sandcastle 0.12.0's `ClaudeCodeOptions` has **no MCP field**, so `--mcp-config` had to ride `buildPrintCommand` — the same wrapper seam the Windows model de-quote already used, now generalised via a `BurnAgentOptions` argument that also forces the host build. Second, the agent reports through `~/.runcastle/reviews/<ticketId>/` (new `reviewDir` path helper) rather than the repo root: a `DIGEST.md` written into the human's real checkout is an untracked file, and the drive refuses to start on a dirty tree. `WorkflowCtx` gained `runId` so the agent's `mcp.json` can carry `X-Runcastle-Run`.

## Surprises

- **Reaching for `getRuntimeCtx()` breaks `apps/web`.** Workflows are AppCtx-free by design, and `launcher/runtime.ts` dynamically imports `db/client.ts` — which TypeScript still resolves, so importing it from the burner pulled `bun:sqlite` into web's type graph through the tRPC router and failed web's typecheck with a module-not-found. Same trap applies to `mcp/server.ts`. The fixes: `RUN_HEADER` + a new `renderRunMcpConfig` moved to `launcher/artifacts.ts` (their natural home anyway), and the drive now remembers how to end itself and exposes a ctx-free `releaseReviewDrive()` in `git.ts`.
- **`TicketOutcome`'s failed variant had nowhere to put a reason the human reads.** "Review could not run: X" belongs in the run digest, not only in `ticket.error`, so `failed` gained an optional `digest` that `failTicket` stores and harvests. Generic, but added for this.
- **`packages/server/tsconfig.json` only includes `src`** — test files are never typechecked, only transpiled by vitest. So type errors in tests are invisible until they fail at runtime.
- **The web typecheck baseline in the ticket is stale**: it predicted 3 pre-existing errors in `EnableAfkCard.tsx`/`SettingsOverlay.tsx`; `bun run --filter '@runcastle/web' typecheck` is now fully green.
- **One pre-existing suite failure, environmental**: `dev-pane.test.ts > kills the child process tree so the port-holder is not orphaned` fails in this sandbox (process-group reaping). Neither that test nor `services/dev-pane.ts` nor `pty/` has changed since the baseline commit. Everything else is green (1692 passed).

## Left undone

- **A failed implementation ticket still cascade-fails the review ticket** ("blocked by failed ticket N"), because that is the generic `blockedBy` semantics and the ticket said not to change it. With the skill now telling sessions to block review on *every* implementation ticket, one flaky ticket means no review at all. Worth deciding deliberately: either review should treat a failed blocker as satisfied, or the skill should say so.
- **Nothing verifies `agent-browser` can actually launch a browser** — the probe only checks the binary is on PATH. A present-but-broken install fails inside the agent, which reports it through `BLOCKED.md`, so the outcome is right but the diagnosis is late.
- **`review-ticket.ts` and `ticket-burner.ts` import each other.** Safe (neither touches the other during module evaluation) but a shared `burn-shared.ts` would be cleaner if a third execution kind ever appears.
- **Seam 5 (the loud review surface) is untouched** — that is another ticket's territory; agent notes currently land in the notes panel with their `agent` author flag and nothing summarises them.

## 4. Review phase surfaces the agent's report loudly

# Ticket 4 — Review phase surfaces the agent's report loudly

## What was done

Added `reviewOutcome` to `apps/web/src/lib/feature-ui.ts`: it reads the feature's
tickets and test notes into one of four states — `none` (no review ticket),
`ran` (with a findings count), `failed` (with the ticket's `error` as the
reason), or `waiting` (a review ticket that has not reached a terminal status).
Findings are counted from agent-authored notes, all of them regardless of
status, since a finding the human already ticked off was still a finding. A
private `reviewRow` paints that outcome as a `CheckRow` keyed `review agent`, so
`CheckLine` renders it as "review agent · 2 findings" with no new UI primitive.

`reviewChecks` now **leads** with that row rather than appending it — the goal
is that the human cannot miss the report on arrival — and omits it entirely when
no review ticket ran. `mergeSummary` appends it instead, and unlike the review
card it *does* report an absent review ("no review ticket", grey), because
reporting every gap in the picture is that dialog's whole job. A review that
could not run also adds one warning sentence beside "never test-driven".
Findings deliberately add no warning: the existing open-notes line already
counts the outstanding ones, agent-written included, so warning again would
double-count. Nothing was added to the merge path — `MergeFeatureDialog` was not
touched at all, and its confirm button is still gated only on `busy`.

Agent notes are badged with a new `NoteAuthorChip` in `ui.tsx`, mirroring
`TicketKindChip` exactly (renders nothing for the default author). Its CSS
shares one rule with `.chip-kind-review`. The badge is the *only* thing that
differs about those rows — toggle, edit, delete and promote-to-ticket are
untouched, since an agent finding is precisely what the Fix loop consumes.

One deviation worth naming: `ReviewBody` now reads `notes.list` once and passes
the rows down to `NotesPanel`, which previously read them itself. The summary
needed the notes to count findings, and a third observer of that query key would
have let the count disagree with the list directly beneath it.

## Surprises

- **The documented web-typecheck baseline is stale.** The three pre-existing
  `EnableAfkCard`/`SettingsOverlay` errors the prompt says to ignore are already
  fixed on this branch by ancestor commit `bf6470f` ("name query data at the
  router, not off the hook"). `bun run --filter '@runcastle/web' typecheck` is
  fully green, so I treated any error there as mine.
- **`apps/web` has no component-test setup** — no testing-library, no jsdom; all
  17 web test files are pure-logic tests over `src/lib`. So "whatever component-
  test pattern the app already uses" is: keep view logic in `feature-ui.ts` and
  test it there. That is what I did (21 new cases); the `.tsx` changes stayed
  thin enough to be read rather than tested.
- **`bun run test` has one failure that is not mine and not in the listed
  baseline**: `packages/server/test/dev-pane.test.ts:183` expects a PTY process
  group to be reaped after kill and finds it alive. It fails identically on a
  targeted run, imports only `packages/server/src/pty/*`, and my entire diff is
  inside `apps/web` — it cannot reach it. Container process-reaping fault.
  1699 tests pass; both typechecks are clean.
- Ticket rows already carry `error` and `digest`, so the failure reason needed
  no API change, exactly as the ticket hoped.

## Left undone

- **Multiple review tickets per feature.** `reviewOutcome` takes the *last*
  review ticket, which is right for lap 1 (spec pins one per feature) but would
  under-report if two review tickets disagreed. The function is the seam that
  has to aggregate when that lap lands; the doc comment says so.
- **The `waiting` state is rendered but never really reachable today** — G4 means
  all tickets are terminal by the time the review screen shows. It exists so a
  mid-burn review ticket cannot be misreported as "ran".
- Findings are counted feature-wide, not lap-scoped, because `notes.list` is not
  lap-filtered. If notes ever accumulate across laps, the count on lap 3 will
  include lap 1's agent findings. Untouched — changing the query's scope is a
  server-side decision beyond this ticket.

## 5. Review agent records a walkthrough video; server stores and serves it

# Ticket 5 — review walkthrough video: recorded, stored, served

## What was done

Two surfaces, as the ticket framed them.

**Routes.** `packages/server/src/routes/reviews.ts` is a new Hono sub-app mounted at `/api/reviews`
next to `/api/hooks` in `index.ts`, in the same runtime-ctx style (`getRuntimeCtx`, no DI threading).
`GET /api/reviews/:featureId` lists the feature's review-kind tickets as
`{ticketId, seq, hasVideo, videoUrl}`, with `hasVideo` stat'd off disk each request and `videoUrl`
null when there is nothing to stream; a feature with no review tickets — or no feature at all —
returns `[]`, not an error. `GET /api/reviews/ticket/:ticketId/walkthrough.webm` streams the file
with `Content-Type: video/webm`, `Accept-Ranges: bytes`, and manual `Range` handling (single range,
open-ended, suffix, clamped end, 416 when it starts past the end; anything unparseable or multi-range
falls back to 200 with the whole file, which RFC 9110 permits). Nothing a caller sends is ever joined
into a path: the ticket id is looked up in the DB first, and the path is then computed from the row's
own id by a new `reviewWalkthroughPath(ticketId)` helper in `packages/core/src/paths.ts` —
`reviewDir` plus one fixed filename. A non-review ticket 404s exactly like a missing file.

**Prompt.** `packages/skills/burner/review-ticket.md` now wraps browser walkthroughs in
`agent-browser record start <path>` / `record stop`, aimed at a new `{{WALKTHROUGH_PATH}}` placeholder
that `workflows/review-ticket.ts` fills from the same helper. Recording failures are explicitly
swallowed (notes stay the deliverable), the recorder is stopped in the same step-5 cleanup that stops
the drive and browser — including on the "could not review" path — and non-browser reviews skip
recording entirely. The closing-summary step now tells the agent to say when it reviewed a
partially-built feature (ticket 6's blockedBy carve-out is what makes that reachable).

Deviation from the ticket, minor: rather than duplicating the `walkthrough.webm` literal in the route
and the workflow, I put it in core's `paths.ts` beside `reviewDir`, which is where every other path
computation in this codebase lives.

## Surprises

- **Bun drops `Content-Length` on a streamed body.** Verified by curl against a real booted server:
  the 200 and 206 replies come back `Transfer-Encoding: chunked`, so the `Content-Length` the handler
  sets survives under node/undici (where the tests assert it) but not under Bun. `Content-Range` is
  present on 206 either way, which is what a scrubbing player actually needs — but if the review UI
  ever wants a progress bar before the first byte, that is the thing to revisit.
- **The review agent cannot query ticket statuses.** `get_feature_context` resolves a *session*, and
  a review agent identifies by run header, so it has no MCP wire that would tell it which
  implementation tickets failed. The partially-built-feature sentence therefore tells the agent to
  recognise the situation by its signature (a surface missing outright rather than misbehaving)
  instead of instructing it to look the fact up.
- `packages/server/test/dev-pane.test.ts > "kills the child process tree…"` fails in this sandbox,
  and is NOT in the prompt's baseline list. It fails identically in isolation and its import graph
  (pty/dev-pane, services/events) is disjoint from everything this ticket touched — it asserts a
  process group is reaped within 400ms, which this container does not honour. Rest of the suite:
  1729 passed.

## Left undone

- **No UI.** The ticket scoped this to curl; `ReviewBody` still shows notes only. The listing route
  is the seam the player will hang off — note that it is plain HTTP, so the web app needs an absolute
  or proxied URL rather than the tRPC client.
- **No `HEAD` support** on the video route, and no `ETag`/`Last-Modified`. A recording is immutable
  once written, so caching headers would be nearly free if playback ever feels heavy.
- **Nothing prunes old `reviewDir` trees.** A re-burn of the same ticket wipes its own directory
  (existing behaviour), but videos from previous laps' review tickets accumulate under
  `~/.runcastle/reviews/` forever, and nothing reports how much disk that is.

## 6. Review survives failed implementation tickets and shows its purpose while driving

# Ticket 6 — review survives failed implementation tickets; drive purpose on the wire

## What was done

Two changes, both in `packages/server`.

The burner's blocker semantics gained a review-only carve-out. `burnTickets`'
`satisfied` helper now takes the ticket asking, and counts a `failed` blocker as
satisfied when that ticket is a `review` one; the cascade branch in `readyState`
defers to the same helper, so implementation tickets keep the old behaviour byte
for byte. A blocker that is *missing* from the run still cascades whatever the
kind — that is a malformed graph, not a ticket that tried and failed. The
defensive hold (a review waits while any implementation ticket is pending or in
flight) is untouched.

Digest honesty landed as a new module-private `harvestDigest` closure that both
the done path and `failTicket` now go through: for a review ticket it prefixes
the run-digest entry with `> Reviewed with failed implementation ticket(s): N.`
Deviation from the ticket's sketch: it reads the failed tickets off the run's own
ticket set rather than off `blockedBy`, mirroring `implementationsSettled`, so a
review emitted without edges still records what failed under it. Only the run
digest is annotated — `ticket.digest` stays the agent's own words.

`DriveInfo` gained an optional `purpose`, populated from the drive state for
feature drives and absent for a dry run. Because `feature.driveInfo` is an
un-schema'd tRPC query, that types the whole wire the review screen polls with no
router change; a test asserts it end-to-end through the tRPC caller.

## Surprises

The three pre-existing `apps/web` typecheck errors the prompt lists as baseline
are gone — `bun run typecheck` (which now filters web and design-system too) is
fully green on this branch. The only red anywhere is the documented environmental
`dev-pane.test.ts` "kills the child process tree" failure.

## Left undone

No UI consumes `purpose` yet — the review screen's test-drive card still says
"test drive active" while a review agent drives (next ticket, by design). The
prompt sentence telling the review agent to mention failed implementation
tickets in its summary note is this lap's routes ticket, not mine, so
`packages/skills/burner/review-ticket.md` was left alone as instructed; until it
lands, the run digest's annotation is the only place that fact is recorded.

## 7. Review screen plays the walkthrough and tells the truth while review runs

# Ticket 7 — review screen plays the walkthrough, and tells the truth while review runs

## What was done

Three surfaces in `apps/web`, plus two new pure functions in `lib/feature-ui.ts`
(`reviewWalkthroughUrl`, `driveWheel`) with tests beside the existing
`reviewOutcome` cases. The player is a native `<video controls preload="metadata">`
in a new `WalkthroughCard` in `ReviewBody`, rendered only when a review actually
recorded; the listing comes from a new `lib/reviews.ts` holding the app's **first
non-tRPC query** (`useQuery` + fetch on `/api/reviews/:featureId`, same-origin via
the Vite proxy), whose key prefix `lib/live.ts` now invalidates on every SSE push —
no polling interval. Run lanes got the existing `TicketKindChip`. The drive label
branches through `driveWheel`, whose human wording is byte-identical (a test pins
the exact sentence).

Two deliberate deviations from the ticket's sketch:

- **The drive card had to change its source, not just its copy.** It gated on
  `driving`, which is React state this browser sets when *it* starts a drive — a
  review drive started by an agent on the host is simply absent from it, so
  branching on `purpose` alone would have relabeled a card that never rendered. It
  now shows live status on `isDriving || ownDrive` (server truth). Side benefit: a
  human drive now survives a page reload on this card, which it did not before.
- **Stop needed adding, not relabeling.** For the same reason, both existing Stops
  (next-step bar, status bar) are invisible during a review drive. Rather than
  touch `nextStep` — which the ticket forbade — I put a `Stop the review drive`
  button in the drive card itself. `feature-ui.ts` is 65 insertions and **zero
  deletions**, so the three review verbs and their priority are provably untouched.

## Surprises

- **The documented baseline is stale in two ways.** The three pre-existing
  `@runcastle/web` typecheck errors are *gone* (something after that note fixed
  `EnableAfkCard`/`SettingsOverlay`), and root `bun run typecheck` now filters web
  in too. Both are green.
- **One test fails that the baseline does not list:**
  `packages/server/test/dev-pane.test.ts > kills the child process tree…` — it
  asserts a process group is reaped, and fails in isolation as well as in the full
  suite. Not mine: this ticket's diff is seven files, all under `apps/web`, so the
  server code it exercises is byte-identical to the base commit. It reads as this
  sandbox's process reaping, not a regression. Everything else: 1741 passed.
- `ReviewTicketArtifacts` could not be imported from the server — the web tsconfig
  maps `@runcastle/server` to the router barrel only. Mirrored it locally with a
  pointer comment, the way `lib/live.ts` already mirrors `LiveSignal`.

## Left undone

- **The dev pane stays hidden during a review drive** (`isDriving && ownDrive`,
  untouched). Showing it would let the human watch the agent's dev server output
  and click "Open app" live — genuinely useful, and now a one-token change — but
  the ticket did not ask.
- **The status bar can never announce a review drive**, for the client-state reason
  above. It shows nothing rather than something wrong, so it is not lying; hydrating
  `driving` from `driveInfo` would fix it globally but flows into `nextStep`'s
  `ctx.driving` and would have changed the review verbs.
- **The card heading stays "Test drive"** even while it reads "review agent
  driving" underneath. Deliberate: the label carries the criterion, and swapping
  the heading is more human-copy surface than the ticket licensed.
- The three non-`devPaneId` states of `DriveStatus` ("checked out — nothing
  started") still use human-oriented wording; a review drive in that state is a
  review that is failing anyway.
