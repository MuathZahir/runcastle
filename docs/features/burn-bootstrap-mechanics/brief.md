# Burn bootstrap mechanics

## Ticket 1

Create the burn cache directories that burnCacheEnv points at. packages/server/src/workflows/burn-cache.ts:102-103 sets TMPDIR to ${BURN_CACHE_MOUNT}/tmp and NODE_COMPILE_CACHE to ${BURN_CACHE_MOUNT}/node-compile, but nothing creates either: ensureBurnCacheVolume (burn-cache.ts:204-232) only creates the volume and chowns it, buildSlotSetupCommand (ticket-burner.ts:1513-1528) only mkdirs the slot dir, and the host-side mkdirSync at ticket-burner.ts:4069 is skipped for volume mounts. Result observed on a real project: every ticket died on a missing /home/agent/cache/tmp until the operator pasted `mkdir -p /home/agent/cache/tmp &&` into their setup command. Fix: mkdir -p tmp, node-compile and the store/<pm> path (storePath at burn-cache.ts:79) inside the slot setup command, before the project's setup command runs, for both the slotted path and the no-slot fallback. Unit test: the rendered slot setup command contains the mkdir for every path burnCacheEnv references, derived from the same constants so they cannot drift.

## Ticket 2

Stop preflight-probing binaries that setup itself shims, and surface unrunnable gates once on the run card instead of in every digest. Today preflightCommandNames (ticket-burner.ts:211) extracts command names from the setup and verify commands and probes them all with `command -v` (buildToolchainProbeArgs :231) before setup runs; a project whose setup enables pnpm via corepack fails preflight on `pnpm is not installed in image` even though setup would have provided it. Separately, when a verify command needs a runtime the image lacks (a real case: root typecheck dying on a Python-dependent package), the only record was prose in 28 ticket digests. Two changes. (1) Preflight: skip names the setup command itself provides (at minimum: any name that appears as an argument of `corepack enable|prepare`, `npm i -g`, `bun add -g`, or a shim/alias it defines); keep probing the agent binary and everything else. (2) An unrunnable-gate protocol: packages/skills/burner/implement-ticket.md tells the agent that when a verify command cannot run at all (command not found, missing runtime) it writes GATE_UNRUNNABLE.md at the sandbox root with the exact command and error and continues with the gates it can run, never treating it as its own failure; the burner reads that file at ticket end (next to where it reads BLOCKED.md, interpretRunResult :2123) and emits a `ticket.gate_unrunnable` event with command and error, and the run card shows it once per distinct command. Tests: preflight name extraction skips shimmed names; a sandbox result containing GATE_UNRUNNABLE.md yields the event and does not flip the ticket to failed.

## Ticket 3

Commit runcastle's own docs checkpoints with hooks off. Every docs checkpoint (scaffold at features.ts:535, outcome at outcome.ts:123, the pipeline-docs sweep at git.ts:1786, and the six MCP checkpoints in mcp/server.ts:2252-2503) funnels through commitDocs (git.ts:1736), which runs `git commit` with repo hooks enabled. On a project with husky + commitlint the hardcoded `runcastle:` subject is rejected, the lap's docs stay uncommitted, and the dirty tree then blocks the next test drive; observed on a real project on 2026-09-14. Fix: commitDocs passes --no-verify (these are runcastle's commits, not the human's; burn commits are the agent's own and stay as they are), and the subject prefix becomes a per-project setting defaulting to `runcastle:` so a project can choose `docs(runcastle):` or similar; wire it through the settings service and UI like other per-project fields. Do NOT reword the `ticket(<seq>):` subject burn agents use. Tests: commitDocs invokes git with --no-verify; the prefix setting is honoured by every checkpoint site (assert through one shared helper rather than seven strings).

## Ticket 4

Teach the burn timing categoriser Codex tool names. classifyToolCall (ticket-burner.ts:1938) maps only Claude Code tool names (TOOL_NAME_CATEGORY :1898: Read, Grep, Glob, Edit, Write, Notebook*) and treats every other non-Bash name as `other`; the runtime is never consulted. On a real Codex burn 323 of 534 attributed minutes landed in `other` and 30 of 36 tickets showed 0 test time though their logs show 18-29 test runs each. Fix: classify by runtime; for Codex map its shell tool (whatever the stream labels it: `shell`, `local_shell`, `exec_command` or similar — verify against the actual burn stream events, do not guess) through BASH_PATTERNS, and map `apply_patch` to file-edit and any read/search tool to file-read/search. Also emit a structured `burn.tool_error` event when a tool call result carries an error, if the stream exposes it; if the sandcastle stream does not expose tool results, say so in the digest and do not fake it. Tests: a Codex-shaped tool event sequence produces tests/typecheck/file-edit categories, not `other`.

## Ticket 5

Make the sandbox mirror-push hook tolerate an amended commit. A burn agent amended a commit; the post-commit sync hook installed at ticket-burner.ts:1394 pushes the attempt branch to the mirror and rejected the rewrite as non-fast-forward; the agent recovered by merging the branch into itself, leaving a permanent no-op merge in the feature's history. Fix: the hook pushes with --force-with-lease for the ticket's own attempt branch (it is private to that ticket under ADR-0002, so a rewrite of it is safe), and implement-ticket.md states plainly that amending is allowed on the attempt branch and that the agent must never merge a branch into itself. Test: a rewritten attempt branch syncs without error in the hook's unit coverage.

## Ticket 6

Rebuild-image says which Dockerfile it is about to build. The settings 'Rebuild image' action built the stock template while the operator expected their project's own Dockerfile, and there was no way to tell before clicking. Fix: the button's label or confirm text names the resolved Dockerfile path (project-owned .runcastle/sandbox/Dockerfile vs the packaged stock template) and the tag it will produce, using the same resolution the build uses (services/project-image.ts and services/sandbox-image.ts), so the text cannot disagree with the action. Also warn in the run-lane model menu when a `kind: review` ticket is assigned a model whose roster note marks it as an implementer-only model. Tests: the label reflects each resolution branch.

## Ticket 7

Loud recovery after a server restart kills a burn. When the server restarts mid-run the runner reconciles the run (run.reconciled) and the feature parks silently at Building with no run; the operator saw nothing and the lap was lost. Fix: on reconciliation of a run that was live, emit an event the feature's next-step bar renders as a persistent alert ('A burn was interrupted by a server restart: N tickets landed, M pending') with one action, Resume burn, that calls the existing restart path (feature.burn's `restarting` branch, features.ts:699-759, which already sweeps orphaned burning tickets). No auto-resume without a click. Tests: a reconciled live run yields the event; the resolver offers Resume burn only while pending tickets exist.
