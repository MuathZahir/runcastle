# Decisions — persistent-burn-cache-volume

## 1. All caches in one lap, each one proven in a real container
**Decision:** Lap 1 ships the whole cache set — pnpm store, per-package `.tsbuildinfo`, vitest/jest cache, turbo cache — not a pnpm-only skeleton. Every cache type added is verified by actually running containers (cold burn → warm burn, measured), and that verification is the review agent's job, not a unit test's.
**Why:** A pnpm-only slice gives users a fraction of the promised win; the feature is only worth shipping if a burn's first typecheck and test run warm, not just install. A cache that is mounted but never hit is indistinguishable from no cache without running the real thing.

## 2. Persistent slot workspaces on the volume, not four redirected caches
**Decision:** One Docker named volume per project. It holds the pnpm/bun store and N persistent repo checkouts — one per burn-concurrency slot (`<vol>/slots/<n>/repo`). A burn claims a free slot, syncs it (`git fetch` + `reset --hard <base>` + `clean -fd`, keeping gitignored `node_modules`/`dist`/`.turbo`), runs the install command (near no-op on a warm slot), and the agent works there. The slot path replaces `/home/agent/repo` as the isolated hot path (ADR-0005); the named volume replaces the bind-mounted store ADR-0004 rejected.
**Why:** The "redirect each tool's cache into the volume" design is not feasible: pnpm/bun only hardlink when the store and `node_modules` share a filesystem, and tsc/vitest have no env or CLI lever at all — their caches live inside the checkout and are keyed to a stable path. Keeping the whole working folder makes every cache (node_modules, `.tsbuildinfo`, vitest, jest, turbo) persist with zero per-tool tricks, and only the store is shared between concurrent containers — the one cache designed for it. Cost accepted: a burn no longer starts from a byte-fresh clone; stale ignored files are mitigated by the fixed sync step and lockfile-hash invalidation.

## 3. Mount the named volume via a bun patch of sandcastle; upstream later
**Decision:** Add a `patches/@ai-hero/sandcastle@0.12.0.patch` (via `patchedDependencies`, precedent `node-pty`) that lets a mount name a Docker/Podman volume instead of a host path. Keep the exact `0.12.0` pin. Open an upstream PR as a parked follow-up so the patch can be retired.
**Why:** Sandcastle 0.12.0's `resolveUserMounts` refuses any `hostPath` that is not an existing host directory and `DockerOptions` has no raw-arg pass-through, but the `-v` flag it emits already accepts `name:/path` — the patch is a few lines of validation. A bind mount is not an option (ADR-0004: no hardlinks across it); waiting on upstream blocks the feature.

## 4. Slots are claimed per ticket, in memory, for the whole ticket run
**Decision:** Slots are numbered `1..burnConcurrency`, created lazily. A ticket claims the lowest free slot before its first iteration, keeps it across every iteration (sandcastle rebuilds the container per iteration — the slot survives that), and releases it in the same `finally` that emits `ticket.timing`, so every exit path (success, failure, abort, crash) frees it. The lock is an in-memory set in the burner; nothing about ownership is persisted on the volume. Reviews run on the host and never take a slot.
**Why:** The server is the only spawner, so in-process locking is sufficient and a server restart (which kills the burns) frees everything — no "stuck slot" state can exist on disk. Per-ticket rather than per-iteration claiming is what turns ADR-0008's per-iteration re-install into a seconds-long re-sync.
**Resilience the sync step must guarantee** (a slot is never trusted to be clean, only made clean): remove stale `.git/index.lock` / `.git/*.lock` left by a killed container; `git fetch` + `reset --hard` + `clean -fd` (ignored dirs kept); if the slot's git dir is corrupt or missing, delete the slot dir and clone fresh — a slot is a cache, and the worst case is one cold burn. A `burnConcurrency` decrease leaves higher-numbered slot dirs unused (harmless disk, reclaimed by the operator's clear action); an increase creates them lazily.

## 5. Invalidate on toolchain change, not on lockfile change
**Decision:** No lockfile-hash wipe. Each slot carries a stamp (`<slot>/.runcastle-stamp`: sandbox image id, Node version, package manager name + major, package manager detected for the repo). If the stamp mismatches at claim time, the slot's `node_modules` and gitignored build outputs are wiped before sync — one cold burn, then warm again. Lockfile changes are left to the package manager's `--frozen-lockfile` reconciliation, which is its normal `pull && install` path.
**Why:** Package managers reconcile an existing `node_modules` against a changed lockfile correctly and cheaply; wiping on every lockfile change would throw away the warm state on exactly the burns that touch dependencies. What they do not survive is the ground shifting underneath — a new Node ABI breaks native modules, a pnpm major changes the store and `node_modules` layout — and the stamp catches precisely those. Everything else is the operator's explicit clear action (decision 6).

## 6. Operator controls: one clear button, one config-only kill switch
**Decision:** (a) `system.clearBurnCache` mutation → `docker|podman volume rm <volume>`, refused with a clear reason while any burn is active; surfaced as a button beside "build image" on the AFK card, showing the volume's current size. (b) `burnCache: 'volume' | 'off'` in `RuncastleConfig`, default `'volume'`, config-only like `burnWorkspace` — `'off'` is exactly today's behaviour. Providers other than docker/podman behave as `'off'` automatically.
**Why:** A cache the operator cannot see or drop is a support ticket waiting to happen; a kill switch makes any cache-induced weirdness diagnosable in one config change. Keeping the switch out of the settings UI matches the precedent for burn-internals knobs.

## 7. A probe script proves every cache type in real containers
**Decision:** `bun run burn-cache:probe <repoPath>` runs two consecutive burn-style containers through the real burner path (claim slot → sync → install → verify) and prints a per-cache table: install cold vs warm; `.tsbuildinfo` present and hit on run 2; jest / vitest / turbo cache dirs populated and hit; pnpm store hardlinked (link count > 1), not copied. Non-zero exit on any expected cache miss. This feature's review ticket runs the probe against a fixture pnpm + `tsc -b` + vitest + turbo monorepo and a second small jest repo, with the table in the review digest.
**Why:** A mounted cache that is never hit looks identical to no cache; only a real cold→warm pair proves it. Making the proof a script rather than an improvised review keeps it rerunnable on every future burner change and lets it become a doctor probe.

## 8. `burnCache: 'volume'` implies the slot workspace on every host
**Decision:** With the cache on, burns use the slot workspace on Linux, macOS and Windows alike; `burnWorkspace` (ADR-0005) only applies when `burnCache: 'off'`. The volume is initialised host-side: `docker volume create <name>` then a one-shot `docker run --rm --user root -v <name>:/mnt <sandbox image> chown 1000:1000 /mnt` (same for podman), because the burn container always runs `--user 1000:1000` and cannot fix a root-owned volume itself.
**Why:** ADR-0005 kept Linux on the bind mount because isolation only added clone overhead; a warm slot has no clone overhead and carries the caches, so the trade flips. One code path on every host also means the probe (decision 7) proves the setup every user actually runs.

## 9. Setup time becomes measurable
**Decision:** The setup hook is timed; `ticket.timing` gains a `setup` category (per iteration, summed), and `burn.setup` carries `slot`, `cold | warm`, and the sync and install durations.
**Why:** ADR-0008's telemetry is the yardstick the brief says the win must be verified with, and today setup falls into `wallMs` with no bucket — the feature's headline number would otherwise be unobservable outside the probe.

## 10. With the cache on, every package-manager store lives on the volume
**Decision:** When `burnCache: 'volume'`, the ADR-0004 download-cache bind mounts are not attached; instead the container gets `npm_config_store_dir` + `pnpm_config_store_dir`, `BUN_INSTALL_CACHE_DIR`, `npm_config_cache`, `YARN_GLOBAL_FOLDER` pointing at `<vol>/store/<pm>`, and `TMPDIR` + `NODE_COMPILE_CACHE` pointing at the volume (jest's default cache and Node's compile cache follow). With `'off'`, ADR-0004's mounts stay exactly as today.
**Why:** Bun hardlinks from its cache like pnpm does, so a bind-mounted bun cache is the cross-filesystem copy case; the volume shares a filesystem with the slots. One mechanism for all package managers is also one thing for the probe to prove.
