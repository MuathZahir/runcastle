# Outcome — Persistent burn cache volume

Mount a persistent per-project Docker named volume into burn sandboxes carrying the pnpm store, per-package .tsbuildinfo, vitest/jest and turbo caches, so setup and every burn's first verification run at warm instead of cold prices.

- Shipped: 2026-08-28
- Lap: 1

## 1. Named-volume mount patch, burn-cache config knob, volume manager and slot allocator

# Ticket 1 — named-volume patch, burnCache knob, volume manager, slot allocator

## What was done

All four building blocks landed, tested, and unwired — nothing touches the burn path yet.

**Sandcastle patch.** `patches/@ai-hero%2Fsandcastle@0.12.0.patch` + a `patchedDependencies`
entry. A mount entry may now carry `volume: '<name>'` instead of `hostPath`; `resolveUserMounts`
skips host-path expansion and the existence check for it, and the name reaches `docker run` as
`-v <name>:<sandboxPath>`. **Deviation from the ticket:** the patch also suppresses the SELinux
`:z` suffix for a volume mount (host-path mounts keep it). `:z` on a named volume asks the engine
to relabel the volume's whole tree on *every* container start, which is ruinous for a multi-GB
cache — and it is what makes the emitted pair literally `-v x:/path` as the acceptance criterion
states. Four hunks in `chunk-VOG34SRF.js`, `chunk-CP3TYXZA.js` and three `.d.ts` files;
`MountConfig` became a two-arm union (`hostPath` XOR `volume`).

**Config.** `burnCache: 'volume' | 'off'` (default `volume`) in core's schema, `RUNCASTLE_BURN_CACHE`
in `config-load`, and `resolveBurnCacheMode(config)` returning `'off'` for anything that is not
docker/podman. Config-only: no `DESCRIPTORS` entry, no web `META` entry — a test now pins that
absence for `burnCache`, `burnWorkspace` and `burnGuard` together.

**`packages/server/src/workflows/burn-cache.ts`.** `burnCacheVolumeName`, `ensureBurnCacheVolume`
(inspect → create → chown only when it did not exist), `removeBurnCacheVolume` (throws
`BurnCacheBusyError` carrying the held slots), `burnCacheVolumeSize`, `createSlotAllocator` /
`getBurnSlotAllocator`, and the constants ticket 2 needs (`BURN_CACHE_MOUNT`, `slotRepoPath`,
`storePath`, `burnCacheEnv`). All engine calls go through the doctor's injected `ExecFn`, so the
tests assert exact argv with no Docker on the box.

## Surprises

- **`bun patch` does not work in this repo.** Bun 1.3.14 installs this workspace with the isolated
  linker (root `node_modules` holds four packages; everything real lives under `node_modules/.bun/`),
  and `bun patch @ai-hero/sandcastle` dies with `error overwriting folder in node_modules: FileNotFound`
  from both the root and `packages/server`. The patch was generated by hand instead: copy the pristine
  package into a scratch git repo, edit, `git diff --cached --full-index`. `bun install` applies the
  result normally. **Anyone regenerating this patch must use that route, not `bun patch --commit`.**
  Note also that after toggling `patchedDependencies`, a plain `bun install` does not always re-apply
  the patch — `rm -rf node_modules/.bun/@ai-hero+sandcastle@0.12.0 && bun install --force` does.
- **The docker provider drops unknown mount fields**, so carrying `volume` through to
  `formatVolumeMount` needed a second hunk in `chunk-CP3TYXZA.js`. Podman passes the resolved mount
  object straight through and needed none.
- **Asserting the emitted argv required a global vitest change.** Vitest externalises node_modules, so
  a dependency's `import { execFile } from 'child_process'` is loaded natively and `vi.mock` cannot
  touch it. `vitest.config.ts` now has `server.deps.inline: ['@ai-hero/sandcastle']`. That is the only
  reason the patch is testable at all; the full suite still runs in ~36s. The test was verified red
  (4 of 6 failing) with the patch removed and green with it back.
- **`docker`/`podman system df -v --format json` output could not be verified** — no container engine
  in this sandbox. Rather than pin one guessed shape per engine, `burnCacheVolumeSize` walks whatever
  JSON came back looking for a record named `Name` **or** `VolumeName`, reads `Size` or the nested
  `UsageData.Size`, and accepts either a raw byte count or a human string (`"1.25GB"`, decimal and
  binary suffixes). Unreadable → `null`, never a guess. **Ticket 3 / the review should confirm the real
  output against a live engine**; if it disagrees, the fix is confined to `findVolumeSize`.
- **The stated baseline in the burner prompt is stale** ("118 files, 1768 passed"); this branch is 138
  files / 2331 tests. One test fails: `packages/server/test/dev-pane.test.ts > kills the child process
  tree so the port-holder is not orphaned`. I confirmed it fails identically at the pre-ticket commit
  `a3bcbd0` in a scratch worktree — it is an environment fault (process-group reaping in this
  container), not mine. Typecheck is 0 errors.

## Deliberately not done

- **`SlotAllocator` gained one method the ticket did not list: `resize(capacity)`.** Without it
  `getBurnSlotAllocator(capacity)` would silently ignore its argument after the first call, and
  `burnConcurrency` is a live setting with `restartRequired: false` — an operator lowering the width
  would still get the old number of slots. Held slots above a lowered capacity stay held.
- Nothing wires into the burner: `ticket-burner.ts` is untouched, `CacheMount` has not grown a
  `volume` field, and `buildSandboxOptions` still yields only the ADR-0004 bind mounts. That is
  ticket 2's seam, and it will need `CacheMount` to become a union mirroring the patched `MountConfig`.
- No `system.clearBurnCache` mutation and no AFK-card button — ticket 3. `BurnCacheBusyError` is a
  plain `Error` subclass, so `toTRPCError` maps it to `INTERNAL_SERVER_ERROR`; ticket 3 should add a
  mapping (`PRECONDITION_FAILED` or `CONFLICT`) when it wires the mutation.
- No `burn-cache:probe` script (decision 7) and no fixtures — not in this ticket's criteria.
- **Drive machinery: no edit needed and none made.** This ticket adds no service, no required env var
  (`RUNCASTLE_BURN_CACHE` is optional with a default), no seed and no extra process, so
  `.runcastle/drive-setup.ts` / `drive-stop.ts` are unchanged. I checked that both files still exist
  and are referenced correctly; I did not run them (no services in this sandbox, as instructed).

## 2. Burn on a persistent slot workspace with the cache volume mounted

# Ticket 2 — burn on a persistent slot workspace with the cache volume mounted

## What was done

Ticket 1's pieces are now wired into the burn path. `CacheMount` became a
`HostPathMount | VolumeMount` union mirroring the patched sandcastle
`MountConfig`; `buildSandboxOptions`/`selectSandbox` gained an `env` map;
`BurnWorkspaceMode` gained `slot`, which `resolveBurnWorkspaceMode` returns on
every platform whenever `resolveBurnCacheMode` says `volume`. A ticket claims one
slot for its whole run through a new exported `withBurnCacheSlot` and gives it
back on every exit path; the resolver pass reuses that slot rather than claiming
a second. `buildSlotSetupCommand` renders the sync script (safe.directory, lock
removal, clone-or-fetch/reset/checkout -B, `clean -fd`, stamp compare with
wipe-then-restamp, then the shared steps, then the marker line). `ticket.timing`
gained a `setup` category and `burn.setup` now carries `{ slot, cold, syncMs,
installMs }`.

Three deviations from the ticket's sketch, all deliberate:

- **The steps `isolated` and `slot` share are now one helper** (`buildRepoSetupSteps`)
  rather than copied. The isolated script renders byte-identically apart from one
  change the persistence forced: the `.git/info/exclude` append is now guarded by
  `grep -qxF`, because a slot outlives its burn and an unguarded `>>` would add a
  line per attachment-carrying burn forever.
- **The mount/env choice is a pure exported unit** (`buildBurnCacheMounts`), not an
  if/else inside the burn path. Acceptance criterion 1 ("volume mount + burnCacheEnv
  and *no* pm bind mounts") is otherwise only true by construction, with no seam to
  observe it at. The spec's seam 1 asks for exactly this.
- **An exhausted allocator degrades to a cold burn instead of failing the ticket.**
  `hasActiveRun` is per *feature*, so two features burning at once can want more
  than `burnConcurrency` slots between them, and `claim()` throws. Failing a ticket
  because a *cache* is busy inverts decision 4's own rule, so `withBurnCacheSlot`
  swallows `BurnSlotsExhaustedError` only and runs the body with no slot — and the
  workspace mode is resolved from the slot the ticket actually holds, not from
  config, so the fallback is coherent (no volume mount, no env, `isolated`/`mounted`
  behaviour).

## Surprises

- **Sandcastle discards a sandbox hook's stdout.** `execOk2(sandbox, hook.command)`
  captures it and throws it away, and `onAgentStreamEvent` never sees it — so the
  `RUNCASTLE_SETUP` marker cannot be parsed off any stream. The script writes it to
  `/home/agent/workspace/.runcastle-setup` instead and the host reads it from
  `burnWorktreePath(repoPath, branch)` on that iteration's **first agent event** —
  by construction the moment after the setup hook finished — then deletes it, so
  the worktree is not left dirty at teardown. That is the only observation point
  that exists: on success sandcastle removes the worktree, so reading after `run()`
  returns is too late. This is safe specifically in slot mode, where the agent
  never works in the mounted workspace and so cannot commit the file.
- **The `setup` timing category is measured host-side, not from the marker.** It is
  the gap from `timer.beginSetup()` (called immediately before each `run()`) to that
  container's first agent event, plus every inter-iteration gap — which was
  previously discarded outright. So it includes the container rebuild as well as the
  hook. That is the number the operator actually cares about, but it is *not* the
  same as `syncMs + installMs`, which is the hook alone. Both are reported.
- **The toolchain stamp cannot be computed entirely host-side.** The host knows the
  image tag and the corepack pin, but not what Node the image ships, so
  `buildSlotStamp` embeds a literal `$(node --version 2>/dev/null)` that the
  container resolves. The script assigns it to `RC_STAMP` once so the compare and
  the write cannot disagree.
- **The existing `resolveBurnWorkspaceMode` tests passed by accident.** `packages/server/tsconfig.json`
  has `include: ["src"]`, so test files are never typechecked; the helper was
  handing in a config with no `burnCache` at all, which happened to fall through.
  Fixed to pass `'off'` explicitly.
- **Baseline.** `bun run typecheck` is 0 errors. `bun run test` is 2357 passed / 1
  failed: `dev-pane.test.ts > kills the child process tree so the port-holder is not
  orphaned`. That file imports only pty/registry/events/db — nothing this ticket
  touches — it fails identically when run alone, and ticket 1 confirmed it failing
  at the pre-ticket commit `a3bcbd0`. It is the container's process-group reaping,
  not this diff. (The prompt's stated baseline of "118 files / 1768 tests" is stale
  for this branch, as ticket 1 also reported: it is 139 files / 2362 tests.)
- **Drive machinery: no edit needed and none made.** This ticket adds no service, no
  required env var (`RUNCASTLE_BURN_CACHE` is optional with a default), no seed and
  no extra process. I checked that `.runcastle/drive-setup.ts` and `drive-stop.ts`
  still exist and parse; I did not run them, as instructed.

## Left undone

- **Local branches accumulate in a warm slot.** Every burn does `checkout -B <tempBranch>`
  with a fresh unique name, so a long-lived slot collects one ref per burn. Refs are
  tiny but they keep old objects alive against `git gc`. A one-line `for-each-ref |
  grep -vFx | xargs git branch -D` prune in the sync script would bound it; it is not
  in this ticket's step list, so I left it. The operator's clear-cache action
  (ticket 3) reclaims it either way.
- **A stale `.runcastle-attachments/` can survive on a warm slot.** Once the exclude
  line is written, `git clean -fd` treats the directory as ignored and keeps it, so a
  previous attachment-carrying burn's PNGs linger. They cannot be committed (excluded)
  and cannot be mistaken for another ticket's (note ids are unique), so I left it
  rather than restructure the shared attachments step.
- **Remote-tracking refs go stale in a slot.** The sync fetches by path into
  `FETCH_HEAD`, not into `refs/remotes/origin/*`, so `origin/main` in a warm slot is
  whatever the original clone saw. Nothing in the burn contract reads them (the
  resolver fetches explicitly), but an agent running `git log origin/main` would see
  an old tip.
- **No probe script** (decision 7) and no real cold→warm measurement — this ticket has
  no container engine, so the sync script is proven by driving it under `sh` against
  real temp repos, not by running containers. Proving the *caches* hit (`.tsbuildinfo`,
  vitest, turbo, pnpm hardlink counts) is the probe's job and the review's.
- **`BurnCacheBusyError` still maps to `INTERNAL_SERVER_ERROR`** in `toTRPCError`, as
  ticket 1 noted. Ticket 3 owns that when it wires `system.clearBurnCache`.

## 3. Operator surface: burn cache size and clear on the AFK card

# Ticket 3 — operator surface: burn cache size and clear on the AFK card

## What was done

`system.burnCache.status` / `system.burnCache.clear` now exist on the tRPC system router, both
taking `{ projectId }` (the volume is one per project, and nothing else in the request carries
that). `status` returns `{ mode, engine, volumeName, sizeBytes }`; it only shells out to the
engine when the mode resolves to `volume`, so an `off`/`noSandbox` project issues no command at
all. `clear` refuses via `removeBurnCacheVolume`'s `BurnCacheBusyError` when the shared slot
allocator reports held slots, and emits `burn-cache.cleared` on the project timeline on success.

Two deviations worth naming. **First**, the PRECONDITION_FAILED mapping went into `toTRPCError`
in `packages/server/src/errors.ts`, not into the router: `trpc/context.ts` states that routers
and services never construct `TRPCError` themselves, and that helper is the documented single
mapping point. `errors.ts` therefore now imports `BurnCacheBusyError` from
`workflows/burn-cache.ts` — no cycle, because that module's only imports are type-only.
**Second**, `clear` with a non-docker/podman sandbox throws `InvalidInputError` (→ BAD_REQUEST)
rather than silently doing nothing: there is no engine to run the removal with. Clearing is
deliberately still allowed when `burnCache: 'off'` on a docker/podman host — the operator who
turned the cache off is exactly the one who wants the disk back.

On the web, `EnableAfkCard` gained an optional `projectId` prop and renders a burn-cache row
directly under the build-image row when it is present. `SettingsOverlay` passes it; the
first-run wizard does not, because it can run before any project exists. The row is
`BurnCacheRow` (pure, exported, tested with `renderToStaticMarkup` exactly like
`ImageBuildAction`) behind a small `ProjectBurnCache` tRPC wrapper. A refused clear renders the
server's message inline under the button (`afk-verdict is-warn`) instead of as a toast — setting
`onError` also stops the global mutation-error net from double-reporting it. `fmtBytes` is new in
`apps/web/src/lib/format.ts`; it uses decimal units so the number matches what
`docker system df` prints.

## Surprises

- **The ticket's pointer to `setup.ts` emitting around `build-image` does not describe the code.**
  `trpc/routers/setup.ts` emits nothing at all — `startTerminal` just spawns a PTY. The nearest
  real precedent for a project-scoped emit is `services/projects.ts`, so `emitProject` with a
  `project.*`-style dotted type (`burn-cache.cleared`) is what I followed.
- **The AFK card had no project in scope.** It is rendered from the first-run wizard (which may
  precede any project) and from Settings (which has one). Hence the optional prop rather than a
  required one; the row is simply absent in the wizard.
- **`system.burnCache.status` is deliberately NOT on the SSE invalidation allowlist** in
  `apps/web/src/lib/live.ts`. That list is an allowlist precisely because `setup.doctor` shells
  out to probe the machine, and reading the volume size is the same kind of call — putting it on
  the list would run `docker system df -v` on every event of every burn. The emitted event still
  lands on the timeline; the card refetches through an explicit
  `utils.system.burnCache.status.invalidate()` after a successful clear.
- **`docker volume rm` on a volume that never existed will fail**, and the card will show the
  engine's own message. I did not add `--force`: the argv of `removeBurnCacheVolume` is ticket 1's
  and is pinned by its tests.
- **Baseline**: `bun run typecheck` is 0 errors. `bun run test` is 139 files / 2346 tests with
  exactly one failure — `packages/server/test/dev-pane.test.ts > kills the child process tree` —
  which ticket 1 already confirmed fails at the pre-ticket commit `a3bcbd0`. I re-confirmed it
  fails on a single targeted run of that file alone; it is a process-group reaping fault of this
  container and nothing in my diff can reach it. The prompt's stated baseline ("118 files, 1768
  passed") is stale for this branch.

## Left undone

- **Nobody creates the volume yet.** Ticket 2 wires `ensureBurnCacheVolume` and the slot claim
  into the burner, so until it lands `status` will always report `sizeBytes: null` on a real
  machine and `clear` will always hit "no such volume". That is expected, not a defect here.
- **`burnCacheVolumeSize`'s parse is still unverified against a live engine** (ticket 1's own
  caveat: no container engine in this sandbox, so the `system df -v --format json` shape is
  inferred). My test feeds it a `{ "Volumes": [...] }` document with human sizes. If a real engine
  disagrees, the fix stays inside `findVolumeSize`; the router and the card need no change.
- **No settings-UI control for `burnCache`** — config-only by decision 6, and out of scope.
- **Drive machinery: no edit needed and none made.** This ticket adds no service, no required env
  var, no seed and no extra process. I checked that `.runcastle/drive-setup.ts` and
  `.runcastle/drive-stop.ts` still exist and that nothing I added is read at boot; I did not run
  them (no services in this sandbox, as instructed) and they are TypeScript, so `bash -n` does not
  apply.

## 4. burn-cache:probe script and fixture repos proving every cache type warm

# Ticket 4 — burn-cache:probe script and fixture repos

## What was done

`bun run burn-cache:probe <repoPath> [--engine docker|podman] [--keep]` now
exists. It preflights the engine and the sandbox image with doctor-style fix
lines, copies the target into a scratch git repo, and drives **two consecutive
containers on one slot of a probe-only volume** (`runcastle-probe-<hash of
repoPath>`) through the real burner path — `ensureBurnCacheVolume` →
`createSlotAllocator(1).claim()` → `buildSlotSetupCommand` as the
`onSandboxReady` hook → install → the repo's own verify commands — then prints a
`cache | cold | warm | hit` table and exits 1 if any expected row missed, 2 if it
could not run at all. Fixtures `pnpm-monorepo` (pnpm 10 + `tsc -b` composite +
vitest 3 + turbo 2) and `jest-app` (npm + jest 30 + ts-jest) live under
`packages/server/test/fixtures/burn-cache/`, with every version pinned exactly
and lockfiles committed.

Three deviations from the ticket's sketch:

- **The work lives in `packages/server/src/workflows/burn-cache-probe.ts`, not in
  `scripts/`.** `@ai-hero/sandcastle` is a `packages/server` dependency and does
  not resolve from the repo root (verified: both `bun` and `tsc` fail on it), so
  the probe cannot call `createSandbox` from `scripts/`.
  `scripts/burn-cache-probe.ts` is the 30-line entry point the root script name
  points at, exactly as the ticket specified.
- **`createSandbox`, not `run()` with a no-op agent.** Sandcastle 0.12.0's
  `createSandbox` runs `hooks.sandbox.onSandboxReady` and then hands back an
  `exec()` — which is the whole probe, with no agent variance on top of the
  measurement.
- **The fixtures' verify commands name the TOOL, not a package script**
  (`pnpm exec vitest run`, not `pnpm test`). `expectedCaches` reads those strings
  to decide which rows a repo can even have, and `npm test` hides that it is jest.
  The pnpm fixture drives turbo through `build` only, so the tsbuildinfo and
  vitest rows measure tsc and vitest rather than turbo's cache of them.

Commits are `ticket(4): …` per the standing brief, not the
`feat(burn-cache): …` the ticket body suggested.

## Surprises

- **`.tsbuildinfo` does not land in `outDir`.** TypeScript 5.9 writes it beside
  the tsconfig even with `composite` + `outDir` set — which the slot sync's
  `git clean -fd` would delete before every burn, since an untracked file at the
  repo root is not ignored. Both fixtures set `tsBuildInfoFile` explicitly into
  the gitignored `dist/`. **This is a real hazard for any user repo that does not
  gitignore `*.tsbuildinfo`: the slot will never warm that cache.**
- **vitest's results file is one level deeper than the ticket said**:
  `node_modules/.vite/vitest/<sha1>/results.json`, one hash directory per project
  root. The probe globs for `results.json` rather than hard-coding the path.
- **jest's cache directory is `$TMPDIR/jest_rs`** (base-36 uid), not `jest_<uid>`
  — globbed for the same reason. Measured cold→warm locally: 1.43s → 0.81s.
- **The root vitest `include` reaches the fixtures.**
  `packages/*/test/**/*.test.ts` matches the fixture repos' own test files, and
  the jest fixture's globals fail under vitest. `vitest.config.ts` now excludes
  `**/test/fixtures/**`.
- **Baseline unchanged.** `bun run typecheck` 0 errors. `bun run test` is
  2412 passed / 1 failed: `dev-pane.test.ts > kills the child process tree…`,
  which fails identically when run alone and which tickets 1 and 2 both confirmed
  as the container's process-group reaping, not this diff.
- **Drive machinery: no edit needed and none made.** This ticket adds no service,
  no required env var, no seed and no extra process — the probe is a manual
  operator/review tool. I checked that `.runcastle/drive-setup.ts` and
  `drive-stop.ts` exist and parse (an ad-hoc `tsc` on them reports only missing
  node/bun types, no syntax errors); I did not run them, as instructed.

## Left undone

- **Nothing creates `$TMPDIR` on the volume.** `burnCacheEnv` points `TMPDIR` at
  `/home/agent/cache/tmp`, but neither the volume chown nor the slot sync script
  makes that directory. jest and Node's compile cache `mkdir -p` their own
  subdirectory so they are fine, but a tool that assumes `$TMPDIR` already exists
  will fail inside a burn. I deliberately did NOT `mkdir -p` it in the probe:
  that would hide the defect the probe exists to surface. If the review's probe
  run trips on it, the one-line fix belongs in `buildSlotSetupCommand`.
- **The probe has never run against a real engine.** This sandbox has no
  docker/podman, so the containers, the cold→warm table and the exit code are
  unexercised end to end — that is this feature's review ticket's job (decision
  7). Everything reachable without an engine IS exercised: the verdict logic
  under 40 unit tests, the scratch-repo conversion against both real fixtures,
  and both fixtures' full `install → typecheck → test → build` cycles run
  natively on node 22 (the image's base) with their committed lockfiles.
- **`--frozen-lockfile` against corepack in the container is untested.** The pnpm
  fixture's install goes through `corepack pnpm`, which downloads pnpm 10.15.0 on
  first use; in a non-TTY `docker exec` corepack may want
  `COREPACK_ENABLE_DOWNLOAD_PROMPT=0`. That is the existing burner's behaviour
  for every pnpm repo, not something this ticket introduced, so I left it.
- **Row thresholds are duration comparisons on a tiny fixture.** The tsbuildinfo
  and jest rows require the warm command to be strictly faster; on fixtures this
  small the margin is a few hundred milliseconds. The load-bearing half of each
  criterion (the cache file present *before* run 2 started) is not timing
  dependent, but a flaky duration could still flip a row.

## 5. Review: persistent burn cache volume — prove cold→warm in real containers

This lap teaches burns to stop starting from scratch. Until now every burn cloned the repo fresh, reinstalled everything, and paid full cold price on its first typecheck and first test run — on every iteration of every ticket. The lap gives each project a persistent cache that lives with the container engine rather than in the throwaway container: a handful of numbered working folders, one per concurrent burn, each keeping its installed packages, its compiled-output bookkeeping and its test-runner caches between runs, plus one shared package store they all download into. A burn now claims a folder, brings it up to date with a fetch and a reset instead of a clone, and hands it to the agent already warm. There is a new row on the AFK card showing how much disk the cache is using with a button to drop it, a config switch that restores the old behaviour byte for byte, and a repeatable probe command that runs two real containers back to back and prints a table proving each cache type was actually reused.

The mechanism genuinely works, and I proved it in real containers rather than reading the code and hoping. Both fixture projects came out warm on the second run: everything hit — installs, TypeScript's incremental state, vitest, turbo, and the package store hardlinking rather than copying files. Inspecting the volume afterwards showed the working folder intact between runs. The test suite is fully green on a real machine — 2398 passing, nothing failing — including the one test every implementer reported as broken, which turns out to have been an artifact of their own sandbox exactly as they suspected.

What needs your attention is that none of that happens on a clean install. Two small defects sit on the path before any of it, and either one alone stops the feature dead. The step that prepares a new cache volume for writing silently does nothing, because the command it runs gets swallowed by the container image's startup command; and every install then crashes because the feature points the system temp directory at a folder on the volume that nothing ever creates. I had to fix both by hand before I could measure anything. They are one-liners, and the second was predicted in writing by the implementer who left it — but they mean that as merged, the first burn on any machine fails. That is the thing to fix before this is switched on for real.

Beyond those, the findings are about durability rather than function: rebuilding the sandbox image won't invalidate a stale cache folder the way the design said it should, clearing the cache in the middle of a run leaves the next burn unable to write, and the bookkeeping that tracks which folders are in use is shared across all projects instead of per project, so one project's burn can refuse another project's clear. One promise is unproven rather than broken — the headline claim that installs get an order of magnitude faster. The test fixtures are far too small to show it; they went two and a half times faster, and nothing in the repo can currently demonstrate the real-world case the feature was built for. I also could not see the new AFK card row in a browser: the drive's fresh database opens the first-run wizard and its final button doesn't advance, which is unrelated to this lap's changes but blocked that half of the walkthrough. I checked the card's server side directly instead, and both showing the size and clearing the cache work correctly against a live engine.
