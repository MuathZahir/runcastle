How a feature goes

A feature is one thing you want built, like tags on entries. Each one gets its own chat with its own agent, and its own git branch. It goes through four stages, and asks for you only at the points shown below.

  2. Build
  3. Review
  4. Shipped

Planning: talk it through

Describe what you want in the feature's chat. The agent asks about anything unclear, writes the decisions into your repo, and splits the work into tickets: small tasks that can each be built on their own. Nothing is built until you approve the plan.

Design screens in your real app

If the feature adds or changes a screen, the agent first builds that screen in your app, with your app's own components and sample data, and shows it beside the chat. You approve it or ask for changes.

Build: workers in containers

Once you approve, a round of workers builds the tickets. Each worker is an agent working alone in a container. Several work at once, and each commits to the feature's branch. Nothing needs you, so you can close the tab.

Review: it tests the feature first

When the tickets are done, a review agent starts your app, uses the feature the way you would, and records it. It posts a review package in the chat: whether the feature works, the results of your typecheck and tests, any problems it found, and the recording.

Then you try it

A test drive runs the feature's branch of your app inside runcastle, with a notes panel beside it. Write down anything that is wrong, send your notes to the agent, and it fixes them.

A scenario sets the app up before the drive starts, for example with entries that already have tags, so you land on the feature instead of an empty app. Pick one at the top of the drive. The agent writes one when that setup would take several steps by hand, and + New scenario adds your own.

Shipped: you merge

When you are happy with it, press Merge & ship to merge the branch into your main branch. The decisions and the plan stay in your repo, under docs/features/.
